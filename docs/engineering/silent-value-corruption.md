# 静默改值：C# / .NET 里那些不报错却把数变掉的地方

> 起于 2026-09-21。这份和本库其他文档不一样：**它不是某个项目的交接，是一份清单。**

这里只收一种东西：**不抛异常、不写日志、编译器不警告，而值已经变了**的地方。

判断一条该不该进来，问三句：

1. 它出错时**报错吗**？报错的不收——报错的自己会说话。
2. 屏上 / 日志里**看得出来吗**？看得出来的不收。
3. 我**真的撞到过吗**？推想出来的不收，那是最佳实践清单不是这个。

每一条都带：**怎么写会错、症状长什么样、判据怎么写才抓得住**。
抓不住的判据比没有判据更糟——它会让人以为这一块验过了。

## §1 语言本身

### 1.1 两支类型不同的三元表达式，会把两支都提升成"大"的那个

**撞了三次，一天之内，三个不同的人 / agent 写的。**

```csharp
// 内核 Huike.Sdk/Json/JsonScalar.cs，已上线
JsonValueKind.Number => element.TryGetInt64(out long l) ? l : element.GetDouble(),
```

`?:` 的类型是**两支的最佳公共类型**。`long` 能隐式转 `double`，反过来不行
⇒ 整个表达式的类型是 `double` ⇒ **`long` 那一支等于没写**。
再装箱成 `object` 时，箱子里装的是 `double`。

**实测**：`9007199254740993`（2⁵³+1）存下去读回来是 `9007199254740992`。**值变了。**

**症状**：

- `value is long` **恒假** ⇒ 所有按类型分支取参数的代码，在**方案存过一次之后**集体走 else。
- 而 JSON 文件里的数是对的、屏上显示的是对的、没有任何日志。
- 现场那句话是：**"新建的方案好好的，重启软件之后开始出问题。"**

另外两处同一天撞到的：

```csharp
// 参数面板：整数参数交出去的是 12.0
object boxed = integer ? (int)clamped : clamped;      // int 和 double ⇒ double

// 导入老方案：照着内核那一行抄的，被自己的判据当场抓住
```

⚠ **判据要断类型，不能只断值。** 第二处那条判据报的是
`Expected: 12 / Actual: 12`——**两边打印出来一模一样**。

```csharp
Assert.IsType<int>(boxed);          // 这样才抓得住
Assert.Equal(12, boxed);            // 这样抓不住
```

**修法**：拆成语句，让两支各自装箱。

```csharp
if (element.TryGetInt64(out long l)) { return l; }
return element.GetDouble();
```

⚠ **修之前先扫一遍谁在依赖现状。** "读回来都是 double" 跑久了会变成既成契约——
下游那些 `value is double` 的分支会一起哑掉，而它们同样不报错。

### 1.2 `double.TryParse("NaN")` 返回 true

.NET Core 起就是这样，和 `NumberStyles` 无关。`"Infinity"`、`"-Infinity"` 同理。

**症状**：人往上限那一格里打 `NaN`，解析成功、存进方案、之后**每一件都判合格**——
因为 `任何数 > NaN` 和 `任何数 < NaN` 都是 `false`，两头的比较一起失效。
屏上那一格写着 `NaN`，而人不会觉得那是个错误值。

**修法**：`TryParse` 之后再问一句 `double.IsFinite(value)`。

### 1.3 `(int)` 强转是 unchecked 的，溢出直接回绕

```csharp
(int)3000000000L      // ⇒ -1294967296
```

C# 默认 unchecked，编译器不警告（字面量除外）。

**症状**：一个"很大的数"变成**负数**，而下游多半有 `if (n < 0)` 的分支，
于是走进一条"参数非法"的路，报的错和真实原因毫无关系。

**修法**：`checked` 或先比范围。⚠ 判据里要**先证明这个转换真的会回绕**
（断一次 `(int)3000000000L < 0`），否则那条判据在"其实没溢出"的数据上照样绿。

### 1.4 `TimeProvider.GetLocalNow()` 假定 `GetUtcNow()` 返回零偏移

默认实现是 `GetUtcNow() + LocalTimeZone.GetUtcOffset(...)`。
自己写假时钟时如果 `GetUtcNow()` 直接返回一个 `+08:00` 的 `DateTimeOffset`，
本地时间就**多出 8 小时**。

**症状**：时间戳"有点不对"，看起来像时区没配好，而不像类型用错了——
于是人会去查机器的时区设置。

**修法**：假时钟的 `GetUtcNow()` 里 `ToUniversalTime()`。

### 1.5 装箱之后的数值比较按**类型加值**算

```csharp
object a = 3L, b = 3;
a.Equals(b)        // false
```

**症状**：参数"没改过"却被判成改过 ⇒ 自动保存一直在写盘、审计里一串空改动；
或者反过来，改过却判成没改 ⇒ **人改完点保存，什么都没写下去**。

**修法**：比之前先归一（统一转 `double` 或 `decimal` 再比），并且
⚠ 判据要**先证明 `Equals(3L, 3)` 真的是 false**，否则它分不开两种写法。

## §2 存盘与读盘

### 2.1 `DefaultIgnoreCondition = WhenWritingNull` 不管字典的值

它只作用于**属性**。`Dictionary<string, object?>` 里值为 `null` 的键会照常写出去。

这次是**想要的**行为（"人清空了这一项"和"人从来没配过这一项"必须分得开），
但它是 `System.Text.Json` 的行为细节，将来有人改序列化选项就会破。
⇒ 不管你依赖的是"会写"还是"不会写"，**都要用判据钉死**。

### 2.2 `System.Text.Json` 把 `NaN` 写成带引号的名字

`double.NaN` 写出去是 `"NaN"`（字符串），读回来也是**字符串**。

**症状**：一个本该是数的参数，读回来是 `string` ⇒ 按类型分支的代码走 else，
和 §1.1 一模一样的表现。

**修法**：要参与判定的数值**走强类型字段**，别塞进 `Dictionary<string, object?>`。

### 2.3 "原子写"的临时文件名固定时，反而会亲手制造半截文件

```csharp
string tmp = path + ".tmp";      // 内核 HuikeJson.WriteFileAsync
```

两个后果：

1. 两处同时写同一个目标，会抢同一个临时名 ⇒ 后到的可能把先到的**半截内容**
   `File.Move` 成正式文件。**为防半截文件而做的机制，亲手造出了半截文件。**
2. 序列化中途抛异常时 `tmp` 留在原地。它不匹配任何业务后缀 ⇒ **不出现在任何列表里**，
   存失败一次多一个，磁盘慢慢被占满而没人看得见。

**修法**：临时名加随机后缀；`catch` 里删，而且**删除失败要吞掉**——
不能让"收拾现场失败"盖住原始的失败原因。

⚠ **原子性只能靠真的中途失败一次来验。** 判据里要能注入一个"写到一半就抛"的写入器，
然后断：原文件**零字节未变**、临时文件**收拾干净了**。
只断"正常路径写成功"的判据，对非原子实现一样是绿的。

## §3 判据本身

### 3.1 `Assert.Equal(expected, actual, decimals)` 是"各自四舍五入到那一位再比"

不是"差值小于 10⁻ⁿ"。

`Assert.Equal(9.75, 9.747, 1)`：9.75 进位到 **9.8**，9.747 退到 **9.7** ⇒ **红**，
而两者只差 0.003。

**修法**：断误差本身。

```csharp
Assert.InRange(Math.Abs(actual - expected), 0, 0.01);
```

### 3.2 一条"防某种写法"的判据，要自带反证

同一条用例里跑两遍：正确的写法要绿，**错误的写法必须红**，
失败信息直接写"这条判据分不开两种写法，白写了"。

不写反证的话，判据可能对两种写法都绿——而你要等到下一次变异检查才知道。
变异检查不是每次都跑，判据是每次都跑的。

**实例**：分组顺序那条判据原本用「找边/拟合/显示」三个词，
结果它们的 UTF-16 码位顺序**碰巧**和声明顺序一致 ⇒ "按声明排"和"按字母排"
产出同一个结果 ⇒ 判据什么都没防。反证当场红了，换一组词才成立。

### 3.3 拿默认值当样本，等于没有样本

判据里那个"存进去的值"如果正好等于默认值，
"读方案"和"用默认值"就分不开了 ⇒ 一个根本不读方案的实现照样绿。

⇒ 存一个**和默认值不同**的值进去。

## §4 数据的"形状"

前三节都是**语言和库**的坑。这一节是另一类：代码没错、语言没坑，
**只是那段字节的含义和作者以为的不一样**——而算出来的数照样是个正常的数。

### 4.1 按"字节数"遍历一张图，喂进来的通道数一变，数就是几倍

```csharp
ReadOnlySpan<byte> pixels = source.AsReadOnlySpan();
for (int i = 0; i < pixels.Length; i++)
    if (pixels[i] == ForegroundValue) area++;
```

作者心里想的是"每个像素一个字节"（8 位灰度，工业相机出的就是这种）。
喂一张 24 位彩图进来，**三个通道各数一遍** ⇒ 面积约三倍。

**症状**：不抛异常、不写日志、轨迹上那一行显示"完成"、测量值栏里有一个正常数字。
唯一能看出来的办法是拿同一张图手工数一遍——而没有人会去数一个"看着合理"的数。

⚠ **它比 §1、§2 那些更难发现**，因为它连"写法"层面都没有可疑之处：
`AsReadOnlySpan()` + `Length` 是这段代码最自然的写法。
真正缺的是一句**从来没被写下来的前提**：「我只吃 8 位灰度」。

**判据怎么写才抓得住**：

- 断"不同通道数喂进来，结果不同"是**错的方向**——那等于把缺陷编码成期望值。
- 正确的方向是**让前提可读、可查**：把"我收什么"做成一份**声明**（端口上的形态标签），
  然后在入口断言它。这样"作者脑子里的前提"变成了一份**别人读得到的数据**，
  搭链路的时候就能拦住，而不是跑起来出一个三倍的数。
- ⚠ 声明加完要**逐个点名**地断（"这几个算子都必须声明"）。
  只断"声明了的那些表现对不对"的话，**漏声明的那个恰好逃过判据**——
  实测撞过：漏了一个算子，新判据全绿，红的是一条为上一次收口写的老判据。
