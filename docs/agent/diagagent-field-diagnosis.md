## 0. 这是什么 / 现在到哪一步

**目标**：现场调试员在工控机上用浏览器问本地小模型，自己解决简单故障（相机不拍照、PLC 没收到信号、识别不到）；解决不了就一键生成诊断包（zip）发给远程支持喂 Claude。替代"每次都远程连进去看"。

**现状成绩（2026-08-17 收工，8-19 复核代码无变化）**：

| 指标 | 状态 |
|---|---|
| mock 场景全量回归 | **15/15 结论正确、零"自信的错误结论"**（14 场景 + 1 个问法变体） |
| `check_tool_hints.py`（工具层判定断言） | 14/14 |
| `check_tool_coverage.py`（工具覆盖断言） | 10/10 |
| 真机（`DIAG_TARGET=real`）四端点 | 通，8-13 三处修复未退化 |
| 网页 SSE 流式进度 | 通 |
| 全量回归耗时 | 14 条约 **26.4 分钟**（预取改造前是 45 分钟） |
| 单轮耗时（开发机 RTX 2060 6GB） | 清晰故障 41~84s，含糊场景 130~190s |
| 最大功能缺口 | **多轮复读**（助手不知道上一轮自己建议过什么），已 A/B 定性为既有缺陷 |

⚠ **代码状态：外层仓库有一批"已验证但未提交"的改动**，且**外层仓库没有任何 git remote**。迁移见 §2.1。

### 2.1 ⚠ 先解决"代码怎么过去"（最容易踩的一步）

### 2.3 启动（双击 .bat 最省事）

| 方式 | 做什么 |
|---|---|
| `启动-Mock模式.bat` | 杀残留 ollama → `ollama serve`（E 盘模型目录）→ `mock_status_server.py`(:18081) → `webapp.py`(:18080) → 等 18080 起来再开浏览器 |
| `启动-真机模式.bat` / `start_real.ps1` | 设 `DIAG_TARGET=real`，**不起 mock**，并先杀占用 18081 的旧 mock 进程 |
| `停止.bat` | 收摊 |
| 命令行冒烟 | `python agent.py 相机为什么不拍照了` |

**启动顺序铁律**：
1. **mock 和 JET2DVis 抢 18081**。起主程序前必须确认 mock 已停、18081 空着——否则 `DiagStatusServer.Start()` 绑不上端口就直接 `return`，软件照常运行，只有一行 loginfo，**界面上毫无提示**，等于诊断助手静默死掉（8-17 上午为此白折腾一轮，见 §4.13）。
2. **`JET2DVis.exe` 必须用户自己双击启动**。这个 Claude Code 环境里**分离启动的 GUI 进程会被回收**（存活 16s~1min 随机；`Start-Process`、WMI `Win32_Process.Create` 都一样，只有 `Process.Start(UseShellExecute=false)` 且 PowerShell 握着句柄 `WaitForExit` 才活）。曾误以为自己把主程序改崩了，stash 后用 main 代码 A/B 才确认基线一样会退。
3. 改了 `agent.py` / `tools.py` / `config.py` **必须重启 webapp** 才生效；改 `playbook.md` **新会话**即生效。
4. 跑完 mock 回归 `git checkout -- DiagAgent/mock_data/Log/logerror.log` 还原夹具（mock server 每切场景都重写它，仓库基线是空文件）。

## 3. 核心架构心法：三层，越往下越硬

这个项目最值钱的经验就一句：**8B 小模型上，提示词压不住的事，全部下沉到确定性层用代码写死。**

| 层 | 载体 | 管什么 | 可靠性 |
|---|---|---|---|
| ① 手册层 | `playbook.md` → system prompt | 领域知识：症状→查什么→结论 | **最弱**。手册 9433 字符时，中段规则会被 lost-in-the-middle 淹没（实测：prompt 中段"接着调 get_plc_status"被忽略，每轮工具数从 4~5 掉到 2） |
| ② 数据注解层 | `tools.py` 的「状态说明」+「⚠下一步」 | 拿到数据后**该往哪走、该说什么话** | **强**。规则贴在数据旁边，模型抄得到 |
| ③ 控制流层 | `agent.py` 的预取 / 拦截 | **到底查哪些工具、答案放不放行** | **最强**。代码直接执行，不问模型意见 |

三条落地做法：

1. **"要不要调工具"这件事本身不能交给模型决定**。原来是"发系统提示顶回去让它补查"，`nudged` 只顶一次、模型不理就放行 → "必须查满四个工具"实际是随机生效的，这正是"同一故障、问法不同答案不同"的真来源。**改成代码直接执行缺失的工具**，把真实返回作为数据注入上下文并补进 `tool_trace`（网页照常显示查证块）。附带收益：全量从 45 分钟降到 26.4 分钟——顶一次要多花一整轮模型生成（60s+），预取只是几个本机 HTTP。
2. **`tools.py` 里的确定性禁令，只在对应工具真被调用时才存在**。模型不调 `get_camera_status`，"创建句柄失败别让他点【手动软触发】""不要念错误码"就根本不在上下文里。这是①和②必须配③的原因。
3. **出口拦截比提示词管用**：`_all_green()` 在"四工具查满且全绿"时，若回答带 🔍（=在报故障）就追加系统提示顶回去重答一次；半成品回答**不写进 history**（会锚定）。`normal` 控制组的概率性编故障就是这么修掉的。

## 4. 硬经验清单（按价值排序，可直接引用编号）

### 4.1 手册缺分支 = 模型原地打转或编造
调试员说"点了开始运行没用"，手册没有"操作了但没变化"分支 → 助手答"请再点一次"；手册走投无路后开始编（"以管理员身份运行"是手册里没有的）。**这是 playbook 类项目的头号失效模式。** 修法：通用原则加四条硬规则（先读日志→再问界面弹窗原文→**绝不许把刚做过的操作再让他做一遍**→无线索直接升级，不许编手册外方案）+ 给故障一补"第1b步：点开始运行却启动失败"分支。

### 4.2 ⚠ 兜底规则不能写否定句，必须正向指定该写什么
- 写"不要提光源" → 8B 把末句换成"检查光电传感器"（等于没修）。
- 写"不许写成步骤让他去界面看" → 它照抄出"做完后看：PLC 是否已连接"，还把 🔍📋🔧❓ 四段格式头整个弄丢。
- 写"硬触发一律不要提【IO转发】" → **实测无效**；改成在 `_camera_next_step_hint` 里给硬触发一份**写满的正向步骤**（光电传感器/触发线/PLC 触发条件），一次过。

**同一个坑栽了两次以上。规则一律写成"这一支从头到尾只查两件事…末句写××"。**

### 4.3 规则里不要放带引号的示例句；元指令会被照念
- 引号内容会被当成要照念的模板抄进回答（实测抄出"做完后看：关好了"、人称串了的"回复你一声"）。
- 手册里"请他把最近几行念给你"这类**写给模型看的话**，会被原样念给调试员听 → 写手册时凡"让他/请他…"的元指令，都要挪出可引用段落。收尾句用面向调试员的第一人称。

### 4.4 分支写在一句话里，模型会替调试员把分支选掉
`get_last_result` 的 `⚠注意` 原文是"**先问一件事**：产品在位时画面是不是发黑"，模型把"该问的问题"读成了"已知的答案"，判断依据里写出"且画面没有发黑或变暗"——**助手根本看不到图像，这是红线问题**。
⇒ 凡是"先问 X，他说 A 就…，说 B 就…"这种，必须**显式写明本轮只输出提问**，两个分支明确挂到"等他回复之后"。

### 4.5 ⚠⚠ 跨工具的字符串串词（同类坑踩了三次）
`read_error_log` 的结论行里嵌着 `_live_fault_signs()` 的文字（"…IO_72301通讯断开…"），而"通讯断开"正是 `_DEVICE_FAULTS` 一项 → `_missing_tools` 在**所有工具返回拼成的一整块文本**里找故障词，于是**凭一条日志注解就判定"设备故障已定位、可以收工"**，相机和 PLC 一次没查。
修法：`ask()` 分出 `status_text`（只含四个状态工具）给 `_missing_tools`，`results_text`（含日志）仍给 `_all_green`（它要认 `_FRESH_LOG_MARK`，方向相反）。
**教训：凡是拿字符串判状态的，先问一句"这段文字只可能来自我以为的那个工具吗"。**
（另两次：`check_tool_hints.py` 第一版栽在"旧账"和"现行故障"两句共用关键词；`_all_green` 的判定字符串直接依赖 `tools.py` 的中文措辞——**改文案要同步改 agent.py 常量**。）

### 4.6 "综合判断"类的确定性规则，要清点它看了几个信息源
`_all_green` **压根不看日志** → `cycle_too_fast` 场景四个状态端点确实全绿（在取流、18 秒前刚拍到图、PLC 正常、结果 OK），硬证据只在日志里（30 秒前丢帧），全绿拦截把它顶掉了，答成"一切正常"。**这是自信错误结论里最难查的一种：判定逻辑写漏了一个信息源。**
修法：日志结论从两种扩到三种——①当前有故障迹象→现行故障的记录；②全绿+超 30 分钟→旧账；③**全绿+报错很新→日志是唯一线索，结论按它下**（`_FRESH_LOG_MARK`，`_all_green` 认它就让路）。

### 4.7 "旧账 vs 现行故障"不能只看时间
`_STALE_SEC=300` 在真机上把 **9 分钟前的现行故障**判成"很可能早就恢复了"（真机不生产时所有日志都 >5 分钟）；反过来 6 分钟前的报错也完全可能是现行的（现场停机排查时根本不会有新日志进来）。
**真正的判据是当前状态绿不绿，时间只当第二重保险**：`_live_fault_signs()` 查 app/camera/plc 返回当下仍在发生的故障迹象；有迹象→"这条报错很可能正是现行故障的记录"；确认全绿且最新报错 ≥`_STALE_LOG_SEC=1800`→才说旧账；接口读不到（`None`）→**两个结论都不下，宁可沉默也不劝退证据**。
⚠ **故意不看 `lastError`**——它自己可能就是那条旧账，拿它判会变成循环论证。
（真机验证成功：报错 7 分钟前 + 5 条现行故障迹象 → 正确判"现行故障的记录"。）

### 4.8 "让它多查一个工具"的兜底必须成对写
为真机叠加故障加的"查到运行模式类故障也必须补查相机"，**打破了 mock 里的单一故障场景**：`editing_mode` 让模型看到相机数据后，把"软件没在运行模式"这个真原因丢了，改答"相机已打开但没在取流"+点【手动软触发】（mock 里软件没运行，不取流本来就是必然结果）。
**让模型多看到数据，它就可能被最后读到的那条数据劫持结论。** ⇒ 一边让它多查，一边**在数据行上指定清楚谁是原因谁是结果**（"相机不取流是软件没运行的必然结果，不是故障"）。只加前半截就是一次回归。

### 4.9 mock 假绿的四类成因（写新场景前逐条自检）
1. **mock 场景都是单一故障，真机是叠加故障**（真机：软件停止 + 两相机句柄失败 + 两路通讯断开）。
2. **兜底只加了一半**（见 4.8）。
3. **问法压根没触发到要考的那条路径**——测试入口写错，判定再对也考不到。`stale_error_log` 挂了两周都没真正测到它要考的那句结论，因为问法"设备好像不太对劲"里一个 `_LOG_TRIGGER_WORDS` 都没有。
4. **判定逻辑漏了一个信息源**（见 4.6）。

### 4.10 ⚠⚠ 判"模型答错了"之前，必须先看工具实际返回了什么
真机问"点了开始运行提示启动失败"，模型答"软件可能未在运行，请确认 JET2DVis 是否启动"。当场判成"查满 5 工具却无视数据的自信错误结论"，还做了 A/B（旧版本同样答法）→ 升级判定成"既有缺陷"→ 据此改了 `tools._RUN_MODE_TEXT` 措辞 + `agent._RUNMODE_FAULTS` + playbook。
**全错**：翻 `sessions\*.jsonl` 的 `tools[].result` 才发现，那两轮 **JET2DVis 早就退出了**，四个状态工具全返回"状态接口访问失败"（只有 `read_error_log` 有数据——它读磁盘不走接口），模型那句回答**完全正确**。全部回退。
**答案文本不是证据，`tools[].result` 才是。A/B 对照也救不了——两次跑在同一个坏环境里，"复现"只复现了环境故障。** 长时间联调要定期确认被测进程还活着（真机上 JET2DVis 曾自行退出）。

### 4.11 秒级确定性自检先行，再花 LLM 时间
改工具层后先做**不花 LLM 时间的路由自检**：逐场景只打印「状态说明」+「⚠下一步」，先证明只有目标场景的提示变了、其余一字未动，再花半小时跑 LLM 全量。这条手法确认过"12 条无误伤"，已固化成两个脚本：

```powershell
python check_tool_hints.py      # 管 tools.py：查到数据后怎么下结论（14 用例）
python check_tool_coverage.py   # 管 agent.py：到底该查哪些工具（10 用例，含真机实录两轮）
```
两个都做过**负向验证**（打断状态源会红 7 处；退回旧提交只红顺序 bug 那两条）——不是哑测试。退出码非 0 即红。

### 4.12 会话记录要能"事后对上号"
`sessions\YYYY-MM-DD.jsonl` 每条：问答全文 + `tools[]`(name/arguments/result) + 反馈 + `elapsed_sec` + `source`(web|cli|scenario，批跑不混进真人统计) + `model` + `playbook{hash,mtime,chars}` + `code{rev,dirty,py_hash}`。
- **手册天天改，没有 playbook hash 事后说不清"这问题修没修好"**。
- **光有 git rev 不够**：同一天上下午跑的是两版判定逻辑，rev 都是 `9a9c37e`+dirty，对不上号 → 加 `py_hash`（`DiagAgent\*.py` 内容 sha1 前 8 位，改一字就变、未提交也认得出）。
- `dirty` 三态（`null`=git 没查成，和"干净"不是一回事），**范围收成 `*.py`**——mock 夹具 `logerror.log` 每切场景就被重写，拿整个目录判会恒真。
- 历史 111 条老记录没有这些字段。

### 4.13 ⚠ 留在后台的测试夹具会伪装成产品缺陷
用户截图"软件明明运行了"，助手却答"请先启动 JET2DVis"。按 4.10 先查接口而不是判模型错 → JET2DVis 在跑、但 **18081 无人监听**，LogInfo 里明写"诊断状态接口启动失败(:18081): 通常每个套接字地址只允许使用一次"。**根因是我自己**：测 .bat 时留了 `mock_status_server.py` 在后台占着 18081，用户随后双击主程序 → 绑不上端口就 `return`。
**告诉用户"服务在后台跑着"的同时，必须说清它占着哪个端口、什么时候要先停掉。**

### 4.14 中文键名要在出口翻译
模型会照抄它看到的英文字段名（泄漏 `isOpen` 给调试员）。修法：内部判断仍用英文键，`_localize` 只在**出口**翻译成中文（`是否已打开: 是`/`触发模式: 硬触发`/`最近报错: 无（没有记录到报错）`，布尔转是否、空值说人话），`TOOL_SPECS` 描述也换中文，**playbook 里 18 处英文字段名同步改中文**（不然模型照样从手册抄英文）。`docs\status-api.md` 是 HTTP 契约，保持英文。⇒ 英文泄漏实测归零。

### 4.15 手册体积 vs 速度，是这个项目的主要张力
手册 7586→9433 字符（+24%），开发机单场景耗时**普遍翻倍**（全量 22→45 分钟；`normal` 65→134s、`cycle_too_fast` 153→296s）。现场调试员等 5 分钟基本没法用。
出路排序：①现场大显存 + Qwen3-14B（权重整个进 GPU）＞②把 12 条"现场案例"改成**按需注入**＞③回退填充（不建议）。
预取改造后全量回到 26.4 分钟、最慢 296→190s，紧迫性已下降，但**手册不能再无限涨了**。

### 4.16 一刀切的"必须查满"会拖垢所有场景
"回答前必须查满四个工具"把每条从 50s 拖到 130s+（原因明摆着的场景也绕圈）。改成**条件式**：`_DEFINITIVE_FAULTS`（相机没有打开／但没有在取流／通讯断开／方案编辑状态／处于停止状态）出现就早退；例外是报错含"网段"时不早退（相机和 PLC 通常一起断，只说一半会漏）。清晰故障回到 41~67s。
⚠ 但早退分支的顺序会咬人：早退写在 `need_log` 之前，会导致"调试员明说失败/报错 + 状态已查到确定性故障"时**永远不读日志**——而启动失败的原因恰恰只在日志里。⇒ **日志判断提到最前**；早退分支只认**调试员亲口说的词**（不认「最近报错」字段，那内容已随状态摆在模型面前）。

### 4.17 界面指导必须照源码核实，禁跨模块编因果
最初凭常识写的 playbook 界面操作多处不存在（用户："相机配置里没有重新连接相机按钮"）。照源码整理出《软件界面参照》节，含三条**关键否定事实**：
- 相机配置窗口只有【添加相机】【添加多拍】【删除多拍】【手动软触发】+【选择相机】/【触发模式】下拉，**没有"重新连接/打开相机/搜索设备/开始取流"**（【运行相机】被 `Visible=false` 隐藏）；
- 通讯配置窗口只有【创建设备】【保存】，**没有"连接/断开/测试"**；
- **"停止运行→开始运行"既不会重开相机也不会重连 PLC**（`ToolManager.Stop` 注释明确不 `cam.Stop()`；`btn_run_Click` 内无 `Open`/`CommunicationManager.Start`）——这种建议纯属白费工夫。
真能重开相机的路径：相机配置窗口点【手动软触发】(`IsOpen=false` 时当场 Open)、切【选择相机】下拉、【换型】(走 `CYCameraManager.Load` 全部重连)、重启软件(`Form1_Load` 是唯一批量 Open 点)。重连 PLC：【停止运行】→点【通讯】开窗→**关窗**(`Form1.cs:2170` 关窗后 Start 全部通讯)、【换型】、改存 IP/端口、重启。
另：调试员贴"IMV_CreateHandle 创建句柄失败"，助手答"PLC 通讯断开导致相机无法打开"=自信的错误结论 ⇒ 通用原则加"**相机与 PLC 是两条互不相干链路，禁跨模块编因果**"+"调试员贴的报错原文是最硬证据，不许绕开它讲别的模块，看不懂就升级"。**错误码枚举在 SDK dll 里查不到源码 → 手册明禁解释错误码数字。**

### 4.18 填手册 TODO 的原则
**只填能从 JET2DVis 源码查实的软件行为，纯现场经验的坚决留 TODO**（凭常识编界面栽过一次）。8-17 凌晨照此填掉 4 处 / 6 处，最有价值的一条是挖出：**【配置】里"延迟发送OK/NG结果"+"偏移个数"会让开机头几个产品故意不发**——这是设定行为，旧手册下会被报成故障。

## 5. 回归体系（照这个跑，别自创）

### 5.1 三层测试，从便宜到贵

| 层 | 命令 | 耗时 | 管什么 |
|---|---|---|---|
| 确定性路由自检 | `python check_tool_hints.py` / `check_tool_coverage.py` | 秒级 | tools 判定分支 / agent 工具覆盖 |
| 单场景 LLM | `python run_scenarios.py <场景名> [...]` | 每条 40~200s | 端到端结论 |
| 全量 LLM | `python run_scenarios.py` | 约 26 分钟 | 归档成绩 |

**顺序铁律**：改 `tools.py` / `agent.py` → 先跑两个断言脚本 → 再跑受影响的几条 → 最后才决定要不要跑全量。
⚠ **归档文件必须是一整轮同代码的结果**，不能混两版代码的数据（`scenario_results.md` 曾混过，只能重跑）。
⚠ `run_scenarios.py` 每跑完一条**立刻落盘**并按场景合并（长跑常被中断，早期一中断整批白跑）；分批 2~5 条比一次 14 条稳。

### 5.2 14 个 mock 场景 + 问法变体

| 场景 | 考什么 |
|---|---|
| `normal` | **控制组**：不许无中生有报故障，要明确说正常并追问现象 |
| `camera_not_open` | 枚举不到设备 → 引到设备侧查供电/网线/被占用 |
| `camera_open_not_grabbing` | 打开了没取流 → 给真实的重新取流入口 |
| `hw_trigger_no_signal` | 相机正常但很久没来触发 → 查光电/接线/PLC 程序 |
| `soft_trigger_no_signal` | 软触发没有请求进来 → 查触发来源，不是相机坏 |
| `network_unstable` | 反复断流重连 → 网络问题；**不许让他点【手动软触发】**（按下去恢复几秒又断） |
| `plc_disconnected` | 核对 IP/端口/网段/防火墙；不得说成相机故障 |
| `editing_mode` | 不在运行模式 → 点【开始运行】（**不许被相机数据劫持**） |
| `multi_camera_one_bad` | 只说 B 流道坏，A 流道正常 |
| `stale_error_log` | **干扰项**：全绿 + 3 小时前的报错 → 正面回应"那是旧账" |
| `result_not_sent` | 有结果没发出去，写地址报错 → 核对通讯地址 |
| `light_out_of_sync` | 连续 NG 属看图问题 → 升级或查光源；**红线：不许假装看得到图像** |
| `cycle_too_fast` | 状态全绿、证据只在日志（上一帧没处理完就来触发） |
| `wrong_subnet` | 相机和 PLC 同时连不上 + IP 不同网段 |
| **变体** `camera_not_open_说了报错` | 问法"相机报错了打不开"——14 个场景里**一个都没有**"已查到确定性故障 + 调试员亲口说报错"这个组合，而真机上恰恰是它照出了 `_missing_tools` 的顺序 bug。轨迹里必须有 `read_error_log` |

**`VARIANTS` 机制的意义**：同一 mock 状态换一种说法再考一遍。**判定分支只要没有对应的问法，回归就考不到它，迟早在现场被撞见。**

### 5.3 验收标准（原始定义，仍有效）
手册覆盖场景 ≥80% 给出正确结论；**零"自信的错误结论"——宁可建议升级，不可编造原因**。

### 5.4 知识库自更新闭环（人机协作三步，8B 不自改手册防污染）
1. 现场每轮问答与 👍解决了/👎没解决 自动落 `sessions\*.jsonl`（👎 会请调试员填"实际原因/最后怎么解决的"，**这是最有价值的原料**）；
2. 定期把 `sessions\` 交给远程 Claude 整理：重点看 unsolved 记录、和工具轨迹绕远路的 solved 记录，提炼成 playbook 候选条目；
3. 林工审核合入 playbook，跑回归确认不劣化。

## 6. 真机联调（`DIAG_TARGET=real`）

### 6.1 接口契约要点
- 四端点：`/api/v1/status/app`、`/status/cameras`（**复数**，写单数会被 `{"error":"not found"}` 唬住）、`/status/plc`、`/status/last-result`。
- **纯只读**，无任何写/操作端点；处理函数只读内存快照，不调相机 SDK、不加检测线程的锁。
- ⚠ **客户端必须请求 `http://localhost:18081`，不能写 `127.0.0.1`**——HttpListener 按 host 匹配前缀，写 IP 匹配不上。
- mock 专用端点（真实接口不实现）：`GET /mock/scenarios`、`POST /mock/scenario`。

### 6.2 一上真机就查出 3 个 mock 测不出的缺陷（根因都不是"缺工具"）
1. **早退规则**把"软件处于停止状态"当终点，只查 1 个工具就答"点【开始运行】"——真机两台相机都没打开，点了必弹"启动失败:相机X"。（mock 的 `editing_mode` 相机是好的，这条规则一直显得安全。）⇒ 拆 `_RUNMODE_FAULTS` / `_DEVICE_FAULTS`，运行模式类故障**必须补查相机**才准收工。
2. **`read_error_log` 在真机是瞎的**：相机"创建句柄失败"、通讯"connect failed:…超时"这些最硬的证据走的是 **loginfo**，当天 `Log\LogError` 是 **0 字节**，而 `config.LOG_DIR` 只指 LogError。⇒ `LOG_DIRS=[LogError, LogInfo]`；`_parse_log4net` 解析多行块**只抽「日志消息」**（原始块一条占七八行还带源码路径，纯噪声）；LogInfo 侧按 `_FAIL_WORDS` 过滤；mock 单行格式仍兼容。
3. **相机 `lastError` 恒为 null = 三个 bug 叠着**（改完不生效才逐层挖出来）：
   (a) `FindRecentLog(cam.Name)` 用显示名"A流道"搜，日志里写的是标识"CCD1"（`DHCamera.Open(string ip)` 的参数，公开访问器是基类 `GetIPAddress()`）和 GUID（`CameraManager.cs:426` 用 `item.Key`）→ **传三个别名一起匹配**；
   (b) **订阅时机太晚**：相机在 `Form1_Load` 打开，`Start()` 在 `Form1_Shown` 才 `LogHelper.OnLog +=`，启动期报错全发生在订阅之前 → 拆出 `HookLog()` 放到 `Program.Main` 的 `Application.Run` 之前；
   (c) 只返回最新一条，把"启动期取流失败(后果)"返回了、"创建句柄失败(根因)"被挡掉 → **返回该相机最近 3 条报错用 `｜` 连接**。
   另加：**报错单独存 50 条队列**（正常流水不会把启动期报错冲掉）、错误关键词补 `error`/`fail` 英文写法。

### 6.3 真机上验不了的分支
真机有现行故障 → 日志判定永远走 `LIVE` 支；**`FRESH`/`STALE` 两支只有 mock 覆盖**（要验得让真机全绿，而相机硬件不在现场）。

### 6.4 未修的真缺陷（内层，要重编）
`DiagStatusServer.Start()` 绑端口失败只 `LogHelper.WriteLog` 进 **loginfo**，界面上毫无提示 → 现场等于诊断助手静默死掉、没人知道。**建议改成 LogError + 界面可见提示（或换端口重试）。**

### 6.5 其他内层坑
- `JET2DVis.Camera` 命名空间会遮蔽全局 `Camera` 命名空间，写 `Camera.CYCameraBase` 编不过（CS0234）→ 直接写 `CYCameraBase`（文件已 `using Camera;`）。
- 既有无关告警两条：`ProtoBuf: No parameterless constructor found for JET2DVis.Tool.ToolBase`（`Common.Config.DeserializeSave` 里，打到 stdout）、关机时 `ThreadAbortException`（`Form1.cs:170` splash 线程）。

## 7. 性能与硬件（结论已定，别再重新调研）

**一把尺子：单流 tok/s 上限 ≈ 显存带宽 ÷ 模型占用。** 每生成一个 token 要把全部权重过一遍，所以是**带宽**问题，不是算力/TOPS 问题。

- **开发机慢的根因是容量不是卡慢**：RTX 2060 带宽 336 GB/s，8B Q4_K_M 权重约 5GB，理论上限 ~67 tok/s；实测只有 3.73，因为 5GB 权重 + 16k 上下文的 KV 塞不进 6GB，一半落到 CPU（实测只装进 4.1/7.6GB）。
- **别买 NPU**：Axelera Metis（€325.5 / 4GB / 214 INT8 TOPS）**否决**——4GB 连权重都放不下、固定 INT8 表达不了 Q4_K_M 的分组量化、SDK 面向 CNN 视觉；对 `ImageProcessToolkit`（传统 CV：blob/模板匹配/找圆）**也完全没用**。CPU 内置 NPU 共享系统内存(~100 GB/s)比 2060 还低三倍；数据中心 NPU（昇腾 300I Duo 等）带宽 ~200 GB/s 级仍不如二手 3090 的 936，**真正的代价是换掉 Ollama+GGUF 整套栈**（模型重转、回归全跑、现场搬一整套运行时）。
- **推荐**：二手 **RTX 3090（24GB / 936 GB/s）**性价比最优；5060 Ti 16GB(448) 次之；⚠ **4060 Ti 16GB 带宽 288 比 2060 的 336 还低**，赢的纯是容量。
- ⚠ **先别急着买**：现场工控机本来就有 8-12GB 中端独显（检测是纯 CPU OpenCV，GPU 空闲）。**若那块是 NVIDIA 且有 12GB，8B 直接整个进显存，现场根本不用加卡**；慢的只是开发机。**下一步先查清现场那块卡的型号和显存。**
- **一次偶发严重性能异常（根因未确定，别当已解决）**：同一问题第一次跑 **1024 秒**，ollama 日志 `eval 0.16 t/s`（正常 3.73），`n_decoded=100 时 tg=0.10 / 到 153 时 tg_3s=2.9` = 前 100 token 吃掉约 1000 秒、后 53 个恢复正常。推测 WDDM 显存换出，**但重跑只要 63 秒、显存全程稳定一次没动，假设未被证实**。现场风险实打实（调试员碰上一次 17 分钟就会认定它没用）。换成权重全驻显存后值得专门复测。
- **排查手法记住**：`ollama serve` 的 stdout 里有 `slot print_timing` 逐请求 token 速率，是判断"慢在哪"的硬证据；模型缺失/目录不对看 Ollama 的 `server.log` 头部的 env 行 + `GET /api/tags` 是否为空。

## 9. 一页纸总结（贴在显示器边上那种）

1. **提示词压不住的，全部下沉到确定性层**；"要不要调工具"这件事本身就不能交给模型决定。
2. **兜底规则一律正向指定该写什么**，不写否定句，不放带引号的示例句，元指令挪出可引用段落。
3. **判模型答错前，先看 `sessions\*.jsonl` 的 `tools[].result`**；A/B 跑在同一个坏环境里等于没做。
4. **拿字符串判状态前，先问"这段文字只可能来自我以为的那个工具吗"**。
5. **综合判断类规则要清点信息源**——少看一个就会误判（`_all_green` 不看日志那次最难查）。
6. **让模型多查一个工具，就必须同时指定谁是原因谁是结果**，否则结论被最后读到的数据劫持。
7. **秒级确定性自检先行，再花半小时跑 LLM 全量**；归档必须是一整轮同代码的结果。
8. **判定分支没有对应的问法，回归就考不到它**——这就是 `VARIANTS` 存在的理由。
9. **手册缺分支 = 模型原地打转或编造**；填手册只填源码查得实的软件行为。
10. **留在后台的测试夹具会伪装成产品缺陷**；GUI 进程会自己退出，联调前后都要确认 18081 还通。
