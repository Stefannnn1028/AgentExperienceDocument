# HuikeAgent 主干道 + 插件架构 — 项目经验交接

> 生成日期：**2026-08-19**（林工 / fuzhao.lin@nexai-tech.co）
> 代码位置：`HuikeAgent` 仓库，主线在 `HuikeAgentNew/`（.NET 10）。
> 用途：**换台主机 / 隔三个月回来，看懂这套架构为什么长这样、哪些约束有守卫、下一步该做什么。**
> 姊妹文档：[DiagAgent 现场诊断助手](diagagent-field-diagnosis.md)。
> **两个项目都是"LLM + 只读工具层做工业视觉诊断"，但走到了完全不同的深度**，
> 对照关系写在 §3 和 §6 —— 那两节是这份文档最该先读的部分。

---

## 0. 这是什么 / 现在到哪一步

**目标**：把方案搭建、参数调试、工程诊断、插件开发、自动测试建立在**一套人、界面、Agent 共用的结构化契约**上。
一句话原则：*大模型负责理解目标、规划步骤、选择工具和解释证据；确定性软件负责执行和验证；
所有生产修改必须经过权限控制、验证和人工确认。*

与 DiagAgent 的关系：DiagAgent 是**在旧软件外面挂一个只读诊断助手**（Python + Ollama + 5 个工具，
已在真机跑通）；HuikeAgent 是**把整个软件重建成 Agent 可调用的形状**（.NET 10，主干道 + 插件）。
后者的架构强度高一个量级，但**它的诊断能力从来没接过真实模型**——见 §7。

**现状（2026-08-19 实测）**：

| 指标 | 状态 |
|---|---|
| 单元/架构测试 | **264 条全绿**，Windows + WSL2/Ubuntu 22.04.4 / .NET 10.0.400 双平台 |
| Linux 四步回归（构建→测试→无头端到端→界面启动） | 全过，界面在 WSLg 下真起来 |
| 已注册算子 / 已登记错误码 / 状态 scheme | 6 / 39 / 3 类 |
| 工具面动词 | 7 个，**封闭集合**（加动词要先写 ADR） |
| 内核契约版本 | `KernelContract.Version = 4` |
| 插件可扩展维度 | 8 个 |
| 100 节点方案规模 | 编译 4.3 ms / 执行 1.9 ms / 画布建模 9.0 ms（无头，不含 GPU 光栅化） |
| **真实 `IModelClient` 实现** | **0 个**。只有 `ScriptedModelClient`（按固定顺序调工具的离线脚本） |
| **诊断场景数** | **1 个**（Phase 1 验收要求 ≥10） |
| **Agent 结论的自动评分** | **不存在**，一行都没有 |

⚠ 最后三行是这个项目当前最大的实质缺口：**架构建好了、守严了，但"Agent 能诊断"这个核心主张
一次都没被真实模型验证过。** DiagAgent 在这件事上反而是走通了的（15/15 场景零自信错误结论），
所以 §6 是一份**从 DiagAgent 往 HuikeAgent 搬**的清单。

代码状态：38 个提交已全部快进合进 `main` 并推送，工作区干净。**不走 PR**（单人仓库，PR 只是多一道手续）。

## 1. 架构地图

```
主干道 src/                        插件 plugins/            生态 src/
┌─────────────────────┐          ┌──────────────┐        ┌──────────────────┐
│ Huike.Ui   Avalonia │          │ Vision2D     │        │ Huike.Sdk.Testing│
│ Huike.Host 组装根   │·运行期加载→│ Devices 仿真 │        │ Huike.Mcp        │
│ Huike.Kernel        │          │ Diagnostics  │        └──────────────────┘
└─────────┬───────────┘          └──────┬───────┘                 │
          └──────────────┬──────────────┴─────────────────────────┘
                    Huike.Sdk（契约层 · 零工程引用 · 零第三方包）
```

**被测试守着的三条边界**（不是约定，是会变红的断言）：

| 约束 | 守卫 | 为什么 |
|---|---|---|
| `Huike.Sdk` 不引用任何工程、任何第三方包 | 按引用表断言 | 第三方要能只拿一个程序集编出插件 |
| `Huike.Sdk.Testing` 同样只引用 Sdk，且不绑测试框架 | `ConformanceSuiteOnlyDependsOnTheSdk` | 绑了 xunit 等于替第三方选了测试框架 |
| 内核不认识领域概念 | `KernelDoesNotKnowAnyDomainConcept` **+** 提示词无领域词那条 | 换厂商不动主干道。**两层守卫，理由见 4.3** |

**两条运行时链路**，只有两个受控接触点：

- **链 A 产线执行**：`IFrameSource`(pull) → `PipelineRunner`(async DAG) → `ExecutionTrace` → `ITraceSink`。
  **完全不依赖 `IModelClient`**——没有模型、Diagnostics 插件没装，检测照跑。
- **链 B Agent 诊断**：`DiagnosticTask` → `AgentHarness` → `ToolRegistry` → `PermissionGate` → `ITool`
  → `CriteriaVerifier` → Episode。
- 链 B 想影响链 A 只能经 `trace.query`（读同一个 traceId）和 `run.sample`（沙箱回放）。
  **内核动词表里没有"应用提案"**——应用是人的动作，走 `ISolutionStore` 而不是工具面。

`docs/architecture.md` 有三张 mermaid 图（依赖 / 装配时序 / 运行时调用链），
另有一份可交互的架构全景 HTML（`docs/architecture-diagram.html`，同时发布成 Artifact）。
**架构图的数字一律来自 `scripts/linux-check.sh` 的实测输出**，不手填。

## 3. 心法：和 DiagAgent 同一条主张，两种强度

DiagAgent 那份文档的核心是一句：**"8B 小模型上，提示词压不住的事，全部下沉到确定性层用代码写死。"**
HuikeAgent 是**同一条主张的架构级版本**——不是"写几条兜底规则"，而是把确定性层做成**类型系统和守卫**：

| DiagAgent 的做法 | HuikeAgent 的对应物 | 强度差在哪 |
|---|---|---|
| `agent.py` 里代码直接预取缺失的工具 | `AgentHarness` 四条硬停机条件 + 按生效风险上限过滤工具清单 | 前者是"补一手"，后者是"模型看不到不该看的工具" |
| `_all_green()` 出口拦截，带 🔍 就顶回去重答 | `CriteriaVerifier` + `IVerificationRule`：**验证规则拿不到 `Transcript`** | 后者是**类型级**保证："模型说了什么"不可能影响判定 |
| `tools.py` 的"⚠下一步"贴在数据旁边 | `ErrorCatalog`：39 个错误码带「常见原因 / 下一步」，经 `catalog.query` 给模型查 | 后者不进提示词，**按需查**，不占上下文也不会 lost-in-the-middle |
| playbook 里写"不许改在线参数" | `PermissionGate` + `ToolRisk.ProductionWrite` + `HumanApproved` | 后者是执行点，不是叮嘱 |
| 手册整体进 system prompt（9433 字符，涨 24% 耗时翻倍） | 提示词分段（`AddPromptSection`），内核只留不变量，领域由插件贡献 | 后者可按插件裁剪，且**领域词有守卫盯着不许回流内核** |

**结论：DiagAgent 用规则治模型，HuikeAgent 用类型和守卫治模型。** 后者贵得多，
但它换来的是"新入口想漏掉核对权限连编译都过不去"这种性质。

⚠ **但强度不等于已验证。** HuikeAgent 的确定性层全绿（264 条），
而**模型那一侧一次都没跑过**；DiagAgent 反过来——规则层弱，但端到端成绩是真的。
两份文档合起来才是完整的：**架构强度看这份，模型行为怎么调看那份。**

## 4. 硬经验清单（本项目独有，可引用编号）

### 4.1 ⚠⚠ 限制性断言必须实测，否则一句错话会污染整条推理链

**这是本项目最贵的一条经验。**

2026-08-19 之前，"`ScottPlot.Avalonia` 与 `NodifyAvalonia` 无法共存，所以图表页做不了"被写进 ADR、
roadmap 和架构图，并在多轮对话里当既定事实复述。实测（建一个探针工程摆进候选版本组合跑一次
`dotnet restore`，成本一分钟量级）后发现：**只是最新版冲突，退一个小版本三者即可共存。**

**代价不止是一句错话**：它成了"换节点编辑器有额外代价"这一判断的**依据之一**。
错误的事实污染了后续推理，而推理结果看起来完全合理。

由此定下三条规矩（已写进项目的 Agent 指令文件，对所有协作 Agent 生效）：

1. **依赖冲突类断言必须实测**，不能靠读包元数据推断。
   包元数据只回答"最新版要求什么"，**不回答"有没有能共存的旧版本"**——两者不是一回事。
2. **验证不了就带限定词。** 写"最新版 5.1.59 与 6.6.0 冲突，旧版本未验证"，不要写"两者无法共存"。
   **限定词本身就是下次的钩子**，它标出了没查的那一块。
3. **注明来源是实测还是推断。** 架构图页脚早就对**数字**这么做了（"数字来源：`linux-check.sh` 实测输出"）；
   限制性断言享受同样待遇——**它们比数字更能左右决策**。

> 同族经验：DiagAgent [§7 那条 1024 秒性能异常](diagagent-field-diagnosis.md#7-性能与硬件结论已定别再重新调研)
> ——"推测 WDDM 显存换出，但重跑只要 63 秒，**假设未被证实**"。那条做对了（明确标了未证实），
> 这条做错了（当成事实用了）。**区别只在有没有写限定词。**

### 4.2 同一系统里两条链路对同一件事用了两种建模，其中一种更差 → 照搬好的那条

链 A 从一开始就把一次执行沉淀成结构化事实（`NodeExecution` → `ExecutionTrace` → `ITraceSink`，
逐条产出、逐条落）；链 B 对应位置上只有 `EpisodeState.Transcript` 这个可变 `List<ChatMessage>`，
整个 Episode 等循环**结束后**才一次性落盘。

这不是"链 B 功能少"，是**同一个问题的两个答案，而其中一个明显更差**。四个后果同源：

1. **崩在中途什么都不剩**——而那个类的注释写的是"事后任何人都能重放"。**恰恰是崩掉的那次最需要重放。**
2. **没有上下文预算**（停机条件只有调用数、时间、重复调用），撞上供应商硬限后失败被宽 `catch`
   归成"模型出错"，与"服务不可用"无法区分——一个要裁上下文，一个要看网络。
3. **无进展签名不含结果**，于是"隔一会儿再读一次 `camera://cam-1` 看设备起没起来"这种正当取证
   第三次被判无进展。
4. **停止原因是字符串字面量**，且内部用 `!= "completed"` 做分支——那条分支决定要不要升级人工，
   写错一个字母不报错，**只静默改变行为**。

修法不是加功能，是换建模：把链 A 的那一套搬过来。
**判据：一个系统里凡有两条并行链路，去问"同一件事它们是不是用同一种方式建模的"，不一样就有一条是错的。**

### 4.3 ⚠ 守卫的绿色可能暗示一个比事实更强的结论

架构守卫 `KernelDoesNotKnowAnyDomainConcept` 断言的是「不装插件时算子目录与工具表为空、
只剩 `runtime://`」——**查的是注册表有没有被污染，不扫描源码文本**。
而 `AgentHarness.BuildSystemPrompt` 里写死了"你是工业视觉系统的诊断助手"——
一段落在内核里的领域知识，守卫一个字也管不着。

于是出现了比"少一个功能"更麻烦的情况：**这条约束一直是绿的，而绿色让人以为它覆盖了全部。**

**这条缺口自己还栽过一次同类的亏**：它在 roadmap 里原本被描述成"守卫按 camera/plc/halcon
那张禁词表判定，这段提示词不在表上"——**而那张禁词表根本不存在**。
断言没错，错的是**对它覆盖范围的描述**；而错的描述会让下一个人去改一张不存在的表。

⇒ 两条做法：
- 把领域那句话移进插件（`AddPromptSection`，第 8 个维度，契约 3 → 4），
  新加一条测试**直接对着生成出来的 system prompt** 断言里面没有领域词——那一层从此也有守卫。
- **写下"某条约束由某个守卫保证"时，顺手写清那个守卫到底查什么。** 覆盖范围的描述和断言本身一样重要。

> 同族：DiagAgent [§4.6 综合判断类规则要清点信息源](diagagent-field-diagnosis.md#46-综合判断类的确定性规则要清点它看了几个信息源)
> ——`_all_green` 漏看日志那次。同一族的两个面：那条是**判定漏了信息源**，这条是**守卫的覆盖范围被误述**。

### 4.4 "增量持久化"不能靠"跑完检查文件存在"来证明

跑完当然存在。要证明的是**运行途中就已经在盘上**。

做法：写一个测试用的工具，让它在**被调用的那一刻**去数事件日志的行数；
断言第二次被调用时看到的行数比第一次多——说明第一次调用的记录在第二次调用之前就落盘了。
原来的实现在这里只能数到 0。

**这类"时机"性质的断言，都要找一个能在时机内部观察的切入点**，否则测试写出来是绿的，性质根本没被验证。

配套两个决定：
- **"进内存"和"写盘"合成一个方法**（`EpisodeLog.AppendAsync`）。分成两步迟早有一处忘了写盘，
  而那一处就把这条性质抹掉了。
- 每次追加**开关一次文件**，写完即落盘，不依赖进程正常退出时的 flush。40 次调用量级，开销无所谓。

### 4.5 上下文预算必须判在**调用模型之前**

判在之后等于让供应商的硬限来告诉你，而那条路径上的失败与"服务不可用"混在一起。

长度只能**估**：`IModelClient` 是刻意做成最小面的，里面没有 tokenizer 也不该有——
每接一家供应商就多一套分词器，"模型无关"那条边界就破了。

⚠ **中文必须按 1 token/字符估。** 按常见的"4 字符 1 token"估中文会**低估四倍**，
而这个项目的提示词、算子名、报错全是中文——低估等于预算形同虚设。有测试盯这条。

**估算不是计数**，所以预算要定得比供应商硬限低一截。宁可早停一轮，
也不要撞上硬限之后连"为什么停的"都说不清。

配套：工具结果超长时**只在交给模型的那份投影上截断并注明**，事件日志里始终是全量记录——
**该省的是模型的上下文，不是审计的完整性**。静默截断更糟：模型会把"数组只有 3 项"当成事实来推理。

### 4.6 无进展判定的签名要带上结果，并写明它的失效场景

`工具名|入参` 不够——"问了同样的问题、得到同样的答案"才叫没进展。加上结果哈希。

- 哈希用 FNV-1a，**不用 `string.GetHashCode`**：后者每进程加随机种子，而签名要能跨进程比较。
- **代价必须写明**：这条判定从此依赖结果可比较。工具返回里带时间戳之类每次都变的字段时，
  签名永不重复，判定对它失效。⇒ 另加一条**只看入参的高阈值计数**兜底，再兜底是调用数与时间上限。

**"加了一条更聪明的判据"就要问一句"它在什么情况下会失效"，并且把兜底一起写。**

### 4.7 fail 的方向必须同向：忘了填就掉到最小权限

权限有两条路径（Agent 调工具 / 人工审批），共用同一套角色词表，**默认值却相反**：
人工侧默认 `operator`（只能看），工具侧默认 `engineer`（四档里第二高）。
于是"忘了填角色"这件事，一侧变成"看不了"，另一侧变成"能写生产"。

当时没有后果（没有任何工具声明 `RequiredRoles`），**但第一个生产写工具落地那天它就是一次静默提权**。

⇒ 两侧都改成最小权限，并且**判据不写成"两侧默认值相等"，而写成"两侧都不能写生产"**——
方向一致才是要守的东西，值相等只是当下的巧合。

### 4.8 两根独立的轴之间要有约束，否则"可选的声明"就是洞

`MaxRisk` 是**任务**属性、角色是**人**属性，两者独立设定、中间没有约束
→ 一个 `viewer` 可以发起沙箱写任务，只要那个工具没声明 `RequiredRoles` 就一路放行。
**而声明是可选的：内核 7 个工具一个都没声明。** 所以这不是边角情形，是默认情形。

⇒ 加一张"角色 → 允许发起的最高风险"的表，生效上限取两轴较小者。三条落地要点：

1. **两个执行点，缺一不可**：门禁按它**拒绝**，Harness 按它**过滤交给模型的工具清单**。
   只做前者——模型看得见就会去调，每次挨拒都在花停机预算。
2. **门禁里两条规则分开写**，不要只判"生效上限"：拒绝理由要指认**哪根轴**挡的。
   任务定得低就改任务约束，角色不够就得换人来做——**现场处置完全不同**。
   合成一条会得到"风险超限"这种既对又没用的信息。
3. **超限时拒绝，不悄悄收窄。** 收窄之后任务会在完成条件那里失败，表现为"为什么没有提案"，
   而真实原因是权限。**故障点离原因越远越难指认。**

### 4.9 只建了"拒绝"的一半，等于把故障点挪到更难指认的地方

方案文件有 `schemaVersion`，但两处判据不一致：编译器用 `!=`（拒绝一切不等），
存储用 `>`（只拒绝更高版本），全仓库没有任何迁移代码。

后果很具体：**旧版本方案读得进来，但编译不过。** 用户看到的是列表里有它、双击能打开、
一按运行报一个 schema 错——比直接打不开难指认得多。而版本号从 1 变成 2 的那天，
现场所有旧方案一次性全部打不开。

⇒ 政策五条（与内核契约那套同形）：读旧写新 / 不猜新版本 / 一步一版不做跨版直达 /
**迁移只在唯一那道门里发生**（于是编译器那条严格相等语义从"版本策略"改成**断言**）/
放弃支持旧版本要明说是哪个版本还认得它。

**错误码要分清"该谁动手"**：文件比程序新（用户升级软件）、文件太旧（用户用旧软件另存）、
**声明支持却没有迁移步骤（开发：这是程序缺陷）**——第三种混用前两种的码，会把人引向改文件，
而该改的是程序。

### 4.10 机制先于需要而建时，用"可注入的表"让它今天就被执行

上面那套迁移，**真表今天是空的**（版本号还是 1，没有可迁的东西）。
如果只有一个无参入口，这套机制会在**第一次真正需要它的时候**才第一次被执行——
那正是最不适合发现问题的时刻（现场已经躺着一批旧文件）。

⇒ 给它加一个**可注入版本号与步骤表的重载**，测试用假步骤走通 1 → 2 → 3。
于是"逐版串联、顺序正确、缺步骤会报错"这三件事今天就是绿的。

**选在成本最低的时刻定政策**：此刻是一个空列表 + 一条守卫测试；
等到两个版本并存，补迁移要在"有真实数据要救"的压力下做。

### 4.11 "给模型看的文字"和"给人看的文字"是两套，别绑在一起

界面文案走 i18n（`UiText` 词条 + 插件的 `AddStrings`，覆盖率有测试守着）；
**系统提示词刻意不走 i18n**。

理由不是省事：模型的工作语言与界面语言是**两个独立决定**——英文界面配中文提示词是完全正常的组合。
硬绑在一起会导致切一次界面语言就换一套提示词，**模型行为随界面语言漂移**，
而那种漂移在测试里几乎看不见。

> 互补：DiagAgent [§4.14 中文键名要在出口翻译](diagagent-field-diagnosis.md#414-中文键名要在出口翻译)
> 讲的是**给人看的那一侧**（模型会照抄它看到的英文字段名，泄漏 `isOpen` 给调试员）。
> 两条合起来：**内部判断用稳定标识，出口按受众分别处理——人要翻译，模型不要跟着界面走。**

### 4.12 裸字符串收敛成登记值，判据是"写错一个字母会怎样"

项目里有一条硬规矩：错误码一律用 `ErrorCodes` 里登记的常量，禁止在调用点写裸字符串。
但守卫只盯错误码，**没盯别的**——于是停止原因（`"completed"` / `"timeout"` / `"no-progress"`）
散在六处赋值，还有一处用 `!= "completed"` 做分支。

**判据不是"字符串多不多"，是"写错一个字母会不会报错"。** 会静默改变行为的就得收敛。
角色名同理（门禁靠字符串相等判断，把 `enginer` 当成有效角色 = 一次静默提权），
所以角色也有登记表，且**不认识的角色一律丢弃**——拼写错误应当收紧权限，不该放宽。

### 4.13 跨 Agent 协作的仓库，共享规则要有单一来源 + 一致性自检

这个仓库同时被 Codex 和 Claude Code 改。做法：共享规则只在 `docs/agents/project.md` 维护，
`AGENTS.md` 只放 Codex 特有的、`CLAUDE.md` 只放 Claude 特有的，
再用 `scripts/check-agent-instructions.ps1` 核对入口是否一致（新增/移动专题文档时必须同步）。

**"限制性断言要实测"那三条规矩就写在这个共享文件里**——经验只有进了 Agent 每次都会读的地方，
才真的会被下一轮遵守。写在别处等于没写。

### 5.1 三层，从便宜到贵（**第三层还不存在**）

### 5.2 已有的几条判据值得单独点出来

- **架构守卫是引用表级的**，不是靠评审：Sdk 的依赖、Sdk.Testing 的依赖、注册表是否被污染、
  提示词里有没有领域词，全是测试。
- **一致性套件一份代码三个出口**：插件作者本地 `dotnet test` 跑它、他的 AI 助手经 MCP 跑它、
  现场"注册插件"按钮也跑它——否则"我这儿是绿的"会变成常态争议。
- **真第三方插件夹具带真原生 DLL**：手法是**不自己编原生库**，
  拿 .NET 运行时自带的压缩库改名拷进包目录——CI 不用装 C 工具链，加载的又是真原生代码，
  且改名后系统搜索路径上不存在，**能解析到就只可能来自包目录**。
  ⚠ 负例必须换一个**不同的库名**：原生库按名字加载后进程内全局复用，
  同进程里前一个用例装上的那份会顶替，负例会假绿。
- **无头 UI 测试**：控件必须在调度线程上构造，否则单跑绿、全跑红。

## 8. 一页纸总结

1. **限制性断言（"X 做不了"、"A 与 B 无法共存"）必须实测，验证不了就带限定词。**
   一句未实测的断言会成为后续判断的依据，错误的事实污染看起来完全合理的推理。
2. **一个系统里两条并行链路，去问"同一件事它们是不是同一种建模"**——不一样就有一条是错的。
3. **写下"某约束由某守卫保证"时，顺手写清那个守卫到底查什么。** 绿色会暗示比事实更强的结论。
4. **"时机"性质的断言要找能在时机内部观察的切入点**；"跑完检查文件存在"证明不了增量落盘。
5. **上下文预算判在调用模型之前**，否则超限与服务不可用无法区分；**中文按 1 token/字符估**。
6. **加了更聪明的判据，就要写明它什么时候失效，并把兜底一起写。**
7. **fail 的方向必须同向**：忘了填就掉到最小权限；判据写成"两侧都不能写生产"，不是"两侧相等"。
8. **两根独立的轴之间要有约束**，否则"可选的声明"就是洞；拒绝理由要指认是哪根轴挡的。
9. **只建"拒绝"的一半，等于把故障点挪到更难指认的地方**（读得进来但编译不过）。
10. **机制先于需要而建时，用可注入的表让它今天就被执行**；选成本最低的时刻定政策。
11. **给人看的文字要翻译，给模型看的文字不要跟着界面语言走。**
12. **裸字符串收敛的判据是"写错一个字母会不会报错"**，不是"字符串多不多"。
13. **经验要写进 Agent 每次都会读的那个文件**，否则等于没写。
