# HuikeAgent 主干道 + 插件架构 — 项目经验交接

> 生成日期：**2026-08-19**（林工 / fuzhao.lin@nexai-tech.co）
> 代码位置：`HuikeAgent` 仓库，主线在 `HuikeAgentNew/`（.NET 10）。
> 用途：**换台主机 / 隔三个月回来，看懂这套架构为什么长这样、哪些约束有守卫、下一步该做什么。**
> 姊妹文档：[DiagAgent 现场诊断助手](diagagent-field-diagnosis.md)。
> **两个项目都是"LLM + 只读工具层做工业视觉诊断"，但走到了完全不同的深度**，

## 0. 这是什么 / 现在到哪一步

**目标**：把方案搭建、参数调试、工程诊断、插件开发、自动测试建立在**一套人、界面、Agent 共用的结构化契约**上。
一句话原则：*大模型负责理解目标、规划步骤、选择工具和解释证据；确定性软件负责执行和验证；
所有生产修改必须经过权限控制、验证和人工确认。*

与 DiagAgent 的关系：DiagAgent 是**在旧软件外面挂一个只读诊断助手**（Python + Ollama + 5 个工具，
已在真机跑通）；HuikeAgent 是**把整个软件重建成 Agent 可调用的形状**（.NET 10，主干道 + 插件）。
后者的架构强度高一个量级，但**它的诊断能力从来没接过真实模型**——见 §7。

## 1. 架构地图

```
主干道 src/                        插件 plugins/            生态 src/
┌─────────────────────┐          ┌──────────────┐        ┌──────────────────┐
│ Huike.Ui   Avalonia │          │ Vision2D     │        │ Huike.Sdk.Testing│
│ Huike.Host 组装根   │·运行期加载→│ Devices 仿真 │        │ Huike.Mcp        │
│ Huike.Kernel        │          │ Diagnostics  │        └──────────────────┘
│                     │          │ Comm.Tcp     │                 │
│                     │          │ DataIo       │                 │
└─────────┬───────────┘          └──────┬───────┘                 │
          └──────────────┬──────────────┴─────────────────────────┘
                    Huike.Sdk（契约层 · 零工程引用 · 零第三方包）
```

**被测试守着的三条边界**（不是约定，是会变红的断言）：

| 约束 | 守卫 | 为什么 |
|---|---|---|
| `Huike.Sdk` 不引用任何工程、任何第三方包 | 按引用表断言 | 第三方要能只拿一个程序集编出插件 |
| `Huike.Sdk.Testing` 同样只引用 Sdk，且不绑测试框架 | `ConformanceSuiteOnlyDependsOnTheSdk` | 绑了 xunit 等于替第三方选了测试框架 |
| 内核不认识领域概念 | `KernelDoesNotKnowAnyDomainConcept` **+** 提示词无领域词那条 | 换厂商不动主干道。**两层守卫，理由见 4.3** |

**两条运行时链路**，只有两个受控接触点：

- **链 A 产线执行**：`IFrameSource`(pull) → `PipelineRunner`(async DAG) → `ExecutionTrace` → `ITraceSink`。
  **完全不依赖 `IModelClient`**——没有模型、Diagnostics 插件没装，检测照跑。
- **链 B Agent 诊断**：`DiagnosticTask` → `AgentHarness` → `ToolRegistry` → `PermissionGate` → `ITool`
  → `CriteriaVerifier` → Episode。
- 链 B 想影响链 A 只能经 `trace.query`（读同一个 traceId）和 `run.sample`（沙箱回放）。
  **内核动词表里没有"应用提案"**——应用是人的动作，走 `ISolutionStore` 而不是工具面。

`docs/architecture.md` 有三张 mermaid 图（依赖 / 装配时序 / 运行时调用链），
另有一份可交互的架构全景 HTML（`docs/architecture-diagram.html`，同时发布成 Artifact）。
**架构图的数字一律来自 `scripts/linux-check.sh` 的实测输出**，不手填。

## 3. 心法：和 DiagAgent 同一条主张，两种强度

DiagAgent 那份文档的核心是一句：**"8B 小模型上，提示词压不住的事，全部下沉到确定性层用代码写死。"**
HuikeAgent 是**同一条主张的架构级版本**——不是"写几条兜底规则"，而是把确定性层做成**类型系统和守卫**：

| DiagAgent 的做法 | HuikeAgent 的对应物 | 强度差在哪 |
|---|---|---|
| `agent.py` 里代码直接预取缺失的工具 | `AgentHarness` 四条硬停机条件 + 按生效风险上限过滤工具清单 | 前者是"补一手"，后者是"模型看不到不该看的工具" |
| `_all_green()` 出口拦截，带 🔍 就顶回去重答 | `CriteriaVerifier` + `IVerificationRule`：**验证规则拿不到 `Transcript`** | 后者是**类型级**保证："模型说了什么"不可能影响判定 |
| `tools.py` 的"⚠下一步"贴在数据旁边 | `ErrorCatalog`：39 个错误码带「常见原因 / 下一步」，经 `catalog.query` 给模型查 | 后者不进提示词，**按需查**，不占上下文也不会 lost-in-the-middle |
| playbook 里写"不许改在线参数" | `PermissionGate` + `ToolRisk.ProductionWrite` + `HumanApproved` | 后者是执行点，不是叮嘱 |
| 手册整体进 system prompt（9433 字符，涨 24% 耗时翻倍） | 提示词分段（`AddPromptSection`），内核只留不变量，领域由插件贡献 | 后者可按插件裁剪，且**领域词有守卫盯着不许回流内核** |

**结论：DiagAgent 用规则治模型，HuikeAgent 用类型和守卫治模型。** 后者贵得多，
但它换来的是"新入口想漏掉核对权限连编译都过不去"这种性质。

⚠ **但强度不等于已验证。** HuikeAgent 的确定性层全绿（264 条），
而**模型那一侧一次都没跑过**；DiagAgent 反过来——规则层弱，但端到端成绩是真的。
两份文档合起来才是完整的：**架构强度看这份，模型行为怎么调看那份。**

## 4. 硬经验清单（本项目独有，可引用编号）

### 4.1 ⚠⚠ 限制性断言必须实测，否则一句错话会污染整条推理链

**这是本项目最贵的一条经验。**

2026-08-19 之前，"`ScottPlot.Avalonia` 与 `NodifyAvalonia` 无法共存，所以图表页做不了"被写进 ADR、
roadmap 和架构图，并在多轮对话里当既定事实复述。实测（建一个探针工程摆进候选版本组合跑一次
`dotnet restore`，成本一分钟量级）后发现：**只是最新版冲突，退一个小版本三者即可共存。**

**代价不止是一句错话**：它成了"换节点编辑器有额外代价"这一判断的**依据之一**。
错误的事实污染了后续推理，而推理结果看起来完全合理。

由此定下三条规矩（已写进项目的 Agent 指令文件，对所有协作 Agent 生效）：

1. **依赖冲突类断言必须实测**，不能靠读包元数据推断。
   包元数据只回答"最新版要求什么"，**不回答"有没有能共存的旧版本"**——两者不是一回事。
2. **验证不了就带限定词。** 写"最新版 5.1.59 与 6.6.0 冲突，旧版本未验证"，不要写"两者无法共存"。
   **限定词本身就是下次的钩子**，它标出了没查的那一块。
3. **注明来源是实测还是推断。** 架构图页脚早就对**数字**这么做了（"数字来源：`linux-check.sh` 实测输出"）；
   限制性断言享受同样待遇——**它们比数字更能左右决策**。

> 同族经验：DiagAgent [§7 那条 1024 秒性能异常](diagagent-field-diagnosis.md#7-性能与硬件结论已定别再重新调研)
> ——"推测 WDDM 显存换出，但重跑只要 63 秒，**假设未被证实**"。那条做对了（明确标了未证实），
> 这条做错了（当成事实用了）。**区别只在有没有写限定词。**

### 4.2 同一系统里两条链路对同一件事用了两种建模，其中一种更差 → 照搬好的那条

链 A 从一开始就把一次执行沉淀成结构化事实（`NodeExecution` → `ExecutionTrace` → `ITraceSink`，
逐条产出、逐条落）；链 B 对应位置上只有 `EpisodeState.Transcript` 这个可变 `List<ChatMessage>`，
整个 Episode 等循环**结束后**才一次性落盘。

这不是"链 B 功能少"，是**同一个问题的两个答案，而其中一个明显更差**。四个后果同源：

1. **崩在中途什么都不剩**——而那个类的注释写的是"事后任何人都能重放"。**恰恰是崩掉的那次最需要重放。**
2. **没有上下文预算**（停机条件只有调用数、时间、重复调用），撞上供应商硬限后失败被宽 `catch`
   归成"模型出错"，与"服务不可用"无法区分——一个要裁上下文，一个要看网络。
3. **无进展签名不含结果**，于是"隔一会儿再读一次 `camera://cam-1` 看设备起没起来"这种正当取证
   第三次被判无进展。
4. **停止原因是字符串字面量**，且内部用 `!= "completed"` 做分支——那条分支决定要不要升级人工，
   写错一个字母不报错，**只静默改变行为**。

修法不是加功能，是换建模：把链 A 的那一套搬过来。
**判据：一个系统里凡有两条并行链路，去问"同一件事它们是不是用同一种方式建模的"，不一样就有一条是错的。**

### 4.3 ⚠ 守卫的绿色可能暗示一个比事实更强的结论

架构守卫 `KernelDoesNotKnowAnyDomainConcept` 断言的是「不装插件时算子目录与工具表为空、
只剩 `runtime://`」——**查的是注册表有没有被污染，不扫描源码文本**。
而 `AgentHarness.BuildSystemPrompt` 里写死了"你是工业视觉系统的诊断助手"——
一段落在内核里的领域知识，守卫一个字也管不着。

于是出现了比"少一个功能"更麻烦的情况：**这条约束一直是绿的，而绿色让人以为它覆盖了全部。**

**这条缺口自己还栽过一次同类的亏**：它在 roadmap 里原本被描述成"守卫按 camera/plc/halcon
那张禁词表判定，这段提示词不在表上"——**而那张禁词表根本不存在**。
断言没错，错的是**对它覆盖范围的描述**；而错的描述会让下一个人去改一张不存在的表。

⇒ 两条做法：
- 把领域那句话移进插件（`AddPromptSection`，第 8 个维度，契约 3 → 4），
  新加一条测试**直接对着生成出来的 system prompt** 断言里面没有领域词——那一层从此也有守卫。
- **写下"某条约束由某个守卫保证"时，顺手写清那个守卫到底查什么。** 覆盖范围的描述和断言本身一样重要。

> 同族：DiagAgent [§4.6 综合判断类规则要清点信息源](diagagent-field-diagnosis.md#46-综合判断类的确定性规则要清点它看了几个信息源)
> ——`_all_green` 漏看日志那次。同一族的两个面：那条是**判定漏了信息源**，这条是**守卫的覆盖范围被误述**。

### 4.4 "增量持久化"不能靠"跑完检查文件存在"来证明

跑完当然存在。要证明的是**运行途中就已经在盘上**。

做法：写一个测试用的工具，让它在**被调用的那一刻**去数事件日志的行数；
断言第二次被调用时看到的行数比第一次多——说明第一次调用的记录在第二次调用之前就落盘了。
原来的实现在这里只能数到 0。

**这类"时机"性质的断言，都要找一个能在时机内部观察的切入点**，否则测试写出来是绿的，性质根本没被验证。

配套两个决定：
- **"进内存"和"写盘"合成一个方法**（`EpisodeLog.AppendAsync`）。分成两步迟早有一处忘了写盘，
  而那一处就把这条性质抹掉了。
- 每次追加**开关一次文件**，写完即落盘，不依赖进程正常退出时的 flush。40 次调用量级，开销无所谓。

### 4.5 上下文预算必须判在**调用模型之前**

判在之后等于让供应商的硬限来告诉你，而那条路径上的失败与"服务不可用"混在一起。

长度只能**估**：`IModelClient` 是刻意做成最小面的，里面没有 tokenizer 也不该有——
每接一家供应商就多一套分词器，"模型无关"那条边界就破了。

⚠ **中文必须按 1 token/字符估。** 按常见的"4 字符 1 token"估中文会**低估四倍**，
而这个项目的提示词、算子名、报错全是中文——低估等于预算形同虚设。有测试盯这条。

**估算不是计数**，所以预算要定得比供应商硬限低一截。宁可早停一轮，
也不要撞上硬限之后连"为什么停的"都说不清。

配套：工具结果超长时**只在交给模型的那份投影上截断并注明**，事件日志里始终是全量记录——
**该省的是模型的上下文，不是审计的完整性**。静默截断更糟：模型会把"数组只有 3 项"当成事实来推理。

### 4.6 无进展判定的签名要带上结果，并写明它的失效场景

`工具名|入参` 不够——"问了同样的问题、得到同样的答案"才叫没进展。加上结果哈希。

- 哈希用 FNV-1a，**不用 `string.GetHashCode`**：后者每进程加随机种子，而签名要能跨进程比较。
- **代价必须写明**：这条判定从此依赖结果可比较。工具返回里带时间戳之类每次都变的字段时，
  签名永不重复，判定对它失效。⇒ 另加一条**只看入参的高阈值计数**兜底，再兜底是调用数与时间上限。

**"加了一条更聪明的判据"就要问一句"它在什么情况下会失效"，并且把兜底一起写。**

> 2026-08-25 补：这条判据还有一个**盲区**——它按工具调用计数，
> 所以对"模型说要查却一个工具都不发"的空转完全无感。那是无进展的第二种形状，
> 见 [4.28](#428--无进展有两种形状工具计数器数不到说要查却不发调用的空转)。

### 4.7 fail 的方向必须同向：忘了填就掉到最小权限

权限有两条路径（Agent 调工具 / 人工审批），共用同一套角色词表，**默认值却相反**：
人工侧默认 `operator`（只能看），工具侧默认 `engineer`（四档里第二高）。
于是"忘了填角色"这件事，一侧变成"看不了"，另一侧变成"能写生产"。

当时没有后果（没有任何工具声明 `RequiredRoles`），**但第一个生产写工具落地那天它就是一次静默提权**。

⇒ 两侧都改成最小权限，并且**判据不写成"两侧默认值相等"，而写成"两侧都不能写生产"**——
方向一致才是要守的东西，值相等只是当下的巧合。

### 4.8 两根独立的轴之间要有约束，否则"可选的声明"就是洞

`MaxRisk` 是**任务**属性、角色是**人**属性，两者独立设定、中间没有约束
→ 一个 `viewer` 可以发起沙箱写任务，只要那个工具没声明 `RequiredRoles` 就一路放行。
**而声明是可选的：内核 7 个工具一个都没声明。** 所以这不是边角情形，是默认情形。

⇒ 加一张"角色 → 允许发起的最高风险"的表，生效上限取两轴较小者。三条落地要点：

1. **两个执行点，缺一不可**：门禁按它**拒绝**，Harness 按它**过滤交给模型的工具清单**。
   只做前者——模型看得见就会去调，每次挨拒都在花停机预算。
2. **门禁里两条规则分开写**，不要只判"生效上限"：拒绝理由要指认**哪根轴**挡的。
   任务定得低就改任务约束，角色不够就得换人来做——**现场处置完全不同**。
   合成一条会得到"风险超限"这种既对又没用的信息。
3. **超限时拒绝，不悄悄收窄。** 收窄之后任务会在完成条件那里失败，表现为"为什么没有提案"，
   而真实原因是权限。**故障点离原因越远越难指认。**

### 4.9 只建了"拒绝"的一半，等于把故障点挪到更难指认的地方

方案文件有 `schemaVersion`，但两处判据不一致：编译器用 `!=`（拒绝一切不等），
存储用 `>`（只拒绝更高版本），全仓库没有任何迁移代码。

后果很具体：**旧版本方案读得进来，但编译不过。** 用户看到的是列表里有它、双击能打开、
一按运行报一个 schema 错——比直接打不开难指认得多。而版本号从 1 变成 2 的那天，
现场所有旧方案一次性全部打不开。

⇒ 政策五条（与内核契约那套同形）：读旧写新 / 不猜新版本 / 一步一版不做跨版直达 /
**迁移只在唯一那道门里发生**（于是编译器那条严格相等语义从"版本策略"改成**断言**）/
放弃支持旧版本要明说是哪个版本还认得它。

**错误码要分清"该谁动手"**：文件比程序新（用户升级软件）、文件太旧（用户用旧软件另存）、
**声明支持却没有迁移步骤（开发：这是程序缺陷）**——第三种混用前两种的码，会把人引向改文件，
而该改的是程序。

### 4.10 机制先于需要而建时，用"可注入的表"让它今天就被执行

上面那套迁移，**真表今天是空的**（版本号还是 1，没有可迁的东西）。
如果只有一个无参入口，这套机制会在**第一次真正需要它的时候**才第一次被执行——
那正是最不适合发现问题的时刻（现场已经躺着一批旧文件）。

⇒ 给它加一个**可注入版本号与步骤表的重载**，测试用假步骤走通 1 → 2 → 3。
于是"逐版串联、顺序正确、缺步骤会报错"这三件事今天就是绿的。

**选在成本最低的时刻定政策**：此刻是一个空列表 + 一条守卫测试；
等到两个版本并存，补迁移要在"有真实数据要救"的压力下做。

### 4.11 "给模型看的文字"和"给人看的文字"是两套，别绑在一起

界面文案走 i18n（`UiText` 词条 + 插件的 `AddStrings`，覆盖率有测试守着）；
**系统提示词刻意不走 i18n**。

理由不是省事：模型的工作语言与界面语言是**两个独立决定**——英文界面配中文提示词是完全正常的组合。
硬绑在一起会导致切一次界面语言就换一套提示词，**模型行为随界面语言漂移**，
而那种漂移在测试里几乎看不见。

> 互补：DiagAgent [§4.14 中文键名要在出口翻译](diagagent-field-diagnosis.md#414-中文键名要在出口翻译)
> 讲的是**给人看的那一侧**（模型会照抄它看到的英文字段名，泄漏 `isOpen` 给调试员）。
> 两条合起来：**内部判断用稳定标识，出口按受众分别处理——人要翻译，模型不要跟着界面走。**

### 4.12 裸字符串收敛成登记值，判据是"写错一个字母会怎样"

项目里有一条硬规矩：错误码一律用 `ErrorCodes` 里登记的常量，禁止在调用点写裸字符串。
但守卫只盯错误码，**没盯别的**——于是停止原因（`"completed"` / `"timeout"` / `"no-progress"`）
散在六处赋值，还有一处用 `!= "completed"` 做分支。

**判据不是"字符串多不多"，是"写错一个字母会不会报错"。** 会静默改变行为的就得收敛。
角色名同理（门禁靠字符串相等判断，把 `enginer` 当成有效角色 = 一次静默提权），
所以角色也有登记表，且**不认识的角色一律丢弃**——拼写错误应当收紧权限，不该放宽。

### 4.13 跨 Agent 协作的仓库，共享规则要有单一来源 + 一致性自检

这个仓库同时被 Codex 和 Claude Code 改。做法：共享规则只在 `docs/agents/project.md` 维护，
`AGENTS.md` 只放 Codex 特有的、`CLAUDE.md` 只放 Claude 特有的，
再用 `scripts/check-agent-instructions.ps1` 核对入口是否一致（新增/移动专题文档时必须同步）。

**"限制性断言要实测"那三条规矩就写在这个共享文件里**——经验只有进了 Agent 每次都会读的地方，
才真的会被下一轮遵守。写在别处等于没写。

### 4.14 ⚠⚠ 解释存在，只是不在人所在的地方（一天撞了五次）

2026-08-20 至 21 有一整轮全部来自现场提问，事后归类，**五个问题是同一个形状**：
系统内部知道答案，而答案不在人当时看的那块地方。

| 现场原话 | 内部其实有什么 | 人看到的 |
|---|---|---|
| 「MVS 找得到相机，为什么这个软件找不到」 | 枚举失败码和原因 | 一个空列表 |
| 「报错权限不够，哪里能登录权限」 | 角色与风险上限判定得很清楚 | 一句"权限不够"，没有任何入口 |
| 「图像输入为什么选不了相机」 | 可用相机在状态面里列得出来 | 一个要手打 id 的文本框 |
| 「我选择了真机，点取图还是虚拟相机」 | 草稿里存着选中的相机 | 参数存了，执行侧没人读它 |
| 「第三方在用的时候怎么使用这个规则」 | 一致性规则表是活的 | 只能在界面上看，拿不走 |

**这五条的修法各不相同，但判断"有没有修好"的问法是同一句：
那个解释，出现在人下一步会看的那块地方了吗？**

它比"缺功能"更难自查，因为**每一处从代码上看都是对的**——
失败被捕获了（只是 logger 是 `NullLoggerFactory`）、
权限判定完整（只是没有改它的入口）、
参数存下来了（只是没有消费者）、
规则是活表（只是没有导出）。**代码审查看不出这一类**，
它只在"人站在界面前"这个视角下才现形。

⇒ 可操作的两条：
- 新增任何**判定**（拒绝、失败、不匹配），同时回答"人从哪儿看到它、以及从哪儿改"。
  两个问题都要有答案，只答第一个就成了本表第二行。
- 新增任何**参数或声明**，当场找出它的**消费者**。存得下、读不到，
  比不给这个参数更糟：它给出了一个不存在的承诺（本表第四行）。

> 同族但不同面：[4.9](#49-只建了拒绝的一半等于把故障点挪到更难指认的地方) 是"拒绝建了一半"，
> 这条是"解释建齐了，只是没送到人面前"。

### 4.15 测试全绿，而测试环境与部署环境的唯一差别恰好就是坏的那一处

海康相机插件包里塞了一个孤零零的 `MvCameraControl.dll`（想着"依赖带齐"），
现场加载就是 `MV_E_LOAD_LIBRARY 0x8000000C`：那个 DLL 自己还要一串同目录的兄弟库，
单拷一个反而**顶替**了系统上装好的整套 SDK。

**全部测试是绿的。**原因不是判据写松了，而是**测试输出目录里从来没有那个 DLL**——
测试环境与部署环境**只差这一处**，而这一处正是坏的那处。
夹具里"不存在的东西"，恰好是部署里"存在且有害的东西"。

⇒ 两条：
- **凡是"打包时多放/少放一个文件"的决定，都要有一条在真实布局下跑的判据。**
  本项目现在有一条：导出的开发包**不传任何参数**跑一次 `dotnet test`
  （见 [5.2](#52-已有的几条判据值得单独点出来)）——同一天另一个 bug 也是这么抓到的：
  `HuikeSdkDir` 默认指向一个不存在的目录，而 CI 一直显式传参数所以永远是绿的。
  **守卫绕开了真实用户必经的那一步，就等于没守。**
- 原生依赖**不自带**，让它解析到系统安装；带不了就明确报"请装厂商 SDK"，
  不要带半套。半套的失败码指向的是加载器，不是缺件。

**同族的第三次（2026-08-21）**：把默认账号从"只带 admin"改成"带全部角色"时，
新逻辑只走"账号表为空"那一支——**于是这条修复只对全新安装成立**，
而现场那台机器早就有一个旧的默认账号了。
和模板那次是同一个形状：**仓库里是对的，装出来那份不对。**
⇒ 凡是改"初始化时怎么建"的逻辑，都要同时回答
**"已经建过的那些怎么办"**；只改建的那一支，等于只修了还没发生的机器。

### 4.16 右键菜单挂在共同祖先上，就分不出人点的是谁

流程画布上删节点、删连线，第一版把 `ContextMenu` 挂在 `NodifyEditor` 上——
它是节点与连线的**共同祖先**。现场原话："我明明右键在线上，点击删除显示的是模块"。
菜单按选中集去删，于是删掉的是节点。

改成节点与连线**各挂一份**，作用对象取那个控件的 `DataContext`：**点了什么就动什么**。
另加一条测试盯着"编辑器本身不许有菜单"——挂上去从界面完全看不出区别（菜单照样弹出），
**只能靠测试守**。

修这一版时撞出一个附带 bug：切换语言的 `SetMenuText` 只刷"当时已存在"的菜单项，
而节点与连线的控件是模板**之后**才建的——后建的那些菜单项是**空白**的。
⇒ 文案要存下来、建项时就设上；「遍历现有实例改文案」这个写法，
凡是实例会**后续增生**的地方都是错的。

### 4.17 判据选在链条下游，上游断了它照样绿

上一条改完，现场说"右键到线上或者模块上**还是**没有删除弹出"。
菜单挂对了、文案有了、`Click` 处理也对——**右键根本到不了它**。
反射打出 `NodifyAvalonia` 的默认手势表才看见：
`EditorGestures.Mappings.Editor.Pan` 是「右键**或**中键」，
`Editor.CancelAction` 是「右键或某个键」——**裸右键被编辑器自己吃掉了**。

那时画布已经有 15 条无头测试，全绿。它们**直接调菜单项的 `Click`**——
验的是**动作**，而坏的是**到达那个动作的手势**。
判据选在链条下游，上游断了照样绿。

⇒ 三条：
- **人经过的是"手势 → 命中 → 菜单 → 动作"整条链，判据至少要有一条落在人的入口上**，
  而不是全部落在末端。末端的判据便宜、稳定、好写——所以会不自觉地全写在那儿。
- 新判据要**反证**：把修补注掉，它必须红。这条测试反证过（报"Editor.Pan 绑了裸右键"）。
  这一整轮里靠反证抓出四条假绿。
- 断言写成**规则**而不是具体字段：「没有任何编辑器手势绑着裸右键」。
  第三方库的手势表是**全局可变静态**，同类冲突以后还会有，换了版本换了字段名它还成立。

**⚠ 补记（2026-08-21 当天晚些时候，同一个 bug 又报了一遍）**：
上面那三条我当时都写下了，然后**违反了第三条**。
测试名叫 `RightClickIsNotTakenByAnyEditorGesture`——`Any`——
而实现是对两个字段各断言一次（当时反射只看见那两个）。
真实情况是裸右键有**五处**，漏掉的 `ItemContainer.Selection.Select`
正好管"右键点在节点上"，于是现场的症状一点没变。

**规则写在名字里、实现成几次点名赋值，等于没有规则。**
名字是给人看的意图，代码是实际的判据；两者一旦分叉，
**分叉本身不可见**——测试是绿的，名字读起来还很像那条规则。
这比一开始就写窄更危险：写窄的人知道自己写窄了。

改法是把规则真的实现成遍历（扫整张手势表），并且**修补与判据共用同一个遍历**——
两边各写一份的话，它们会各自漂移，而漂移的那天没人在看。

顺带得出第四条，它比前三条更普适：

- **"扫不到"有两种原因：真的没有，和根本没走进去。**
  用反射遍历第三方结构时，库一换版把私有字段改名，遍历就静默地什么也不访问，
  判据于是**永远绿**。所以给判据加判据：拿一张**已知含有三处违规**的默认表去扫，
  扫不出来说明遍历失效了——先证明这把尺子还能量东西，再用它量。
  一句话：**判据自己也需要判据。**

### 4.17bis 同一句症状报了三次，断点每次在链条的不同一节

"右键没反应"这句话，现场一天里说了三遍。三次的原因**完全不同**，
而每一次我修完都以为修的是"那个"原因：

| 第几次 | 断在哪一节 | 实际原因 |
|---|---|---|
| 一 | **挂点** | 菜单挂在节点与连线的共同祖先上，分不出点的是谁 |
| 二 | **手势** | 库的默认手势表里五处绑着裸右键，右键在到达菜单前被吃掉 |
| 三 | **命中** | 右键从控件身上**穿过去**了：画刷为 `null` 的区域不是命中目标 |

第三次的细节值得单独记，因为它是 Avalonia 与 WPF 的一处实质差别：
`Nodify.Connection` 在 Avalonia 下继承自 `Panel`、又没实现 `ICustomHitTest`，
于是**整条连线在任何一点都命不中**——不是"线太细点不准"，是一次都命不中。
节点也一样：只有标题那条有画刷（跟颜色走），主体和容器留白都没有，
所以"只有标题点得中"。

⇒ 三条：
- **一条人机交互链有好几节：手势 → 命中 → 挂点 → 动作。判据要按节写，一节一条。**
  缺哪一节，那一节断掉时就没有东西会红——而症状在最末端，三次长得一模一样。
- **同一句症状连报两次以上，就不要再在上次那一节里找。**
  第二次我还在改手势表，第三次才想到去问"右键到底命中了谁"。
  一个便宜的问法：**把那一节的输出直接打出来**（这次是"在线上取点做命中测试返回什么"），
  而不是继续推理上一节。
- **换 UI 框架时，"能不能点中"这类事不要靠 WPF 的直觉。**
  WPF 的 `Shape` 按几何命中，Avalonia 的 `Panel` 按画刷；
  移植过来的库会把这个差别原样带进来，而它的症状是"什么都没发生"。

### 4.17ter 判据只往自己动过的方向长 → "修好了 A、弄坏了 B、套件全绿"

紧接着 4.17bis：为让连线可命中，派生了一个子类。**连线从此看不见了。**
Avalonia 的隐式 `ControlTheme` 是按控件的**样式键**查的，而样式键默认就是控件自己的类型——
子类在库的主题里查不到任何条目，`Stroke` 为 `null`、`StrokeThickness` 为 0，画出来什么都没有。
实测对照：基类 `stroke=#ff5ca2c9 thickness=3`，没覆盖样式键的子类 `stroke=NULL thickness=0`。
**继承拿到了基类的实现，却丢掉了基类的外观，而且不报错。**

要记的不是这个 API 细节，而是**为什么套件是绿的**：
上一轮我加的两条测试断言的是"类型是不是那个新子类"、"有没有 ContextMenu"——
**全都在盯我改的那一面，没有一条盯我可能弄坏的那一面。**

判据是跟着改动长出来的：改了什么，就想到验什么。
于是它天然覆盖"我想让它成立的事"，天然不覆盖"我顺手破坏的事"。

⇒ 三条：
- **每个改动问一句"这一改可能弄坏什么"，并为那件事写一条判据。**
  这次那条判据只有一句话：这根线有没有颜色、有没有宽度——**人看得见的那个属性**。
- **具体 bug 修完顺手提成规则**，因为同一手法还会用第二次：
  这里提成了"扫整个 UI 程序集，凡从库控件派生的类都必须覆盖样式键"，
  **不点名任何类**——点名的话，新加的那个正好是漏掉的那个（这一天栽过两次）。
  规则型判据要配一条"至少扫到一个"，否则它会静默空转（见 4.17bis 的同款）。
- **规则是筛子，不是结论。**同一轮还撤掉一处改动：我依"画刷为 null 不可命中"
  给节点设了背景画刷——规则没错，但实测那个库的主题**本来就给了**，
  真正缺画刷的是外层容器。凭规则成立就动手、跳过"这一处到底缺不缺"这一步，
  代价是悄悄改了别人没要求改的外观。**过了筛子还得量一次这一处。**

### 4.17quater ⚠⚠ 判据一次都没走过人走的那条路（这是前面三条的共同根因）

同一句"右键没反应"，现场问到第四次，加了一句：**"你能自己操作试试吗"**。
那句话就是解法。

前三轮每轮都修了一处真缺陷、每轮都加了测试，而那些测试断的都是**对象图**：
类型对不对、菜单挂没挂、画刷是不是 `null`。
**"右键点下去菜单开不开"这件事，一次都没被执行过。**
判据和症状之间始终隔着一层，所以三轮下来症状一字未变。

真按下去之后，缺陷第一次现形，而且**和前三轮猜的都不一样**：
右键**按下**落在节点内层的 `Border` 上，**松开**时事件源变成了外层容器——
按下与松开的源不是同一个控件，框架就不发 `ContextRequested`，菜单挂在谁身上都不会开。

⇒ 四条，第一条最重要：

- **UI 缺陷的判据必须至少有一条真的模拟输入。**
  "断对象图"是廉价、稳定、好写的，所以会不自觉地全写成那样；
  而它验的是"我把东西装对了"，不是"人做那个动作会发生什么"。
  三轮白修的代价买来这一条。
- **先判断测具本身行不行。**这次顺手放了一个素 `Border` + 右键菜单进同一个测具：
  它能开，才说明"节点上开不了"是关于节点的结论。
  它要是也开不了，那些 `false` 什么都不说明。**判据自己也需要判据**（同 4.17 那条）。
- **"这个环境做不了 X" 和 "A 与 B 无法共存" 是同一类断言，同样必须实测。**
  能真按右键，是因为先推翻了自己写下的一句话：
  "测试会话不会用那个 AppBuilder，所以没有字体、跑不了布局、只能断对象图"。
  **后半段是从前半段推出来的，而前半段是错的**——补上字体与 Skia 两样都生效。
  这类断言比 4.1 那种更隐蔽，因为它不只错一句话，
  **它决定了接下来所有测试的形状**：一句"环境做不了"能让整类判据永远不被写出来。
- **事件路由方向要选"从里往外"。**修法是右键按下即主动开菜单、
  且只走冒泡不走隧道：隧道从外往里，外层容器会先接、先开出自己那一份，
  于是"点在节点上弹出的是容器那份"——层级关系又一次替人做了选择。

> 同族：[4.14](#414--解释存在只是不在人所在的地方一天撞了五次) 是"解释不在人所在的地方"，
> 这条是"**判据不在人走的那条路上**"。两条是同一件事的两面：
> 一个说输出，一个说验证。

### 4.17quinquies 软件回答不了的问题，不要让它替人回答——但要把证据摆齐

现场问："同一个插件注册两次会怎么样，软件是怎么区分插件是不是相同的"，
接着追问："你怎么区分是同一个插件更新还是不同插件，是不是要弹窗让客户确认比较好"。

**第二问的答案是：区分不了。**插件身份就是清单里的 `Id`，
而 `Id` / 名称 / 作者 / 版本**全是包作者自己写的字符串**，没有签名可验——
"同一个插件出了新版本"和"另一个人用了同样的 `Id`"在数据上完全一样。
（唯一相关的守卫是"清单必须与代码里的声明一致"，所以光改清单没法把别人的库说成自己的；
但两边同一个作者写，它防打包错误，不防冒名。）

⇒ 这类问题的处理法是一套固定动作，比这个具体场景更通用：

- **先把"无论人怎么答都不成立"的情形挑出来，直接挡，不要变成问句。**
  这里是"算子键已被别的插件占着"——重启后宿主根本装不起来。
  把它做成确认框等于**把坏消息包装成一道选择题**。
- **挡要挡在最早能挡的那一刻。**原来的行为是注册一路绿灯说"已注册，重启后生效"，
  重启才炸，现场看到的是"软件打不开了"，而修法要去目录里手工删东西。
  **动作与后果之间隔着一次重启**，这是最难自查的形状之一（同 4.14 那族）。
- **剩下的交给人，但必须把"软件判断不了的那一部分"摆到问句下面**：
  替换谁、版本从几到几、**名字对不对得上**（这是冒名唯一会露出来的地方）、
  **哪些能力会消失**（在用的数据会因此打不开）。
  问句要**点名**，一句"确定要继续吗？"在产线上等于没问。
- **最容易是误操作的那一种要单独成类。**这里是**降级**：它最容易被"成功"四个字盖过去。
  判不出版本关系时算"重装"——**宁可含糊，不要说错方向**：
  把降级说成升级，人就不会多看一眼。
- **"出计划"和"执行"分开，且计划阶段不许有副作用。**
  问人之前就把东西装上的话，人点取消也已经装了——
  那种确认框比没有更糟，它给出了一个不存在的选择。
  执行时吃**那份计划**而不是重新算一遍，人看到的才和真正发生的是同一件事。

> 顺带一条夹具经验：为造"两个插件抢一个键"，我在测试程序集里放了两个同键的算子类型，
> 结果**别的用例扫这个程序集建目录，24 条无关测试一起红**。
> 改成一个类型由两个扩展各登记一次，键名加 `test.` 前缀。
> **夹具的作用域比它看起来大**——凡是"往程序集里加一个会被扫到的类型"都要先想一想谁在扫。

### 4.21 ⚠⚠ 一份不完整的清单比没有清单更糟，因为它会阻止人去数

一天之内同一个形状犯了四次，四次都不是我们自己的测试发现的：

| 那份清单 | 它看起来是 | 实际是 | 后果 |
|---|---|---|---|
| 契约接口表（生成第三方文档用） | 全部对外接口 | 漏 10 个 | 第三方**不知道那些扩展路径存在** |
| "你能实现的接口"一栏 | 一类语义 | 三类混装 | 照着"必须实现"去写的人白干一遍 |
| 翻译键推导方法清单 | 六个（穷举语气） | 十三个 | 漏掉的正好是最容易忘的那批 |
| 名叫 `...FullyTranslated` 的判据 | 全部键类别 | 5 / 13 类 | 内置插件在英文界面上冒中文，缺了几个月 |

**要记的不是"手写清单会过期"**——那是老生常谈，读的人会点头然后继续犯。
要记的是更反直觉的那半句：**不完整的清单会阻止人去数。**

翻译那节是最干净的标本：紧挨着的两句话，前一句列了六个推导方法（穷举语气），
后一句写"该翻哪些键不用肉眼数，问 `translation_keys`"——
**前一句把后一句抵消掉了。**一个看起来完整的清单，让人不必去用那个真正完整的工具。

#### 诊断特征：完整感来自形式，不来自核对

这四处的"完整感"没有一处来自有人真的数过，全部来自**形式**：
名字里带 Fully、列表编了号、语义分了两栏、清单按字母排了序。
**形式对称会伪装成内容完整。**

⇒ 可操作的自检只有一句：**凡是"这是全部 X"的地方，问一句
"这个数字是数出来的还是写出来的"。** 数出来的（反射、扫描、活表）留着；
写出来的，要么改成数出来的，要么加一条清点守卫（"每个 X 都必须被归过类"）。

#### 发现方式也是结论的一部分

四处都是**同一个身份**撞出来的：一个只能看文档、照着做的外部读者
（这次是第三方示例包的作者）。**作者看不见自己表里的缺口**，因为作者知道表外面还有什么；
照着做的人只有表，所以缺口对他是硬碰硬的。

⇒ 要复现这种发现，成本最低的办法**不是更仔细地审**，
是让一个只有文档的人真的照着走一遍。同一条链路换个身份走，默认假设就变了——
[4.15](#415-测试全绿而测试环境与部署环境的唯一差别恰好就是坏的那一处) 那条
"只对全新环境成立的修复"、以及找圆那条"把正常不良品当异常"，都是同一个道理的另一面。

### 4.22 防空转的断言，容易反过来把缺陷写死成前提

给判据加"防空转"这一句是对的（[4.17](#417-判据选在链条下游上游断了它照样绿) 那族的结论：
反射扫不到东西时，判据会永远绿）。但**这一句本身有一个容易走反的写法**。

真实例子（同一天，两个会话各写一次）：一条守卫要保证"源文案是标识符的键必须有中文"，
防空转写成了

```csharp
Assert.NotEmpty(identifierSourced);   // 过滤之后必须非空
```

它在一个**做对了的**包上当场红了——那个包给枚举项都声明了中文显示名，
所以一条标识符源文案都没有。也就是说这句断言的实际含义是
**"这个包必须一直有这种毛病"**：代码变好的时候，测试变红。

写的时候脑子里想的是"防止过滤器空转"，手上写出来的是"断言过滤结果非空"——
**两者只在缺陷存在时等价。**

⇒ 防空转的锚点要落在**工具**上，不能落在**发现**上：

```csharp
Assert.NotEmpty(scanned);                                    // 扫描器扫得到东西
Assert.Contains(scanned, e => e.Key.Contains(".option."));   // 会产生这类缺陷的那一类在视野里
// 然后才是真正的规则：这一类里凡是标识符源文案的，必须有中文
```

⚠ 这条不需要遗留代码就会中：两处都是**当天新写的判据**。
所以它不是"老代码的毛病"，是写防空转时的一个默认手滑方向。

### 4.23 反证本身有假阴性：确认改的是哪一行，或者让失败信息替你确认

"新判据一律反证——把修补注掉，它必须红"是这份文档里被引用最多的一条
（[4.17](#417-判据选在链条下游上游断了它照样绿) 那族）。但**这个动作自己也会骗人。**

真实一次（2026-08-21）：要验一条"扩展维度必须按概念数（8）"的守卫，
反证时用字符串替换去改分组方式——**patch 打到了同一个文件里另一处长得一样的
`GroupBy` 上**（另一个方法的），被测那处一个字没动。测试照样绿。

那一刻正确的读法本该是"这条判据是空的"，而事实是"我没改到被测的那处"。
**两种情况给出的颜色一模一样。**（我是因为觉得 9 → 8 这么大的改动不可能不红，
才回去看了一眼改动落在哪。）

⇒ 两条做法，第二条更省事：

1. **反证之后确认改的是哪一行**，不要只看颜色。
2. **让判据的失败信息带上实测值**——那样红的时候看一眼那个值变没变，
   就知道 patch 有没有落在被测处。比如断言写成"实际数到 9 个维度"而不是
   "数目不对"，反证的可信度是白送的。

第 2 条还解释了一件本来只当"体验问题"的事：**"只报个数、不报清单"的断言
除了难查，还让反证本身变弱。**——报清单的断言，反证时清单会跟着变；
只报个数的断言，反证时你只看到另一个数字，分不清它来自被测处还是别处。

> 这条是第三方示例包作者那边补的：他反证时的做法是 grep `[FAIL]` 后面的测试名，
> 确认**红的是哪一条**——那挡住了"红的是别的测试"，但挡不住
> "我根本没改到被测的那处，而它因为别的原因红了"。同一族的假阴性，两个人各撞一次。

### 4.24 ⚠⚠ 限制性断言写进代码注释时最危险——因为它紧挨着一段正确的规矩

"『X 做不了』这类话进文档前必须实测"这条已经在这份文档里立过（ScottPlot 那次）。
2026-08-24 又撞一次，**这次它在代码注释里**，而这个位置比文档糟。

现场原话：「相机的IP地具体值没显示，要显示出来」。设备页左边信息栏写着
`地址: 192.168.4.101`，右边参数面板的「静态 IP 地址」是个**空格子**。

空格子是**刻意**的，注释写着：

> 设备配置那组读不回来：它不是 GenICam 特征，当前值要从枚举结果看。
> **读不到就不放进结果**——放一个猜的值进去会让漂移比对拿假事实做判断。

**这两句话的地位完全不同，而它们挨在一起：**

| | 内容 | 真假 |
| --- | --- | --- |
| 前一句 | "读不回来，它不是 GenICam 特征" | **推断，而且错** |
| 后一句 | "读不到就不放，猜的值会污染漂移比对" | 对，而且重要 |

前一句错在把**我们的实现缺口**说成了**相机的性质**：写 IP 确实不走特征
（`GigeSetIpConfig` / `GigeForceIp`），但**读**的时候它们就是普通整型特征
（`GevPersistentIPAddress`）。真实原因只是 interop 层缺一个 `MV_CC_GetIntValue`
的 P/Invoke。

⇒ **代码注释比文档危险，有两个叠加的原因**：

1. 它就在**下一个想做这件事的人必经的路上**——文档要人主动去翻，注释是撞上来的。
2. **它紧挨着一段正确的规矩，于是对的那句替错的那句做了担保。**
   读到这里的人（包括我，跳过了一次）看到"猜的值会污染漂移比对"觉得这段想清楚了，
   就不会回头质疑上一句的依据。

⇒ 做法：注释里写"做不到"时，同样注明**实测还是推断**，
并且**把"我们这儿还没实现"和"它做不到"分开写**。
前者是待办，后者是约束——写成后者，待办就消失了。

修完之后那条正确的规矩**一个字都没动**：读失败仍然不放，读到 0 也不放
（0.0.0.0 在这几个格子里的含义是"没配"，把"没配"显示成一个看起来像地址的值，
比留空更容易被当成真配过）。**前提修正了，规矩照样成立**——这也是识别这类错误的一个信号：
如果一句"做不到"被推翻之后，周围的设计基本不用改，那它当初大概就不是设计的一部分，
只是一句顺手写下的解释。

#### 附带一条：这次的交叉核对用了"过度确定"

判据不止"读回来的是个能解析的地址"，还要求它**与枚举结果给的地址一致**——
枚举与特征读回是两条独立的路。反证时把字节序倒过来得到 `101.4.168.192`，
`IPAddress.TryParse` **照样通过**，只有交叉核对红。
单值判据在这里天然弱：串位、字节序反、读错特征，三种错误的产物**都还像个地址**。

### 4.25 ⚠⚠ 归责只发生在有声明可比对的地方——没有声明，缺陷就谁的账都不记

现场问了一句很实在的话（2026-08-24）：

> 是插件的问题还是软件架构的问题？**软件能在注册时增加这种错误提示吗，
> 并且区分是软件问题还是插件问题，插件问题让制作插件的人修改。**

查下来的答案值得单开一条，因为它不是"提示忘了做"。

#### 缺陷本身在插件，但放大它的机制在主干道，而且那半更难发现

设备参数的读回结果是一个 `Dictionary<string, object?>`。
**缺一个键同时表示三件事**：这一项本来就读不回来 / 这次读失败了 / 设备上确实没配。

三者混成一档的后果**不是"提示不够详细"，而是没有可比对物、所以没有归责**：
宿主看到一个键没回来，无从判断该找插件作者、该记一条设备异常，还是什么都不该说。
于是这个缺陷**谁的账都没记上**，靠人盯着界面发现。

同一轮还挖出主干道那一半：设备页的参数面板加载的是**保存值 + schema 默认值**，
不是读回来的值。于是"设备上的 IP 是多少"这个问题**在人问的那一格里没有答案**，
而且"答不上来"这件事本身也没显示。

**那一半会看起来是对的**，这是它的要害。真机上量出来的三格：

| 格子 | 界面显示 | 真实值 | 那个显示其实是 |
| --- | --- | --- | --- |
| 静态 IP | *空* | `192.168.4.101` | 默认值 `""` |
| 子网掩码 | `255.255.255.0` | `255.255.255.0` | **默认值，碰巧撞对了** |
| 网关 | *空* | `192.168.4.254` | 默认值 `""` |

⇒ **空格子会被人抓住，一个看起来对的值不会。** 掩码那格好几天都"显示正常"。

#### 做法：先加声明，才有归责

1. **加一维声明**（这一项读不读得回来）。有了声明，"声明可读却没回来"
   才成为一句**可判定**的话。**声明是归责的前提，不是归责的补充。**
2. **判据只看声明与结果，不看原因。** "设备真不支持 / 作者没实现 / 这次通讯失败"
   三者观测表现完全相同，能确定的只是"和它自己的声明不一致"。
   （与 [4.17quinquies](#417quinquies-软件回答不了的问题不要让它替人回答但要把证据摆齐) 同一条线。）
3. **归责的话要指名，并给全两条改法**（补上实现 **或** 声明它读不回来）。
   只给第一条会逼作者去实现一个设备可能真的不支持的东西；
   而"某个插件有问题"这种不指名的说法**和没判一样**。
4. **规则要奖励声明，不能惩罚声明。** 声明过的不算违规——
   否则报警会报到诚实的作者头上，那会**直接教会作者别声明**。
5. **两个通道不许在界面上合并**："你配的是什么"该补默认值，
   "设备上是什么"**不许补**。合成一格就永久失去"这是读数还是我配的值"这个区分，
   而分不出的那一刻，一个看起来对的默认值就会被当成设备的现状。

#### 附带一条：查不到的时候，说清查不到

现场问的是"能不能在**注册时**提示"。对这一类**不能**，而且原因是硬的：
设备参数表挂在设备对象上，设备对象只能由枚举到的真设备造出来——
**注册时手里没有设备，也就看不到参数表**。所以判定只能落在第一次从设备读回时。

一致性套件因此**没有**为这条加规则，并把"加不了"和理由一起写进了 ADR。
硬写一条只会得到**一条永远不会响的规则**——那比没有规则更糟，
因为它会让下一个人以为这块查过了（同 [4.21](#421--一份不完整的清单比没有清单更糟因为它会阻止人去数)）。

### 4.26 ⚠⚠ 单一输入的守卫看起来完整——两条防撞号的判据都因此漏了它们要防的事

这条是 [4.21](#421--一份不完整的清单比没有清单更糟因为它会阻止人去数)（手写清单）的
**同族第三例**，而且这次栽的是**判据自己**，不是文档。

2026-08-24 给插件包加"更新记录 / 已知问题"两条规则时，两条元判据突然红了：

| 判据 | 它要防的事 | 它的输入 |
| --- | --- | --- |
| 规则表与检查代码不许漂移 | 发得出来却没登记的规则（第三方查不到） | **一个文件** |
| 规则号不许撞 | 同一个号表示两件事 | **同一个那一个文件** |

把输入改成"扫整个套件目录"之后，露出来一个**先前就存在的真缺陷**：
包结构那组规则一直用着 `HKC0080–0084`，**和「翻译」那组撞号**，
而规则表只登记了翻译那一种。后果具体到可以复述：
第三方收到一条 `HKC0082`（清单与代码版本不一致），去开发包里查表，
查到的是"翻译只做了一部分"——**照着改会越改越远**。另外两个号根本没登记在册。

**最刺的一点**：防撞号那条判据的注释里写着"这条守卫是从一次真事故来的：
新加设备那组规则时用了 HKC0060–0062，而那三个号早被错误码那组占着"。
**它记得自己为什么存在，却因为只读一个文件而漏了下一次同样的事。**

⇒ 判据的覆盖面要跟着**代码实际所在的地方**走，
不要跟着写判据那天恰好想到的那个文件走。
一个只看单一输入的判据，红的时候可信，绿的时候什么都不说明——
而它的绿会被读成"这件事查过了"。

⇒ 反证要挑**新加的那个文件**下手：在旧文件里撞一个号，两条判据都会红（旧版本也能抓）；
在新文件里撞，只有加宽后的版本抓得到。**反证要落在"改动带来的那部分覆盖"上**，
否则验的是本来就有的能力。

#### 附带一条：反证第一次没落在被测那条规则上

反证"记录里没提当前版本"这条规则时，第一次只改了清单里的版本号 →
测试确实红了，但报的是 **`HKC0102`（清单与代码版本不一致）**，它先返回，
我要验的那条**根本没走到**。改成清单与代码一起改，才看到目标那条。

这是 [4.23](#423-反证本身有假阴性确认改的是哪一行或者让失败信息替你确认) 的另一种形态：
那一条说的是"patch 可能没落在被测的那处"，这一条是
**"红了，但红的是链条上更早的一环"**。两者的共同解法相同——
**看失败信息里那条规则的 Id / 那个实测值**，不要只看颜色。

### 4.27 ⚠⚠ 评测第一次跑，抓到的第一个缺陷往往是评测自己的账

新建的评测第一次接真模型跑，`camera-evidence-missing-001` 报了"自信错误结论"。
读 Episode 看到的是：那条场景**故意在预取里不查相机**，期望规则停在"判不了"；
而**真模型自己去把相机读了**，规则于是正确命中——系统做得比场景预想的还对，评分卡却记成扣分。

根因是我在评分卡里埋了一个隐含等式：**「预取没取」= 「证据没到」**，而它**只在离线模型下成立**。
真模型会补取，而那正是想要的行为。

⇒ 两条：
1. **评测报警时，先问"错的是被测系统，还是评测自己"**。要是当时顺手去改 harness 迁就那个警报，
   就会为了一个错的判据去改对的代码——**用一条写错的判据去改一条对的实现，是最难回头的方向。**
2. 修法是让期望**跟着实际取到的证据走**（`UndecidedWhenEvidenceAbsent`：规则→它依赖的证据前缀）：
   证据没到必须判不了、到了必须命中。**"结论要和证据一致"这句话对任何模型都成立**，
   而"预取取没取"只是离线模型的实现细节。模型自己补取记进单独一栏、**不扣分**——
   它是两种模型之间最明显的差别，值得看见，不该罚。

**配套**：评分卡自己要有变异检查（把某条期望改错，要求必须变红），否则"十条全绿"什么都不证明——
一个永远给满分的评分卡也是这个结果（见 §5.3）。

### 4.28 ⚠ "无进展"有两种形状，工具计数器数不到"说要查却不发调用"的空转

`AgentHarness` 类注释写着四种硬停机含"无进展"，但那个判据（[4.6](#46-无进展判定的签名要带上结果并写明它的失效场景)）
**只覆盖一种形状**：同一个调用反复得到同一个结果，按**工具调用**计数。

2026-08-25 用 `qwen3:8b` 跑评测时露出第二种：模型每轮输出「还需补充：graph.read、log.search…」
**却一个工具都不发**。这种循环里 `repeatByResult` / `repeatByInput` 一动不动（没有工具调用），
`MaxToolCalls` 同理，**唯一兜得住的只剩 deadline**——同一段话复读 45 轮到 90 秒超时。
结论是对的（收尾照跑因果规则），赔的是延迟，而 90 秒正好压在 DiagAgent 那条"现场等不了"的线上。

⇒ 补第二种判据：连续 N 轮既没有工具调用、验证结果又没变化 → `NoProgress`（N=2：
第一次验证打回时模型还没看过那段反馈，不该算它一轮）。三个决定：
- **只看验证结果，不看模型那段话**——话换了措辞而证据没多一条，系统状态就是原地不动，
  给"换个说法"发额外轮数等于按文采计费。这跟 ADR-0013 同一个道理：判据不经模型的笔。
- **完全不碰 `ClaimsDone`**：隔壁那条线试过收紧 `done` 的取值来堵，证伪了——
  收口只看 `verification.Status`，`done` 只喂给一条日志，约束它对停机毫无影响。
- **反向判据**：真在取新证据（结果每轮不同）时必须走到 `MaxToolCalls`，
  否则这个阈值早晚被后人压到 1，把"取证要花好几轮"的正当诊断掐掉。

⚠ 口径：这个复读循环**目前只在 `qwen3:8b` 上实测到过**。本机 Claude 那几轮读 Episode 是另一回事
（模型回合 1 次、工具调用 6 次，90 秒是纯延迟不是复读）。**洞是结构性的（读代码就能看出来），
"别的模型也会掉进去"则是推断**——两件事分开写（这正是 [4.1](#41--限制性断言必须实测否则一句错话会污染整条推理链) 的规矩）。

**"那个修复改了结论没有"也实测了**：拿 `--rescore`（见 4.29）把修复前后两份存档逐字段比——
11 字段 × 10 场景 × 2 组 = **0 处差异，只有耗时变了**。所以它只买了时间、没动任何结论。
加一条提前停机，天然要被问"它会不会掐掉本来能查成的诊断"，这个数就是答案。

### 4.29 ⚠⚠ 投影必须能从事实重算——判据变了不用重跑真模型

评分卡改过口径（4.27）之后，那轮真模型的数据已经在磁盘上，重跑要几分钟真钱换一个本来就算得出的数。
不用重跑：`events.jsonl` 是唯一的记录之实体、其余都是它的投影（这是 `EpisodeRecorder` 早就写下的话，
本来只用来解释"为什么不另存一份聊天记录"）。**评分卡也是投影，所以它必须能从事实重算。**

⇒ 加 `--rescore <存档目录>`：把事件逐条喂回 `EpisodeState.Add`、按当前判据重判，不调模型。
这条推论比这个功能本身值钱：**重算不出来，就说明判分偷偷依赖了某个没被记进事实里的东西——那本身是缺陷。**
它是个可执行的判据，不是原则性的漂亮话。

两个实现要点：
- **投影用同一段代码**（抽了 `ScenarioRunFactory`，跑一轮和重判共用）。另写一遍"从 JSON 挑字段"，
  出分歧那天两个分数都言之凿凿、谁也证明不了对方错。
- **没有存档的场景记成失败、不静默跳过**：少算几条让分母变小、分数虚高，
  而表现是"分数还挺好看"——跟自信错误结论同一类失效（[4.21](#421--一份不完整的清单比没有清单更糟因为它会阻止人去数)）。

### 4.30 判据变了，历史数据的解释权跟着变，而没有任何东西提醒你

延续 4.29：判据一改，磁盘上那些 `scorecard.json` 就都是旧判据的产物了，
**而报告上那个 10/10 长得一模一样**。隔壁那条线差点拿旧判据的分报上去，靠"这数还作数吗"一问才想起重判。

⇒ `--rescore` 重判完，拿存档里当初那份 `scorecard.json` **逐字段对账**，漂移就点名：

```
⚠ 判分漂移 4 处——…/scorecard.json 是旧判据的产物，别再引用它：
  · camera-evidence-missing-001：过 否 → 是
```

**刻意不做"判据版本号"**：版本号要靠人记得改判据时顺手 bump，而"忘了同步"正是这个洞本身的形状——
拿同一种失败模式去堵它，只是把它挪个位置，以后会出现"判据改了但版本号没改"，
那时校验说"一致"，**比现在更糟，因为它给了假的安心**。比实际分数不需要维护任何东西。

四个决定（`ScorecardDiff`）：**不比耗时**（当场用秒表、重判用事件跨度，两个口径，
算进去每次一堆噪声、真漂移淹在里面——报噪声的检查等于没检查，因为人会开始跳过它，而跳过不可见）；
`过` 排最前（唯一会被直接引用进结论的字段）；清单按集合比不按顺序（顺序不是判据的一部分，
并发预取就改过落盘顺序）；场景增减也算漂移（存档少一条就不再代表"全量跑过一遍"）。

### 4.31 ⚠⚠ 一个改动可以不引入缺陷，却把潜伏竞态从"撞不上"推到"必现"

`OnEpisodeEvent` 一直是这样：后台线程 `_liveEvents.Add(e)`，然后
`Dispatcher.UIThread.Post(() => ShowEpisode(_liveEvents, true))`——**把还在变的列表本身**交给界面。
两个错叠着：`List<T>` 被多线程 Add；Post 过去的是同一个会继续变的列表，界面 `foreach` 到一半又被追加。
症状：`System.InvalidOperationException: Collection was modified; enumeration operation may not execute`，
点「新建诊断」直接闪退。

**这段代码在本机 Claude 上跑了很久没事**——一轮 6~8 秒，事件稀疏得撞不上。
换成本地模型（一轮 1~4 秒）**加上并发预取**之后，第一次点就崩。

归因要分两半，别含糊：
- **缺陷不是这两个改动引入的，代码本来就错**（跨线程读写共享列表 + 传引用而非快照）。
- 但它们各自**提高了撞上的概率**：本地模型把轮次间隔缩到秒级；而并发预取改变了事件的**节奏**——
  改之前那几条预取事件被每个工具的执行延迟撑开，改之后工具活全干完才进那个紧凑的落盘循环，
  几条 Append **背靠背成一簇连发**（落盘本身仍是单线程串行，观察者没有变成多生产者——
  变的是密度不是线程数）。一簇事件正好让 UI 的 `foreach` 大概率撞在半途。

⇒ 三条：
1. **"我的改动会不会引入 bug"和"我的改动会不会让既有 bug 现形"是两个问题**，后者同样要答。
   一个只是加快节奏 / 提高频率的改动，能把一条写了很久没事的竞态变成必现——责任不在"引入"，在"暴露"，但暴露也是要认的账。
2. 修在**契约指定的那一侧**：`EpisodeLog.AppendAsync` 的注释本就写着"观察者跑在调用 Agent 的线程上，
   界面接这个口子必须自己切回调度线程"。所以修法是 UI 侧加锁 + **Post 快照而不是列表本身**，
   不是去改 harness。（没改成"界面自己读 events.jsonl"——那是每条事件一次盘 IO，快照只是一次数组复制。）
   ⚠ **锁不能因为"落盘是串行的"就删掉**：观察者调用虽不重叠，但每次 `await` 之后续在哪个池线程不定，
   而 `LiveSnapshot()` 是界面线程调的——**读写仍然跨线程，只是不并发**。下一个人看到"串行"两个字
   容易把锁当多余顺手删，注释里要写明它守的是"跨线程"不是"并发"。
3. **这类缺陷在无头测试里天生看不见**：所有单元测试全绿时它才被真程序抓到。
   同族的第二个（下拉默认选不中本地模型——把**代码自己填的默认值**当成了人的选择）也只在界面截图里现形。
   跟 [4.17quater](#417quater--判据一次都没走过人走的那条路这是前面三条的共同根因) 那条"真的模拟一次点击"是同一个教训，
   **只不过这次连模拟输入都不够——得跑真程序 + 真模型 + 真并发**。测试写得再多也补不上这一段，
   它是维度问题不是数量问题。
4. **进程崩掉时，栈在系统事件日志里，猜是猜不出来的。** 这个 bug 第一次现身时只表现为
   "截图里没有窗口"，差点被当成截图脚本的毛病——真正的堆栈是去
   `Get-WinEvent -LogName Application`（找 `.NET Runtime` 那条）拿到完整栈才定位的。
   **进程没了 = 你的日志也跟着没了**，别对着"窗口怎么不见了"猜；先去操作系统那层把崩溃栈捞出来。
   （Linux 侧对应 `journalctl` / `coredumpctl`。）

（现场与修都在 UI 侧，2026-08-25 由接本地模型那条线发现并修复；本条按实际因果记，
并发预取只是把概率推到必现的一半原因。）

### 4.32 ⚠⚠ 标签说读了、内容里没有、判据说这一格过了——三件事可以同时成立

诊断技能包里那一步写的是
`new ToolStep("graph.read", """{"detail":"summary"}""", "方案结构与禁用节点")`——
**没有 `solutionId`**。而 `graph.read` 留空 Id 走的是"返回方案清单"那条分支。
存档里那次调用的原文是：

```json
"input":{"detail":"summary"},
"result":{"data":{"count":0,"solutions":[]},
          "evidence":[{"fact":"工作区共有 0 个方案","rawReference":"solution://"}]}
```

标签说的是「方案结构与禁用节点」，事实说的是「共有 0 个方案」。
**十条评测场景全绿，而没有一条里模型见过一个节点。**

配套那格判据也是空的却绿着：`ToolUsedRule(criterion, "graph.read")` 只查
"这个工具调过且成功"，返回空清单照样满足。
而**同一个文件里另一条规则的注释自己写着**「判据绑在**资源**上而不是工具名上，
是这套设计能长期不改判据的原因」——这一格没照做。

⇒ 四条：
1. **三处各自看都像对的**：预取步骤的标签在提示词里、返回内容在工具结果里、判据在验证器里，
   **没有任何一处同时看得见另外两处**。这类洞不是靠仔细看单个文件能发现的，
   要靠"把这三处摆在一起对一次账"——而摆在一起的机会通常只有一次：读存档。
   ⇒ **新加预取步骤时，读一次它在存档里的真实返回**，别信标签。
2. 判据从工具名换成**资源实例**：`scheme://`（这一类）与 `scheme://<某个 id>`（某一个）必须分开，
   否则"列了一下"和"读了它"还是同一件事。
3. 与 §4.17 同族但更隐蔽：那条是判据选在下游，
   这条是**判据选在"动作发生过"而不是"事实到手了"**。前者能靠读链条发现，后者不能。
4. **顺带一个死字段**：`DiagnosticTask.Scope` 声明了、全仓库零消费者，
   于是模型压根不知道现在打开的是哪个方案。同 `ICameraProvider` 那次。
   ⇒ **契约里加了字段就得当场加一个消费者**，否则它会以"看起来支持"的方式误导下一个人。

### 4.33 ⚠⚠ 变异检查自己也会漏——它证明"期望改错会红"，不证明"期望写对了"

评测套件里那条变异检查（把某条场景的期望故意改错，要求必须变红，见 §5.3）挡住了
"永远给满分的评分卡"。但 2026-08-26 加 `ui://` 场景时，它**没有挡住另一种**：

判据写的是「证据里要有 `ui://current`」。而**没有界面在跑时那条资源照样出证据**——
它如实报告"这一轮没有界面"，`rawReference` 也照样是 `ui://current`。
于是**把界面接线整个拆掉，那条场景依然是绿的**：
它验的其实是"这个地址读得动"，不是"读到了界面"。

而变异检查为什么没抓到：它改的是**期望的值**，而这里**期望的值没写错，只是写得太松**。
两种错完全不同——一个是"写反了"，一个是"写了一个恒真的条件"。

⇒ 三条：
1. **来源前缀只能说明"这一类资源被读过"。** 要区分"读到了什么"，得看**正文**。
   补了一栏 `RequiredFacts`（某条证据的事实句里要出现某个片段）。
   它是评分卡里唯一看自然语言的判据，而这不违反"判分不看模型说了什么"——
   它看的是**工具产出的事实句**（确定性代码写出来的字符串）。
   ⚠ 拿它去卡模型的措辞就跑偏了，那会变成按文采计费。
2. **一个恒真的判据和一个没有判据，在报表上长得一样，而前者更糟**——它占着位置，
   让人以为这件事被验过了。同 §4.21 那条"不完整的清单比没有清单更糟"。
3. ⇒ 加新场景时**手动拆一次接线**看它红不红，成本一分钟。
   自动的变异检查覆盖不了"判据写松了"这一类，因为它不知道什么叫"松"。

### 4.34 ⚠ 模型看见了新信息，不等于它会用——确定性推论要下沉，别指望措辞

`graph.read` 改成读画布上那份之后，本机 `qwen3:8b` 的回答里确实出现了
「找圆节点已被禁用」——**那正是画布上那份独有的信息**（磁盘那份里它是启用的），
说明新接的这条数据真的到了模型手上。

但它**没有**把这件事和"所以这次跑的不是你改的那版"连起来。
而现场问的整句话就是「我改了怎么还是老样子」——**那一句才是要回答的问题。**

⇒ 三条：
1. **"信息到了"和"结论出来了"是两件事**，验收要验后者。只看"模型提到了新事实"会误判成成功。
2. 这是个**确定性推论**：没落盘的改动，任何一次执行都不可能跑到它。
   属于该下沉的那一层（原因由规则给，不由模型给）。落成 `vision.unsaved-canvas-change`。
   推论**刻意不依赖版次号**——保存不改版次（只有发布改），两个号相等也说明不了什么；
   真正成立的那句话更简单。
3. 同一轮里还有一段提示词（「结论说给站在哪一页的人听」）**两次跑出两种结果**：
   一次完全没提页面，一次写全了"人当前在「流程编辑」页，选中的是「找圆」节点（已禁用）"。
   ⇒ **一次观测到不等于稳定行为**，所以它留在插件的提示词段里，
   没有下沉进原生核心（那要两个平台重编）。与之对照，第 2 条那个结论由规则给出，两次都在。

### 4.35 ⚠⚠ 机制做出来了、装载记录也算出来了，但界面上一个字都没有——"装上了"和"根本没装上"于是长得一模一样

第二类插件（算子自带的参数界面）做完的第二天，现场只回了一句：
**"我没看到界面插件标签页"。**

按真输入查了一遍，每一环都是好的：插件从目录装上了、双击画布节点确实打开设置窗口、
那一页确实由插件画。**问题在于它只出现在"双击才打开"的那个窗口里，而人在流程编辑页上**——
那一页上没有任何一处说得出"这个算子有没有自带界面"。

更值得记的是第二层：装载过程的记录（`Notes`：装上了什么、跳过了什么、为什么）
**当时就算出来了，算完扔了**。于是三种状态在屏幕上完全同形：
插件装上了、插件没装上、这个算子本来就没有自定义界面。
而**同一个软件的另一半早就把这件事做对了**——内核插件的跳过与失败在扩展页上
和装上的一样显眼，理由当年写得很清楚："现场最常见的问题不是插件坏了，而是以为装上了"。
新机制没有跟着那条规矩走，**而没有任何东西提醒过我们**。

⇒ 四条做法（后两条是可复用的规则）：
1. 出处要**点名是哪个文件里的哪个类**（"由界面插件提供：`X.dll` → `YProvider`"）。
   只说"由插件提供"的话，装了两个插件时人还得自己猜是哪个在起作用。
2. **会因插件而变假的话不要写死在标题里**。那一栏原来叫「参数（由 schema 生成）」——
   插件接管时它就是一句假话。出处挪进一行跟着选中项变的小字。
3. **凡是"在不在起作用"由插件或配置决定的功能，界面上必须有一处说得出这一刻它在不在、由谁提供。**
4. **装载记录一律显示出来。** 算出来的诊断信息扔掉，等于把三种状态压成一种。

⚠ 这是[§4.14](#414--解释存在只是不在人所在的地方一天撞了五次)那个形状的**第三次**
（第二次是"给人做了、模型看不见"）。三次的根因同一句：
**功能与"谁能观测它"是两件被分开做的事。**

### 4.36 ⚠⚠ "点一下不动"和"点一下抖两像素"是两种手势——第一版手势判据抓不住它要防的东西

给工具箱加"拖到画布上"时，最怕的是顺手弄坏已有的双击添加
（按下就捕获指针的实现会让树上的选中与双击一起失灵）。
于是写了一条判据：真双击工具箱里的算子，节点必须照样加进去。

**它是绿的——而把实现改成"按下就捕获"之后，它还是绿的。**
原因：判据里两次点击都按在同一个像素上，而拖动要过阈值才开始，
所以那条路根本没被走到。**真手会抖一两像素。**

补两样之后两种变异（按下就捕获 / 阈值改成 0）都变红了：
① 按下与松手之间插一次 1–2 像素的移动；
② 除了"节点加进去了"，还断言**不许出现「松手在画布外」那句话**——
有它就说明这两下被当成了拖动。

⇒ 三条：
1. **手势判据要模仿手，不要模仿理想输入。**同一像素、零抖动的点击在真实世界里不存在，
   而"不存在的输入"上的绿灯什么也不证明。
2. 一条手势判据往往要**两个断言**：该发生的发生了，**并且不该发生的没发生**。
   只断言前者时，"两件事都发生了"照样绿。
3. 顺带一个平台坑：无头会话那几个鼠标辅助方法的**修饰键默认为空**，
   所以 `MouseMove` 不带"左键按着"时，"按着拖"和"松着划过去"一模一样——
   拖放整条路一次都没被触发，而失败信息只说节点数不对。

### 4.37 ⚠ 又一次差点把推断写成选型依据（限制性断言，第三次）

在"平台拖放（`DragDrop.DoDragDrop`）"和"自己用指针捕获"之间选时，
本来打算把这句话写进代码注释当依据：**"DoDragDrop 在无头会话里根本起不来，
所以那条路测不了。"**

按[§4.24](#424--限制性断言写进代码注释时最危险因为它紧挨着一段正确的规矩)那条规矩去测了。
探针：按下时调它、再分 20 步移动并松手。结果是
**调用时 `WaitingForActivation`，松手后 `RanToCompletion`，结果 `None`**
（探针那个落点没登记 `AllowDrop`，所以 `None` 是对的）。
也就是说**无头会话里有平台拖放源，那条路同样测得到**。

选型没变（自己画的跟手标签两平台一样、落点/阈值/捕获三样都在自己手里），
但**依据换了**：从一条编出来的限制，换成两条真实的取舍。

⇒ 这是同一个形状的第三次（"两个库无法共存"、"相机那组参数读不回来"）。
三次的共同点：**那句限制不是结论，是被拿去当前提的东西**——
它会去给别的判断做担保，而担保是假的。
成本上它便宜到没有借口：这一次的探针连同结论一共二十分钟。

### 4.38 ⚠⚠ "值没变也算改了" —— 一句判断缺失，把布局推成死循环，而症状是"卡住"

界面编辑页做完，加一个控件，**整页布局停不下来**：无头会话里 `RunJobs` 一直转，
测试进程挂几分钟直到被杀。

根因这一句：属性栏里的数值框**在布局期间会自己发一次 `ValueChanged`**
（值经过一次格式化往返），而处理器把每一次 `ValueChanged` 都当成"人改了一个值"，
于是标脏 → 重画整块画布 → 布局再跑一遍 → 再发一次。

⇒ **闸门在"这次到底改了没有"这一句上**：新值和模型里那份相等就什么都不做。
同一条要在每个编辑器上都写（数值、文本、开关），而现值必须**每次现读**，
不能捕获创建时那一份——拖动控件也会改坐标。

三件值得单独记的：

1. **这不是测试的毛病。** 真软件里就是"加一个控件，界面卡死"。
   而症状（"卡住"）和"测试环境慢""无头会话本来就慢"长得一模一样——
   第一反应是后者，差点按后者处理。
2. **定位它靠的是二分 + 文件日志**，不是读代码。
   卡住的进程什么都不打印，所以把进度写进一个文件、每步一行，
   然后逐段砍：控件单独放窗口里 → 好；放进"固定大小 Border + Canvas + ScrollViewer" → 好；
   放进页面 → 卡。再砍页面：不建属性栏 → 好。范围就剩下属性栏那几个编辑器。
3. **同一族还有两个**，都在这一轮里：重画时给列表设选中项 → 列表发"选中变了" → 又调重画
   （第一版直接栈溢出，退出码 -1073741571）；以及"在自己的事件里把自己所在的子树重建"
   （无头会话报 `You've caused dispatcher loop`，真软件里的表现是**打一个字光标跳回开头**）。
   ⇒ 三个都是**回调里改自己**的形状。UI 代码里这类回路有三种闸门可用：
   值相等就返回、重入标志、以及"只在真正需要时才重建那棵子树"。

### 4.39 ⚠ 坐标换算不知道"被裁掉了"——落点判断要连可视区一起判

界面编辑页的画布比可视区大（屏 1280×800，中间那栏只有八百多宽），所以外面套了滚动条。
把控件从控件库拖到**右边属性栏**上松手时，控件被加进去了——加在 x=1123，
一个**滚出去看不见的位置**。

`TranslatePoint` 只做坐标换算，它不知道那一点已经被 `ScrollViewer` 裁掉了。
所以"这一点在不在画布上"这个判断，**要连可视区一起判**：先看点落没落在可视区里，再换算。

⇒ 一般化：凡是**内容比容器大**的地方，"命中"有两个含义——落在内容的坐标范围里，
和落在人真能看见的那一块里。要的是后者。

### 4.40 ⚠⚠ "模型能不能读到 X" —— 先确认 X 存在，否则会做出一个如实报告"不存在"的接口

现场问："界面用了哪些控件插件、**控件插件和流程模块的关联逻辑**、控件的设置，
这些大模型都能知道吗，我希望大模型都能知道。"

查下去，三件里的真实状态是：

| 问的 | 真实状态 |
| --- | --- |
| 用了哪些控件插件 | 半个：只报类型键，不说谁提供、也不说"根本没插件提供它" |
| 控件与流程模块的关联 | **压根不存在**——控件只看整条流程的最终判定 |
| 控件的设置 | 数据里有、事实里没有（而模型主要读事实） |

⇒ 第二件不是"模型看不到"，是**这件事还没有**。
如果按"让模型读到"去做，会做出一个如实报告一个不存在的关联的接口——
它能通过所有判据，而现场第一次用就会发现屏上摆不出两组灯。

**一般化：凡是"模型能不能知道 X"的问题，第一步是问"人能不能做 X"。**
两者的工作量差一个数量级，而问句长得一模一样。

顺带两条做法上的结论（都可复用）：

1. **系统级语义不要让插件各定一份。**"这一块显示谁的结果"和限值同族——
   让每个插件自己定义一个"节点名"属性的话，外壳就答不出"这一屏和流程是怎么对上的"。
   插件只回答"我需不需要绑"。
2. **给模型的事实要用人话，不要用键值对。**"显示几件：8"而不是 `count=8`——
   人在属性栏上看到的就是前者，两边看同一份才不会出现"模型说没问题、人一点就不对"。

### 4.41 ⚠⚠ 接上了不等于用得上：8B 拿到新事实前，先看它会不会去取

facts 接好、判据全绿之后，拿本机 `qwen3:8b` 真问了一句
"屏上那排灯显示哪个模块、由哪个插件提供、还能调什么"：

- **第一轮（任务不带预取）：一个工具都没调**，直接答"需要进一步调查，建议人工检查界面配置"。
- 把那个地址加进技能包的**开场预取**之后，**第二轮答对了三件事并引了证据**。

这是 DiagAgent 那条核心结论的又一例：**"要不要调工具"这件事本身不能交给模型决定。**
⇒ 新增一个模型该知道的事实源时，验收要走两步：
① 判据证明"读得到"；② 真模型证明"会去读"——而②的答案往往是"不会，除非你替它取"。

⚠ 中间还抓到一处**只有真模型那一轮才会露头**的账：第一条技能（最常用的那条）
**自己手抄了开场那几步**，于是往共享的 `Opening` 里加东西时唯独它没跟上。
那一轮模型的工具清单里没有新地址，于是它拿别处的事实硬凑了一个答案
（把 URI 当成插件名，把算子参数当成控件设置）——**幻觉是缺证据的下游症状，不是模型的毛病**。
**抄一份和引用一份的区别，在加第三步的那天才会显形。**

### 4.42 ⚠⚠⚠ 尺子自带答案：评测抄了一份产品的配置，于是"满分"量的是抄的那份

紧接 4.41。把三个新事实源接进技能包的开场预取、判据全绿之后，按惯例跑一次真模型评测收尾：
**16/16 通过、必要证据覆盖率 100%、达到 Phase 1 验收线**。

**然后翻了一眼那一轮真调了哪些工具**（`events.jsonl`）：**只有 5 条**，
当天加的三步一条没有，其中一个地址从 24 小时前起就一直没进过评测。

根因在评测这边：场景库里有一份**手抄的预取清单**，11 条场景共用它，跑的时候照这份跑。
产品的技能里加什么都进不了评测。**而"达到 Phase 1 验收线"这句话，正是用来宣布阶段达标的那句。**

⇒ **和 4.41 是同一形状，只是高了一层——这一层是尺子。**
4.41 里"抄一份"的代价是一条技能落后；这一层的代价是**尺子和被量的东西一起动**，
于是没有任何东西会变红。

**修法：把口子拆掉，而不是补抄。** 场景现在**没有**"整份写死清单"这个属性，
只能在真清单上 `减`（去掉刻意不查的几步）和 `加`（插入一个坏工具/越权工具）。
抄一份在结构上就不可能——比"再加一条测试查有没有人抄"更省事，也更难绕。配套两条：

- **减不掉要报错**：想减的那一步在产品里已经改名或删了，
  那条场景会**悄悄从"刻意少取一项"退化成普通正例**，而它本来是专门抓
  "证据不全时会不会改口说没问题"的。
- **产品每一项都要有人量**：加一条守卫"每个技能至少有一条场景指着它"——
  没人指的技能，它的预取一次都没跑过，而总分照样满（两次变异都变红）。

⚠ **接下来是这一条最值钱的部分：抄的不止清单，还有"期望"那一栏。**
换成真清单之后先掉到 **14/16**，掉的两条**方向相反**：

| 表面 | 真相 |
| --- | --- |
| 场景要求两个来源，真清单里没有 | **评测要错了**：那两条是跟着抄的清单来的（同一串前缀在 11 条场景上逐字重复），不是这个故障需要的 |
| 另一条场景同样要求某个来源 | **产品缺了一步**：那条场景的立意写着"考的是不会顺手把 X 也判成有问题"，而**要凭证据排除 X，就得先读过它**——那条技能一眼都没看，于是"没冤枉 X"是靠沉默做到的 |

⇒ **抄一份的代价是双向的**：产品加了什么，评测看不见；产品不需要什么，评测照样要求。
**只盯着前一个方向，就会把后一个方向的红当成"期望是对的、产品退步了"而去改产品。**

第二条还顺带露出一个更实的洞：技能是**按现场那句话**选出来的，而现场那句话经常不准——
人说"下游收不到结果"，真实原因可能是上游根本没在出图；技能不读上游，那种工单会被整轮查错方向。

**可操作的两条：**

1. **报满分之后一定要看一眼工具调用清单。**分数不告诉你它量的是哪一份配置。
   这一次"翻一眼 `events.jsonl`"花了不到一分钟，抓到的是三天的假绿。
2. **验收物不许持有产品配置的副本。**要量什么就从产品那一份读出来，
   差异只能表达成在那一份上加减。

实测：Windows 734 通过 / 9 跳过、Linux 727 通过 / 16 跳过（743 总，四步全绿）。
真模型 `qwen3:8b` 三次：5 步预取 16/16（假绿）→ 8 步预取 **14/16**（两个发现）→
8 步预取 16/16、必要证据 42/42、路由 16/16、144.2 s。
（重复调用 0→2，是模型在追问轮自己重读，不是预取重复取——算得出来：14 次调用里 8 次是第一轮预取。）

### 4.43 ⚠⚠⚠ 功能"做了、接上了"，却在中间某一层被扔掉——而两头都没人报警

2026-08-28：产品把诊断助手的要求说全了（结论要有依据、每次判断留文档、判不了交给高级工程师、
用户画像是**现场操作员**、无先后的动作一次一件、有先后的一次不超过 N）。
对着实际状态查一遍，四条要求**各差一截**，而差的位置分三种形状：

| 要求 | 实际状态 | 形状 |
| --- | --- | --- |
| 结论要有依据 | 命中的原因确实带证据编号（内核有硬判据），但报告里**只有编号**，复核要另开另一个文件；而且**没有任何东西校验编号解析得回去** | 做了一半，**缺的那半是"给谁看"** |
| 留文档给人复核 | 报告**已经每轮都落盘一周了**，而界面上一个字都没有、也没有可读地址 | 算出来了，不在人所在的页面（这个仓库第四次） |
| 判不了交给工程师 | 没有这个东西 | 真的没做 |
| 一次给几个动作 | 规则里写了"下一步建议"，而**中间那层把它扔了** —— 从来没有一条建议到过现场 | **接上了、然后在中间某一层丢失，两头都没人报警** |

⇒ 第四行是这一条要记的形状。它比"没做"更难发现：**上游有**（规则里写着）、
**下游要**（现场问的就是"我现在做什么"），中间那一层（把规则结论变成给人看的东西）
把它 drop 掉了，而两头都没有任何东西会红。
⚠ **判据**：一个"做了但没人用"的功能，去查**它的值最后落在谁手上**——
从产出的那一行代码，一路跟到人的眼睛。跟不到底，就是这条形状。

顺带记一句：那些"下一步建议"当时是**一句话三个动词**
（"到某页看状态，必要时重开；重开会把参数写进设备"）。对操作员而言，
一句话三个动词的实际效果是**三件事做了一件半，而没人知道是哪一件半**——
而"哪一件起了作用"恰恰是下一轮诊断要用的证据。⇒ 一条动作只放一个动词，
一次只发能承受的量（无序 1 条、有序 ≤N），**N 放配置里，让现场自己调**：
那个数的正确值不在代码里。

### 4.44 ⚠⚠ 一个断言分成两档之前，先想清楚"违反它的人是谁"

同一天的第二个坑，代价是**评测里 16 条场景全红**。

产品要求是"每次诊断的结果需要有实际的依据"。落地时报告里做了两件事：
① 结论引用的证据编号解析不了 → 显眼报出来；② 排除（"证据表明不是它"）没有依据 → 同样显眼报出来。
第二条一上，**整套评测全红**——而红的原因是：契约里那个"不命中"的单例
（`CauseVerdict.No` 这种）**本来就不带证据**，第三方规则用它是完全正当的：
很多排除靠的是**否定事实**（"这一类资源一条都没报异常"），没有哪一条证据单独支撑它。

⇒ 分成两档：**结论**没有依据是硬红线（它在断言"就是这个原因"）；
**排除**没有依据只写一句"规则没有给出排除依据"。
⚠ 一般化的判据：给一条断言定级之前，先问 **"违反它的人是谁"**——
如果答案是"正当使用契约的第三方"，那这条断言的级别定错了，
而症状会是"我们自己的验收全红，红的却是别人的代码"。

（同时记一条正向的：**排除也是判断，判断要有依据**。在这之前规则判"不是它"什么都不留，
于是"查过并排除了"和"根本没查"在报告里长得一模一样——而复核的人第一个问的就是
"为什么不是 X"。让排除也带上依据、也进事实流，这一节才有意义。）

### 4.45 ⚠⚠ 变异检查的还原手段，必须对**未入库文件**也成立

同一天第三个坑，而且它让一整轮变异检查的结论**全部作废**。

变异检查脚本用 `git checkout -- <file>` 还原每一次变异。这一轮新写的几个文件
**还没入库**，于是 `git checkout` 报 `pathspec did not match any file(s)`——
而脚本没看那个退出码。后果不是"没还原"这么简单：**变异叠加了**。
从第三条起每一条都"红"，因为前两条的破坏还在。屏幕上是一排整齐的 `[红 ✔]`，
**而那个红毫无意义**。

⇒ 三条：
1. 还原用**文件内容备份**（跑之前把每个目标文件的内容读进内存），不用版本控制命令；
2. 每轮变异后**必须验一次"还原后是绿的"**——这一条本身就能抓到叠加；
3. 脚本里每个还原动作都要看退出码（这和 4.20「构建结果要按配置分别报」是同一个毛病：
   **没看退出码，于是拿旧状态当新结论**）。

⚠ 顺带又踩了一次同源的坑：实验时把 `dotnet run` 的输出 `>/dev/null 2>&1`，
于是**构建失败被藏起来**，几次实验其实跑的是旧 dll，而我据此得出了三个错误结论。
"藏输出"和"不看退出码"是一回事。

### 4.46 ⚠ 无头 UI 测试**按位置**找控件，会在加一块界面的那天悄悄指向别处

对话记录那块的取法是"这一页上**第一个只读文本框**"。这一天在它上面加了一块
「现在请做」（也是只读文本框）之后，那个取法**指到了新那块上**。
运气好的表现是超时（等的字永远不出现）；**运气不好的表现是读到了另一块的内容然后通过**。

⇒ **位置不是身份。** 给要断言的控件起名字（`Name`），测试按名字找。
这一条和 4.36「点一下不动 vs 点一下抖两像素」同源：**测试的取样方式本身也是一段会过期的假设**。

### 4.47 ⚠⚠⚠ 同一句抱怨问了三次，三次的根因完全不同——"判不了"是一句谁都会说的话

现场指着屏幕上那句"判不了，缺少执行轨迹证据"问了三次。三次都改了东西，
三次那句话原封不动地回来了，而**每一次的根因都不一样**：

| 第几次 | 真正的原因 |
| --- | --- |
| 一 | 两条规则对着同一份事实各说各话（"流程从未跑过"命中，另一条说"还缺执行轨迹"） |
| 二 | 上一条修复**根本没进他跑的那份二进制**（软件开着、dll 被占、我换了输出目录绕过去） |
| 三 | 规则判出了三条、验证过了、停机 `Completed`，**而模型从来没被告知规则判出了什么** |

第三次的形状最值得记：**harness 只往模型送"还缺什么"（验证反馈），从不送"已经判出什么"**。
模型于是照着自己上一轮的措辞继续说——而**屏幕上最显眼的正是它那句话**。
存档里事实链完全正常（`Kind=Causes` 三条命中、缺证据为空、停机 Completed），
"规则那一侧对了"和"人看到的对了"是两件事。

⇒ 判完就把结论与"已排除"清单送给模型，写明"原因由规则给，你不用再推"。
**这不违反"模型不推理原因"**：原因仍只由确定性规则产出，模型只是被**告知**结论。
不告诉它，等于让它去猜一件已经有答案的事。

**一句抱怨反复出现时，不要假定根因还是上次那个。**"判不了"是一句能被
规则矛盾、部署没生效、结论没传达三种完全不同的故障说出口的话。

### 4.48 ⚠⚠⚠ 告诉模型还不够：8B 照做的是**最后读到的那句指令**

把结论送过去之后，19 条评测场景全绿，**而逐条翻最后一句才发现**：
`camera-not-grabbing` 里规则判的是"相机没有在正常出图"，
模型对现场说的却是"画布上的改动还没保存"——**那是判不了的一条**。

原因很物理：送过去那段话里"命中的"在前、"判不了的"在后。
点名之后仍有 3/19 最后一句在讲判不了的那几条，
其中一条更直接：**它把我写在指令里的例句"这条还没查清"整句当成了回答**。

⇒ 三步，每一步都是上一步实测之后才发现还不够：
1. **告知**结论（只在结论变了时说一次，去重键用"哪几条规则各什么状态"，
   不用带证据编号的全文——用全文的话每取一条证据就算作"结论变了"）；
2. **点名**要说哪一条，而且**放在最后一句**（先前收尾是"还缺证据的那几条才需要你去取"）；
3. **停机前固定问一句收尾**并把要说的那条点进指令、不给工具
   （这一句原来只在"人问了没人答"时才问）。

实测轨迹：该项 13/17 → 14/17 → **17/17**；模型发言中位 65 → 59 字、最长 169 → 95 字。

**给小模型的指令，位置和措辞都是行为的一部分，不是文风。**
写例句要当心：它会把例句原样交回来。

### 4.49 ⚠⚠⚠ 评测量的是规则，人看到的是模型那句话——中间那段真空能一路满分

这一轮加的那条量叫 `RetoldTheRuledCause`：模型自己下的那个结论，
说的是规则**判中**的那条，还是**判不了**的那条。

它填的是一个真空：原有的"根因正确率"量的是**规则**判得对不对，规则一直满分；
而现场看到的是**模型**那句话。两者之间**此前没有任何一条判据**——
于是"规则对、屏幕错"可以一路满分地通过，
和 4.42「尺子自带答案」是同一形状的第四次。

判法不抄产品文案（尺子不许自带答案）：把**产品自己给出的**原因句子拿来，
按二字片段与模型那句求重合，看命中的那几条赢还是判不了的那几条赢。

⚠ **这把新尺子自己也错了一次**：`follow-up-on-missing-evidence` 那条里
现场追问的正是判不了那条，模型顺着答**被判成"复述错了原因"**——
追问要什么答什么是对的行为，**错的是尺子**。⇒ 量的改成"追问之前它自己下的那个结论"。

⚠ 另一个口子：离线口径那个占位模型每轮只回一句固定话，按定义不复述。
把这条**量模型行为**的线塞进离线口径，会让它永远红。
⇒ 只在真模型口径上判分，**并加一条守卫盯着这个豁免口子别开大**
（变异："哪个口径都不判分" 必须红）——豁免一旦开大，这条线会安安静静永远绿着。

### 4.50 ⚠⚠ 判据的"取样装置"本身也会让判断落空：工具名错一个字母，两条变异同时装绿

去重那条判据第一版里，脚本模型调的工具叫 `echo`，而注册的叫 `test.echo`。
**每一次"调用"都是工具不存在**，于是规则一次都没被重判，
两条变异（不记上次说过什么 / 去重键用全文）**双双保持绿色**。

改对名字之后又发现两件事：**一直调工具的模型量不到**（规则只在"模型不再要工具"那一支重判），
**一直说话的模型也量不到**（证据不长，规则按证据条数早退）。
最后要一个**一轮取证、一轮说话交替**的模型才量得出来，两条变异这才变红（1 → 4 次重复）。

⇒ 变异检查抓到的两次假绿**长得完全一样**：判据通过、结论正确、**什么都没被量到**。
和 4.46「位置不是身份」同源：**测试的取样方式本身就是一段会过期的假设**，
而它失效时的表现是绿色，不是报错。

### 4.51 ⚠⚠⚠ "我改了颜色"不等于"屏幕上那块真的变了"——一轮里撞了三次，三次都只有真渲染的图能发现

现场给了一张参考图说"参考这个颜色搭配"。改配色的那一轮里，同一形状的错连着出现三次：

| 我改了什么 | 屏幕上为什么没变 |
|---|---|
| 样式里加 `MinWidth = 0`（按钮想贴着文字） | 每个按钮构造时写死了 120/140——**本地值压过样式** |
| 节点的 `Background` / `ContentBrush` 换成主题色 | 节点上那块 `45,45,48` 的中性灰来自**连接器自己带的底**，不是节点 |
| 词条里用 `**每轮**` 强调 | 界面是 `TextBlock` / 只读 `TextBox`，**不渲染 markdown**，两对星号原样显示给现场 |

三个都读代码看不出来：源码里"改了"是事实，只是**改的不是屏幕上那一块**。
第二条尤其典型——是在真渲染的截图上**逐像素扫了一行**（`407→462` 那一段还是灰的）才定位到连接器。

⇒ 做界面改动时起一条自查回路：**起真的软件 → 截它那个窗口 → 逐像素采色比对**。
（`GetWindowRect` + `CopyFromScreen` 只截窗口矩形，不截整个桌面；`SetCursorPos` + `mouse_event` 可以点页签，一次跑多张。）

⚠ 这条回路自带一个陷阱：编译时报 `MSB3027 文件被 HuikeAgent 锁定`。
**那不是障碍，是信号**——有人正开着它。要么关掉再编，要么明说"这次改动还没进到你跑的那份"；
**绝不换输出目录绕过去**（换了就等于让"给人用的那份"停在原地，代价是两轮白花的对话）。

顺带一条配色本身的结论：参考图逐像素采出来是 `24,24,28`（窗体边框/标题栏）、`35,35,36`（大图区）、
`40,40,44`（面板，占全图 238k 采样点）、`60,60,64`（面板标题条/选中行）——
**它的层次顺序和"面积越大越深"是反的**：外壳最深、工作面浮在上面。
我们原来那套让画布最黑、顶栏最浅，于是**最抢眼的一块是最不重要的那块**。

### 4.52 ⚠⚠⚠ "真的，但没用"：结论正确，却报到了链条的上一层

现场原话：**"为什么点取一帧，运行界面可以直接反馈 IP 不对，智能诊断却没有诊断到 IP 不对，只是回复未打开"**。

同一时刻，运行页状态栏写着
`打开相机失败：设备与主机的IP网段不匹配（IMV -107）`，
而诊断说的是「相机 cam-01 状态未打开，从未出过图」。后者**完全属实**，但：

1. 它停在现象的上一层（未打开 ← 为什么打不开）；
2. 它给的第一步动作是"到设备页点「打开」"——**正是刚刚失败的那件事**。

根因不是模型笨，是**事实里根本没有那句原话**：驱动的错误被包在返回值里 → 界面写进状态栏 → **然后就没了**。
诊断能读到的只有"相机此刻是关的"。

两处修法，第二处比第一处更值钱：

- **把原话记下来**：内核在生产写的漏斗上记一份流水（谁、什么时候、对谁、成败、**厂商原话**），
  经状态平面出去；规则把原话**原样**当原因报出来，处置标"要工程师"。
  ⚠ 不要指望插件填契约里那个 `LastError` 字段——填不填由插件作者决定，而出问题的往往正是第三方插件。
  **内核那一侧才是唯一必经的漏斗。**
- **有些事根本不用等人去点**：相机地址和本机网卡的网段都是现成读数，同不同网段是**一次减法**。
  加一个 `net://` 名词空间（每台设备一条：地址、同不同网段、同网段时 ping 一次）之后，
  这条原因在**任何人动手之前**就能报出来。

⇒ 排查"诊断说得不对"时，先分清是**判错了**还是**判在了上一层**。后者的表现是"这句话没错，但照它做没有用"，
而它的根因几乎总是同一个：链条中间某处**知道原因、显示了原因、然后把它扔了**。

### 4.53 ⚠⚠ 一份"整类报告"报了健康位，会污染所有按健康位取适用范围的判据

新加的那份生产写流水，第一版让"最近一次失败"报 `healthy = false`。看起来合理，实测两错：

- **语义**：流水记的是**过去发生过什么**，不是**此刻好不好**。那台设备可能已经修好、也可能早就不用了。
- **连带**：评测里"结论点名了是哪一台"那条量，适用范围**刻意不写死 scheme 清单**
  （写死会随插件变假），而是按"读出来 `healthy == false` 的那几条快照"划。
  于是这份流水一报不健康，那条量立刻开始要求模型说出 **"production-writes"** 这个词——
  而模型明明已经点名了 `cam-01`，却被判红。

⇒ `healthy` 只在资源**表达当下好坏**时给 true/false；清单、流水、汇总这类一律 `null`
（契约里那一档的含义就是"本资源不表达健康"）。
更一般的形状：**一个字段被别处当作"分类依据"在用时，给它赋值就不再是局部决定**。

同一轮里 `net://` 也因此改了形状：**一台设备一条地址**（`net://cam-01`），
而不是一份"所有设备的网络报告"——这样健康位说的就是那台设备，"点名"要求也自然对上。

### 4.54 ⚠⚠⚠ 尺子给自己打分：系统兜底补的那句，被当成了模型的成绩

harness 有一条兜底：收尾时模型不答，就按规则结论**自己补一句**（屏幕上必须有正确结论）。
补的那句同样是 `Assistant` 角色。

而评测里"模型复述的就是规则判的那条"量的是**最后一条 Assistant 消息**——
于是那几轮量的是**系统自己写的话**，必然一字不差，**白送一个满分**。

⇒ 只量 `Origin != Harness` 的那一句；兜底另有一条只报数的量。
这与 [4.42](#442--尺子自带答案评测抄了一份产品的配置于是满分量的是抄的那份) 是同一形状的另一面：
那次是尺子抄了产品的配置，这次是尺子把产品的兜底当成了被测对象的表现。
**判据与被判对象之间必须有真实的间隔**，而"兜底"最容易把这层间隔悄悄抹掉。

同一轮还打出两条相关的：

- **原因写得太通用时，靠改提示词让模型"记得点名"是治不住的。**
  通讯那条规则的原因是「结果没能发出去：通讯链路当前不正常」，8B 原样复述，"点名"判红——**它判得对**：
  现场看到这句仍然不知道是哪条通道。根因是**原因本身没有那个信息**，模型只能从别处捞，捞错比不说更糟。
  ⇒ 命中时把设备 id 写进原因。
- **收尾那句指令里，结论要压在最后一句。** 我在结论后面追加了一段"怎么说"的规矩，
  于是有一条场景连着两轮复述的都不是判中的原因，而是支撑证据里最显眼的那个现象。
  ⇒ 约束写前面、结论压最后，并明说"**只说这一条**，别的现象一个字都不要提"
  （同族见 [4.48](#448--告诉模型还不够8b-照做的是最后读到的那句指令)）。

### 4.55 ⚠⚠⚠ "枚举得出来"和"人建出来"是两种设备，硬做成同一个形状会留下一个永远返回空表的方法

相机接进来的路子是**枚举**：`ICameraProvider.DiscoverAsync` 去问总线上有什么，插上了就在、拔了就不在，
软件的活是发现它。通讯通道照抄这个形状抄不动——
**"连到 192.168.4.30:9000 的那个 TCP 客户端"不存在于任何总线上**，
没有任何发现动作找得到它，它只存在于人的决定里。

在此之前这件事的后果很具体：通道由插件在 `Configure` 里写死
（`channels.Add("plc-main", …)`，注册表只有 `Add` / `Ids` / `Find`），
于是**现场多接一台 PLC 的唯一办法是改代码、重新出包、拷到现场**——
而那是最常见的现场动作之一。

⇒ 通讯那边登记的是**工厂**（`ICommChannelFactory`：类型键 + 建它要填哪些参数 + `Create`），
不是 provider。硬要对称的话，工厂就得挂一个永远返回空表的 `DiscoverAsync`，
而**"为了对称而存在的空方法"会让下一个人以为通道也能被枚举出来**。

这个形状带出三条配套的东西，缺一条都会让"人建出来的设备"半途而废：

1. **清单要落盘，而且和方案分开。** 通道清单存 `config/comm-channels.json`（跟着**工位**走），
   参数复用设备参数那份存储（按 `comm://` 分节）。混进方案文件的后果很具体：
   换一个方案就把 PLC 地址也换了。
   ⇒ 推论要主动说出口：**方案拷到另一台机器上，通道要重建**——
   所以算子报"找不到通道"时把"现有的通道有哪些"一起列出来（人这时停在流程编辑页，手上只有这一句话）。
2. **开机恢复失败要出报告，并且贴到人所在的那一页。** 最典型的失败是"提供这个类型的插件没装"
   （换了台机器、包没拷过去）。静默跳过的话，屏幕上的表现是**通道列表里少了几条**——
   和"从来没建过"长得一模一样。同 [4.14](#414--解释存在只是不在人所在的地方一天撞了五次) 那一族。
3. **人能建的类型，模型要读得到，而且是同一份。** `comm://@types` 与设备页下拉框都问
   `ICommChannelRegistry.Types`。各算一次的话，"模型说可以建 Modbus、人打开下拉框没有那一项"
   会变成常态争议。

代价照实记：给第三方实现的接口新增方法是破坏性变更，**内核契约 7 → 8**。
这是第八次递增，而**连续为设备面递增说明设备那一块的抽象还没稳**——
第三种设备（串口）进来时要复核一次：provider 与 factory 该不该合并成一个概念。

### 4.56 ⚠⚠⚠ 那个口子"早就有了"，只是从来没人往里传——测试里通，真软件里永远是 null

`NodeExecutionContext.Services` 这个口子存在很久了，算子按契约就该从它取插件登记的服务。
写新算子时我照着契约用了它，单元测试全绿。

而 `HuikeHost` 建 `PipelineRunner` 时**从来没传过服务面**：

```csharp
var runner = new PipelineRunner(factory.CreateLogger<PipelineRunner>());   // 改之前
```

于是这条路**在测试里通（测试自己构造上下文、自己塞服务），在人跑的那一份里永远是 null**。
表现会是"这个节点在我机器上好好的、装到现场就说找不到通道"。

⇒ 判据不能只对着契约写，**要对着装配好的宿主问一句**：
`TheRealHostGivesNodesTheServiceProvider` 直接读 `host.Runner.Services`。
为此把那个字段公开了——公开一个属性只为让判据问得出来，是划算的。

这和 [4.43](#443--功能做了接上了却在中间某一层被扔掉而两头都没人报警) 是同一形状：
两头都对（契约有这个口子、算子按契约取），断的是中间那一节，而**两头都不会报警**。
区别在于 4.43 是"算出来了没人用"，这条是"用的人拿到的一直是空的"。

### 4.57 ⚠⚠ "拒绝"和"超时"是两种处置，而默认超时短于操作系统回 RST 的延迟时，前者会被报成后者

TCP 连接失败要分开报：**拒绝**说明网络是通的、去看对端那个程序；**超时**才是去查网段。
错误码按这个分了（`TCP.CONNECT.REFUSED` / `TCP.CONNECT.TIMEOUT` / `HOSTNOTFOUND` / `UNREACHABLE`）。

判据第一次跑就红了：连一个**关着的回环端口**，期望"拒绝"，拿到的是"超时"。
一开始怀疑是自己的 catch 顺序写反了。实测（Windows 10 LTSC 开发机，2026-09-01）：

```
ConnectionRefused after 2092ms
```

**这台 Windows 上连一个关着的回环端口要 2.1 秒才回 `ConnectionRefused`**（Linux 上是毫秒级）。
判据里连接超时给的是 2 秒——超时先到，于是一次拒绝被如实地报成了超时。**代码是对的，尺子太短。**

⇒ 两件事各归各位：判据把超时放到 8 秒（并把**为什么是 8** 写在旁边），
产品那边默认 3000 ms 够用，但**这条延迟本身要写进 `KNOWN-ISSUES.md`**——
现场把超时往下调到 2 秒时，症状会变成"明明是对端没开，报的却是超时"，
而那时没有任何地方解释得了。

更一般的：**分类的精度受限于观测窗口**。分得再细，只要窗口比现象出现得早，
细分就会退化成一档——而退化的方向恰恰是最没有信息量的那一档（"超时"）。

### 4.58 ⚠⚠ 两个默认值在常见情形下等价、在边缘情形下一个静默出错——那就不该选出错的那个

数据读写算子的编码默认给了 `ASCII`（读码器、上位机协议多数是 ASCII，看起来合理）。
判据里用中文变量名试模板展开，拿回来的是：

```
Expected: "{没这个变量}"
Actual:   "{?????}"
```

ASCII 把中文**静静地换成问号**，不抛、不警告。而这条报文发到对端**看起来是发出去了**。

关键不在"ASCII 不支持中文"（那是常识），在于**这两个默认值不对称**：
UTF-8 在纯 ASCII 内容上产出的字节**和 ASCII 一个字节不差**，
所以选 UTF-8 在常见情形下零代价、在边缘情形下不出错；选 ASCII 只有下行风险。

⇒ 默认值改 UTF-8。判断规则记下来：
**两个候选默认值在主流情形下等价时，选那个在边缘情形下不静默出错的**——
"更贴合领域习惯"不构成理由，因为它换不到任何实际差别。

### 4.59 ⚠⚠⚠ 手写的"被测清单"会和产品分叉——尺子那一族的第三例，而这次它连"漏了谁"都不会说

翻译覆盖率那把尺子从一张**手写清单**取被测对象：

```csharp
private static IReadOnlyList<IHuikeExtension> BuiltInExtensions() =>
[
    new Vision2DExtension(), new DevicesExtension(), new DiagnosticsExtension(),
];
```

清单上方还写着"**新增内置插件时要加到这里**"。而这行注释拦不住任何事：
加了插件忘了加进清单，那个插件的**全部译名一条都不会被查**，覆盖率照样报绿——
表现是**英文界面上那个插件整块是中文，而 CI 全绿**。

⇒ 加一条守卫，拿**部署出来的插件目录**逐个比对那张清单
（`TheBuiltInListCoversEveryDeployedPlugin`）：漏一个就变红，并点名漏了谁。

同一轮还撞到这族的另一面：`RecordingExtensionBuilder` 只接住"往注册表里 `Add` 的设备实例"，
而通讯插件**一条通道都不 `Add`**（它只 `AddFactory`，通道由人建）。
于是一个参数表十几项的插件，在覆盖率眼里等于**零条待翻**，然后报"全部翻好了"。
⇒ 记录器要接住工厂，覆盖率要把**通道类型**的参数也算进去。

三例放在一起看（[4.42](#442--尺子自带答案评测抄了一份产品的配置于是满分量的是抄的那份) 抄配置、
[4.54](#454--尺子给自己打分系统兜底补的那句被当成了模型的成绩) 量兜底、这次漏对象），
共同的形状是：**尺子和被量的东西之间缺一条"你有没有把它全量到"的元判据**。
前两例至少还量了东西，这一例最阴——它**连自己漏了都不知道**，因为漏掉的对象根本没进过视野。

### 4.60 ⚠⚠ 一个工作区里两个会话在同时改：提交要按 hunk 拆，而"整文件提交"看起来完全正常

这一轮全程有另一个会话在同一个工作区里改别的功能（诊断那一侧）。
到提交时，四个文件是两边都动过的（`MainWindow.cs` 一个文件里 20 段改动，我的只有 4 段）。
`git add <文件>` 会把对方**没写完**的改动一起提交进去，而提交本身不会有任何异常。

⇒ 按 hunk 拆。可行的做法（`git add -p` 在这个环境里用不了）：

1. `git diff -- <文件>` 拆成 hunk，按内容认领；
2. 每个 hunk 单独写成一份补丁，**自下而上**逐个 `git apply --cached --recount`
   —— 顺序很关键：先贴后面的，前面那些 hunk 的行号才不会被挪动
   （一次性合成一份只留自己 hunk 的补丁会失败，因为丢掉的 hunk 让后续位置全偏）；
3. 提交前机检一遍：**我暂存的那部分有没有引用只存在于对方未暂存改动里的标识符**。
   没有这一步，拆出来的提交可能自己编不过。

另外两条同源的注意事项：

- **分支是整个工作区共享的。** 按规矩从 `main` 切了新分支之后，
  另一个会话也站到了这条分支上——这件事要主动说，不能默默切走。
- **脚本回写文件会带进看不见的改动。** 我有几处用 Python `utf-8-sig` 读写改文件，
  于是给 **10 个原本没有 BOM 的 `.cs`** 加上了 BOM。
  diff 里表现为第一行整行变更，混在正常改动里毫不起眼。
  ⇒ 提交前对着 HEAD 比一遍首字节；能用精确替换就别整文件回写。

### 4.61 ⚠⚠⚠ 版本号是代理指标：一次加法式升版，把磁盘上整个第三方生态判死了

现场发来一张设备页截图：**5 个第三方插件全红**（`HK.Plugin.ContractMismatch`）、
「没有任何厂商相机来源登记进来」，而流程编辑页里算子好好的——于是那句问话：
"这些插件没注册上吗，我看流程编辑里又有"。

两边不一样是因为：工具箱里那些算子来自**随构建打包的包**（每次构建重打，永远是当前契约），
掉的是外部装进来的 5 个。其中一个第三方算子还和内置算子**同名不同键**
（`nexai.2d.find_circle` vs `vision.2d.find_circle`），于是"看着还在"。

根因是当天内核契约 7 → 8（给两个接口各加了几个方法），而规则写着"号不等就拒载"。
**那 5 个包里有 4 个根本不碰这两个接口**——它们的 dll 已经成功加载进进程、
实例化了扩展类，然后死在比较版本号那一行。半个月里契约升了 8 次。

⇒ **能实测就别推断。** 版本号回答的是"作者当时对着哪一版编的"，
不回答"它现在还跑不跑得起来"；在加法式变更里这两件事根本不相关，而加法式变更是绝大多数。
改法：打开插件 dll 的元数据（`System.Reflection.Metadata`），把它引用到契约程序集的
每一个 TypeRef / MemberRef 逐个到当前契约里去找，缺了才拒、**并点名缺的那个成员**。
成本是打开一次 PE，只在号不同时走。

四条配套的判断，每一条都是踩出来的：

- **"最低支持版本区间"是个假解法**。它仍然是**声明**，只是把一个数字换成两个，
  而且由谁在升版那一刻判断 Min 该不该动——正是这次出错的那个判断。
- **查不成 ≠ 兼容**。读不出元数据一律拒。把"没查"说成"没问题"是最常见的那种沉默。
- **装上了要说出来**。"按 v7 编、实测兼容"这句话要出现在人看的页面和模型读的资源里；
  藏起来的话，"按当前契约编的"和"碰巧还能跑的"在屏幕上长得一模一样。
- **两道门要用同一个判据**。包级装载器与扩展级注册各有一道版本门，
  只改前面那道的话，症状是"这边放行那边拒"。

⚠ 还有一条**试过并且失败**的路值得记：只把 `manifest.json` 里的号改大——没用。
宿主还会拿代码里声明的号（`KernelContract.Version` 是 `const`，编译期焊进 dll）与清单比对。
**双声明这件事顺带让"改 JSON 伪造兼容性"不成立**，代价是清单与代码必须一起改。

⚠ 判据这一族的边界写清楚了（限制性断言的规矩）：查得到"调用的成员没了 / 改名 / 参数个数变了"；
查不到"参数个数没变、类型变了"；插件**实现**的接口后来加成员那一类**交给 CLR**
（`TypeLoadException`）——原来它被"发现扩展类"那段代码吞成
「包里没有 IHuikeExtension 实现」，一句与真实原因毫无关系的话。
端到端的反面（真拿一个缺成员的 SDK 编出来的插件）**在仓库里编不出来**，
所以那一半在成员匹配那一层量，并在注释里写明为什么只能这样。

### 4.62 ⚠⚠ "手工拷进去的那一份"是部署物欠账的另一种长相

同一天的第二半：一个厂商插件包**刻意**留在示例目录、不随构建装入，
理由很正当（"相机接入按设计是第三方的事，自动装进去会改变产品的默认装载面"）。
代价是它成了**手工部署物**：契约升版那天仓库里它的清单当天就跟上了，
而装机那台机器上跑的还是三周前手工拷进去的旧版——于是设备页报"这个插件装不上"。

⇒ 这是"改了没进部署物"的又一次，只不过这次挨刀的不是主程序 dll，而是**插件包**。
判断标准很简单：**这个产物有没有一条自动的路从源码走到人跑的那份**。
没有的话，它迟早会落后，而且落后时的症状与"根本没装"长得一模一样。

一个具体的收尾动作：那台机器上的**插件开发包**（由软件自己导出、给第三方用）
里带着一份旧的契约 dll——谁拿它编出来的插件一装就是同一个报错。
**它才是这次事故的上游**，修完现场要顺手把它重导一份。

### 4.63 ⚠⚠⚠ 读硬件状态：能读到的全是征兆，而"坏没坏"没有任何接口回答得了

现场要的是"读取主机 usb 和网卡硬件状态，用来判断 usb 或者网卡是否坏了"。
做下来最值钱的一条不是怎么读，是**读到之后不许说什么**：

链路断开、速率降级、错误计数在涨、USB 设备报错码——这些征兆与
"线没插好 / 对面没上电 / 驱动坏了 / 供电不足"在读数上**完全一样**。
没有任何系统接口会说"这个物理口坏了"。
⇒ 规则给出的动作必须是**对照实验**（换一根线、换一个口、换一台设备），不是判决。
把征兆写成"网卡坏了"，现场会换掉一块好网卡，而原因还在那儿。
这也正好落在"诊断产出面向操作员"那条上：给他一个能做、且做完就能分辨的动作。

**三件真机上才会撞到的事**（设计时一件都没想到）：

- **Windows 把每个 NDIS 过滤驱动也报成一张网卡。** 接相机那块在清单里出现了 **6 次**
  （`-<驱动名>-0000` 后缀），读数完全一样；40 行里 34 行是同一块卡的影子。
  预取里塞进这种清单，等于**真信号被自己人淹掉**。
  ⇒ 按 **MAC 去重**，而不是按"名字里带 -0000"这种命名规律（换个驱动就失效）；
  同组保留名字最短的那条（过滤实例名一定是"真名 + 驱动名 + 序号"）。
  再加一层"只列配了 IPv4 地址的"，40 行降到 6 行。
- **无线会被当成"降速"。** 433 Mb 的 Wi-Fi 不是降级的千兆口。不分开的话，
  每台带 Wi-Fi 的机器上都常年挂着一条假故障——**而报警一多，真的那条就没人看了**。
- **规则必须做设备关联，否则每轮一条假原因。** 开发机上有一张配了地址却断开的备用网卡，
  它跟任何相机都不相干。不关联的话，每一轮诊断都会多出一条与故障无关的"确定原因"。
  ⇒ 网卡快照带**网段**，规则拿设备地址做一次掩码比较，**网段里真有设备才命中**。
  真工控机上这种空着的备用口只会更多，所以这一层不是优化，是能不能上线的分界。

**平台差异关在插件里**：网卡那半两个平台都靠 BCL（`NetworkInterface` +
`IPv4InterfaceStatistics`，实测两边都拿得到；Linux 还多一个 `carrier_changes` 抖动次数）；
USB 那半 Windows 走 `cfgmgr32` P/Invoke、Linux 读 `/sys/bus/usb/devices/`。
主干道一行不动，也没有 `#if` 分叉——**这正是插件存在的理由**。
选 `cfgmgr32` 而不是 WMI 是为了不引 `System.Management`：少一个包，
也少一处"在 Linux 上装得上、一调就抛 PlatformNotSupported"的地雷。

> ⚠ 待确认：Linux 的 USB 读数**没有在真机上验过**。开发机的 Linux 是 WSL2，
> 而 WSL2 里 `/sys/bus/usb` 整个目录不存在（虚拟机没有真 USB 总线）。
> 这句限定词写进了插件的 KNOWN-ISSUES，有真机时验一次再删。

### 4.18 "只是显示不对"会在人试图修正它的那一刻变成数据丢失

方案文件反序列化后，参数标量是 `JsonElement` 而不是 `double`/`bool`/`string`。
**执行链路本来顶得住**（参数绑定会先归一化），所以**跑流程完全看不出来**——
是界面把它照出来的：存盘里 `grayMin=128`，参数面板显示 `0`。

而"显示错"不是最坏的：**人一动面板上任何一个控件，那个 0 就被提交回草稿**，
真值就此没了，且没有任何报错。**一个看起来只是显示问题的缺陷，
会在人伸手去修正它的那一刻升级成静默的数据丢失。**

⇒ 三条：
- **修在加载边界**（一次性把 `JsonElement` 拆成标量），不是在每个显示点做兼容。
  显示点会增生，边界只有一个。
- **判据是类型，不是"跑得对不对"**。写成"跑起来结果对"的话，
  执行链路的宽容会把它一直判绿。
- 「读进来的东西宽容一点也能用」这种局部正确，会把错误推到**别的、更没准备的**消费者身上。
  宽容要放在最外层，内部只见规整数据。

### 4.19 "保存成功"是真话，但真话不等于这件事成了

现场："点保存之后，改的东西重启软件又复原回去了。"
写文件确实成功了，状态栏说的是真话——但**界面构造时无条件新建示例方案**，从不读已保存的；
而草稿 Id 默认是新 GUID，于是**每次启动都是一份新方案**。
用户机器上攒了四个孤儿文件，每一个都是一次"保存成功"。

同一处还有一个静默：方案列表 `List()` 用 `catch {}` 把读不出来的文件直接丢掉。
于是"文件坏了"和"你没保存过"在界面上长得一模一样——
而处置完全相反（前者要去找那个文件，后者本来就没有）。
⇒ 读失败要**带着原因**回去，并且**那个文件绝不许被覆盖**：它是唯一的原始数据。

⇒ 两条：
- **成对的操作要成对验**：存了要能取回来。判据写成"取回来的 Id / 内容与存进去的相同"，
  而不是"保存返回成功"。写入侧的成功是**必要**条件，被人当成充分条件。
- **开机该打开哪一份**是一个有三个分支的决策（恢复了哪份 / 新建了示例 / 读失败了），
  三种要说三句不同的话。埋在窗口构造里就只能靠人重启一次去验，
  而它有一个分支恰恰是"出错的时候"——所以拎成一个独立可测的函数。

### 4.20 关于 Agent 自己：构建结果要按配置分别报

有一次 Release 成功、Debug 因为被运行中的 exe 占用而失败，
我报了一句"已成功生成"——**现场于是在测一个没有修复的二进制**，
接着报"还是不行"，而那句话是真的。**一次错误的汇报把一轮排查整个作废。**

⇒ 多配置 / 多目标的构建，**按"人接下来会用哪一个"分开说**，不要合并成一句。
合并的动机通常是"两个都跑了、听起来啰嗦"，而它抹掉的正是差别所在。
更一般地：**汇报的粒度要对齐人下一步的动作**，不是对齐我执行了几条命令。

### 5.2 已有的几条判据值得单独点出来

- **架构守卫是引用表级的**，不是靠评审：Sdk 的依赖、Sdk.Testing 的依赖、注册表是否被污染、
  提示词里有没有领域词，全是测试。
- **一致性套件一份代码三个出口**：插件作者本地 `dotnet test` 跑它、他的 AI 助手经 MCP 跑它、
  现场"注册插件"按钮也跑它——否则"我这儿是绿的"会变成常态争议。
- **真第三方插件夹具带真原生 DLL**：手法是**不自己编原生库**，
  拿 .NET 运行时自带的压缩库改名拷进包目录——CI 不用装 C 工具链，加载的又是真原生代码，
  且改名后系统搜索路径上不存在，**能解析到就只可能来自包目录**。
  ⚠ 负例必须换一个**不同的库名**：原生库按名字加载后进程内全局复用，
  同进程里前一个用例装上的那份会顶替，负例会假绿。
- **无头 UI 测试**：控件必须在调度线程上构造，否则单跑绿、全跑红。
  另一条只在无头下成立的事实：**没注册字体 ⇒ 布局根本不跑 ⇒ 模板不会被实例化进可视树**。
  要验模板产物就**自己 `Build(vm)` 再塞 `DataContext`**，别指望 `Find` 得到那些控件。
  ⚠ **2026-08-21 修订：上面这条"没注册字体"是错的**，而且它推出了一整套错的测试形状。
  测试会话**会**用那个 `BuildAvaloniaApp`——补上字体与 Skia 之后，
  文本测量、真实布局、几何命中、**真的模拟鼠标点击**全都可用。
  原结论"无头下只能断对象图"由此作废（详见 4.17quater）。

  **同族的第二条：默认关掉渲染时，几何查询一律返回 false。**
  `Geometry.StrokeContains` 在无头下永远说"没命中"——
  在那儿写"点在线上能命中"会得到一条**永远绿或永远红的假判据**。
  ⇒ 判据要分成两半：**能在无头里判的**（类型对不对、挂点对不对）留在主测试，
  **判不了的**（几何、像素、真实布局）拿一个带 Skia 的一次性探针去量，
  并把量出来的数写进代码注释和判据说明里。
  重点不是"探针"这个手法，而是**明写这条测试判不了什么**——
  不写的话，下一个人（包括我自己）会以为它覆盖了整件事。
- **判据至少有一条落在人的入口上**，不能全落在末端动作（见 [4.17](#417-判据选在链条下游上游断了它照样绿)）。
- **新判据一律反证**：把修补注掉，它必须红。这一轮靠反证抓出四条假绿——
  其中一条是测试把 bug 本身编码成了期望值（断言参数读回来是 `JsonElement`）。

**2026-08-31 夜至 09-01 一整轮，仍然全部由现场提问驱动，分两半**：
① **界面**——窗体那条白色系统标题栏归我们画（客户区扩到装饰区，三个系统按钮留着；

⚠ 这一轮**最值得注意的是能力的加法形状**：诊断要"自己调工具定位问题"，

⚠ 这一轮最值得记的不是任何单个修复，而是**问题的来源变了**：
读码自查找出的是"结构上应该有而没有"，现场提问找出的是"结构上有而人到不了"。
后者读代码看不出来（[4.14](#414--解释存在只是不在人所在的地方一天撞了五次)），
**只能靠人真的站在界面前**。

**2026-09-01 又一轮，这次是补一整类设备：通讯。**
产出是两个插件 —— `Comm.Tcp`（TCP 客户端**通道类型**，人在设备页上建出来、配地址、连接）
与 `DataIo`（「数据读取」/「数据输出」两个算子，只认 `ICommChannel`、不认 TCP，
所以以后接串口 / Modbus 不用动方案里的节点）。行为参照根目录那份 `HslCommunication_Net45`
快照（**移植源，不是依赖**：那份是 net45，而主干道要 Windows + Linux 同时跑）——
照搬的是长连接 / 断线重连 / 收发超时 / 四种分包，写在 `System.Net.Sockets` 上是三百行。

这一轮的重点不在"多了一个协议"，在**多了一种设备形状**：相机枚举得出来，通道枚举不出来。
由此内核契约 7 → 8（注册表加工厂面），并配上"清单落盘 + 开机恢复报告 + `comm://@types`"三件套
（[4.55](#455--枚举得出来和人建出来是两种设备硬做成同一个形状会留下一个永远返回空表的方法)）。
顺带修掉一个存量缺陷：`NodeExecutionContext.Services` 宿主从来没传过，
那个口子**测试里通、真软件里永远是 null**（[4.56](#456--那个口子早就有了只是从来没人往里传测试里通真软件里永远是-null)）。
另外三条经验分别关于观测窗口（[4.57](#457--拒绝和超时是两种处置而默认超时短于操作系统回-rst-的延迟时前者会被报成后者)）、
默认值的不对称（[4.58](#458--两个默认值在常见情形下等价在边缘情形下一个静默出错那就不该选出错的那个)）、
以及尺子漏掉被测对象（[4.59](#459--手写的被测清单会和产品分叉尺子那一族的第三例而这次它连漏了谁都不会说)）。
工程侧还有一条：这一轮全程有另一个会话在同一个工作区里改诊断，
提交只能按 hunk 拆（[4.60](#460--一个工作区里两个会话在同时改提交要按-hunk-拆而整文件提交看起来完全正常)）。

这次是它第一次在"加控件"而不是"改配色"上派上用场。

### 7.4 明写为"暂不做"的取舍

- **诊断不做多智能体**（2026-08-25 现场问，当场拍板单 agent）。理由不是难，是**现在加了没法判断有没有变好**，
  而且多智能体的经典收益在这套架构里已经分别归了确定性的那几处：多假设互证归 `ICauseRule`、
  独立验证归 `CriteriaVerifier`、并行取证归 `PrefetchAsync`（并行它不需要 agent，加几行并发就行——
  这一轮已经做了）。剩下能让多 agent 发挥的只有"选工具"这一小块，头寸窄，而代价是四处契约要动
  （`events.jsonl` 的线性顺序要改父子 episode、子 agent 要继承 `RoleRiskCeiling` 而非重算、
  预算变共享池、每 agent 一个 CLI 子进程）。**重开条件**：插件领域多到一个提示词装不下、
  或要做规划层选技能——两者都在评分体系稳定之后。
- **诊断提示词不做"按症状挑段"**（2026-08-25 实测否决）。原以为"相机故障时视觉那段也占位"会稀释上下文，
  实测系统提示词全长仅 1131 字符、领域段 2 段共 302 字符、预算 60k tokens——**稀释不存在**。
  给不存在的问题建过滤机制，等于给下一个人埋一段没有消费者的代码。这条是 [4.3](#43--守卫的绿色可能暗示一个比事实更强的结论) / [4.1](#41--限制性断言必须实测否则一句错话会污染整条推理链) 的正面用法：动手前先实测那个前提。
- 上下文超预算只会"停"不会"裁"：裁要靠模型摘要，而**一条硬停机条件不该依赖模型可用**。
- 无进展签名对"结果里带时间戳"的工具失效：真遇到再按字段名剔除，现在剔除等于凭猜测加规则。
- 存储类 635 行不拆，只写下边界：等有第二个存储实现时再拆，现在拆等于凭猜测定接口。
- 插件与宿主同进程：第三方 P/Invoke 写错一个参数就是宿主无征兆退出，这是明知代价的选择。
- 流程画布**没有对齐线**（`NodifyAvalonia` 没内置）。
- 错误码正文与长篇报告尚未纳入翻译（键位已预留）。
- Linux 只验过 Ubuntu 22.04 一个发行版。
- 生态三件套尚未对外发布。
- 海康只验到「枚举 / 打开 / 触发 / 取一帧 / **读**网络配置」：
  **掉线重连、写 IP、连续取流、彩色相机都没验**，
  按 [4.1](#41--限制性断言必须实测否则一句错话会污染整条推理链) 的规矩这里带着限定词写。
  （2026-08-24 起"读 IP"从"未验"移到"已验" —— 见 [4.24](#424--限制性断言写进代码注释时最危险因为它紧挨着一段正确的规矩)。
  读和写是两条不同的路：写走 `GigeForceIp`，读走整型特征。）
- **写完设备网络配置只报"已写入 N 项"，依据只是返回码**——同一个厂商 SDK
  "接受不支持的写入然后什么也不做"是**已知行为**（触发那组的测试就是为此才断读回值）。
  现在读得回来了，这条路本可以读回核对；没做是因为**验证它必须真改一次 IP**，
  那会把台上唯一在用的相机移出网段。留着，不假装它验过了。
- **没有账号管理界面**：加账号、停用、改别人的角色都要手改 `operators.json`。
- 方案还没有「新建 / 打开 / 另存为」——开机只恢复最近改过的那一份。

### 7.5 顺带一条关于文档本身的经验：状态段会独自烂掉

2026-08-19 写这份交接文档时发现，`README.md` 的「当前状态」一节**落后了整整四轮开发**：
还写着 169 个测试 / 11 个工程（实际 264 / 12）、"界面为骨架"、
"流程画布目前是自绘过渡实现，待接 `NodifyAvalonia`"——后两件早已完成。

**关键在于其他文档全都是对的**：`CONTEXT.md`、`docs/architecture.md`、`docs/security.md`、
`docs/roadmap.md`、ADR，每一轮都跟着改了，只有 README 落下。原因也清楚——
每轮改动都会碰到那几篇专题文档（因为改动本身就在它们的领域里），
而 README 的状态段**不属于任何一次改动的领域**，所以永远没人顺路经过它。

⇒ 两条做法（已落地）：
- README 的状态段**只留一屏概览，并显式指向 roadmap 那一节作为权威版本**——
  一份文档里同一件事有两个权威副本，迟早分叉。
- 数字标明"来自 `scripts/linux-check.sh` 实测输出"，与架构图同源，不手填。

**这正好印证 CONVENTIONS §4.4「状态段最容易陈旧且危害最大」**，
并补上一条它没说的成因：**危害大不是因为它变得快，是因为它不在任何人的必经之路上。**

## 8. 一页纸总结

1. **限制性断言（"X 做不了"、"A 与 B 无法共存"）必须实测，验证不了就带限定词。**
   一句未实测的断言会成为后续判断的依据，错误的事实污染看起来完全合理的推理。
2. **一个系统里两条并行链路，去问"同一件事它们是不是同一种建模"**——不一样就有一条是错的。
3. **写下"某约束由某守卫保证"时，顺手写清那个守卫到底查什么。** 绿色会暗示比事实更强的结论。
4. **"时机"性质的断言要找能在时机内部观察的切入点**；"跑完检查文件存在"证明不了增量落盘。
5. **上下文预算判在调用模型之前**，否则超限与服务不可用无法区分；**中文按 1 token/字符估**。
6. **加了更聪明的判据，就要写明它什么时候失效，并把兜底一起写。**
7. **fail 的方向必须同向**：忘了填就掉到最小权限；判据写成"两侧都不能写生产"，不是"两侧相等"。
8. **两根独立的轴之间要有约束**，否则"可选的声明"就是洞；拒绝理由要指认是哪根轴挡的。
9. **只建"拒绝"的一半，等于把故障点挪到更难指认的地方**（读得进来但编译不过）。
10. **机制先于需要而建时，用可注入的表让它今天就被执行**；选成本最低的时刻定政策。
11. **给人看的文字要翻译，给模型看的文字不要跟着界面语言走。**
12. **裸字符串收敛的判据是"写错一个字母会不会报错"**，不是"字符串多不多"。
13. **经验要写进 Agent 每次都会读的那个文件**，否则等于没写。
14. **⚠⚠ 解释存在，只是不在人所在的地方。**新增任何判定，回答"人从哪儿看到它、从哪儿改它"；
    新增任何参数，当场找出它的消费者。存得下、读不到，比不给这个参数更糟。
15. **测试全绿，而测试环境与部署环境的唯一差别恰好就是坏的那一处。**
    夹具里"不存在的东西"可能正是部署里"存在且有害的东西"；守卫绕开人必经的那一步就等于没守。
    改"初始化时怎么建"的逻辑，必须同时回答"已经建过的那些怎么办"——
    只对全新环境成立的修复，对正在用的人等于没修。
16. **菜单挂在共同祖先上就分不出人点的是谁**；"遍历现有实例改文案"在实例会后续增生的地方一定错。
17. **一条交互链有好几节（手势 → 命中 → 挂点 → 动作），判据按节写、一节一条。**
    同一句症状连报两次以上，就别再在上次那一节里找——把那一节的输出直接打出来。
    换 UI 框架时"能不能点中"不要靠旧框架的直觉（WPF 按几何命中，Avalonia 按画刷）。
    **判据本身判不了什么，要明写出来**（无头没有 Skia，几何查询一律 false）。
18. **⚠⚠ UI 缺陷的判据必须至少有一条真的模拟输入**（按下那个键、点那个位置）。
    断对象图廉价好写，验的却是"我装对了"而不是"人做那个动作会发生什么"。
    并且**"这个环境做不了 X"和"A 与 B 无法共存"同属一类断言，必须实测**——
    它决定接下来所有判据的形状，一句"环境做不了"能让整类判据永远不被写出来。
19. **软件回答不了的问题不要替人回答，但要把证据摆齐。**
    无论人怎么答都不成立的情形要**直接挡**（别包装成选择题）、且挡在最早能挡的那一刻；
    剩下的交给人，问句**点名**，下面摆出软件判断不了的那部分（谁替换谁、什么会消失）；
    最容易是误操作的那一种单独成类；**判不准时宁可含糊，不要说错方向**。
    "出计划"与"执行"分开且计划无副作用——否则确认框给的是一个不存在的选择。
20. **判据只往自己动过的方向长**，于是天然不覆盖"我顺手破坏的事"——
    每个改动都问一句"这一改可能弄坏什么"，并为那件事写一条判据（**挑人看得见的那个属性**）。
    具体 bug 修完顺手提成规则，且**不点名任何类**；规则型判据配一条"至少扫到一个"，否则它静默空转。
    **规则是筛子不是结论**：过了筛子还得量一次这一处。
21. **判据选在链条下游，上游断了它照样绿。**至少一条判据落在人的入口上；
    新判据一律反证（注掉修补必须红）；断言写成规则，别写成具体字段——
    **规则写在名字里、实现成几次点名赋值，等于没有规则**，而这种分叉不可见。
    用反射遍历别人的结构时，"扫不到"可能是没走进去：**判据自己也需要判据。**
22. **"只是显示不对"会在人试图修正它的那一刻变成静默数据丢失。**
    修在加载边界；判据是类型，不是"跑起来对不对"——下游的宽容会把它一直判绿。
23. **写入成功是真话，但真话不等于这件事成了。**成对的操作成对验：存了要能取回来。
24. **一份不完整的清单比没有清单更糟，因为它会阻止人去数。**"完整感"多半来自形式
    （名字带 Fully、列表编号、分栏、排序），不来自核对。自检一句：
    **"这个数字是数出来的还是写出来的"**。而这类缺口通常只有
    "只能看文档、照着做的外部读者"能撞出来——作者看不见自己表里的缺口。
25. **防空转的断言容易反过来把缺陷写死成前提**：锚点要落在扫描器上，不能落在发现上，
    否则代码变好时测试会红。**同族第二例（2026-08-24）**：真机测试里写着
    `Assert.DoesNotContain(静态IP, 读回来的键)`，依据是"这一组读不回来"。
    意图（不许往结果里塞猜的值）是对的，判据却把**"猜的值"和"任何值"混成一件事**——
    真读回来之后，一个变好了的实现让测试变红。锚点该落在"值是真的"上（与另一条
    独立的路对得上），不该落在"键不在"上。
26. **反证本身有假阴性**：patch 可能没落在被测的那处，而"没红"和"判据是空的"颜色一样。
    确认改的是哪一行，或者**让失败信息带上实测值**替你确认——
    顺带一条：只报个数不报清单的断言，会让反证本身变弱。
27. **限制性断言写进代码注释时最危险**：它在必经之路上，而且往往紧挨着一段正确的规矩，
    于是对的那句替错的那句做了担保。**"我们还没实现"和"它做不到"要分开写**——
    写成后者，待办就消失了。
28. **归责只发生在有声明可比对的地方。** 没有声明，缺陷就谁的账都不记——
    加声明才是让归责成为可能的动作。判据只看"声明 vs 结果"，**不判原因**；
    话要指名并给全两条改法；**声明过的不算违规**，否则等于教作者别声明。
29. **单一输入的判据看起来完整。** 覆盖面要跟着代码实际所在的地方走，
    不要跟着写判据那天想到的那个文件走。**反证要落在"改动带来的那部分覆盖"上**——
    在旧输入里造缺陷，旧版本也能抓，验的是本来就有的能力。
30. **汇报的粒度要对齐人下一步的动作**，不是对齐我执行了几条命令；多配置构建分开报。
