读硬件状态时能读到的全是征兆，而"坏没坏"没有接口回答得了——规则要给对照实验不是判决，外加三件真机才撞得到的事（过滤驱动伪网卡、无线被当降速、不做设备关联就每轮一条假原因）；**4.64「能插」和「能插很多个」是两件事——AddService 登记 / GetService 取，第二个插件静默顶掉第一个；4.65 包换目录时旧的那份还在原地，症状是整台软件起不来；4.66 尺子量投影前、人看投影后——折叠把 IP 切成「169.」而「点名」那条判据满分；4.67「太长」不该靠折叠解决（藏起来的是答案本身），短要下沉到生成侧；**4.68–4.69 是 09-02 那一轮的：递给模型的「手上已有的事实」是一份被我们裁剪过的世界（取最早 40 条、按地址去重把一次六值的读数压成一条、一句提示词带偏它、目录没说读数住在哪）——它说「没读到」四次都是真话；以及「追问被回答了」不等于「答的是他问的那件事」，现场连问四次而评测四次满分；**4.70–4.71 同一天下午：中途那句会冒充答复（名字叫「回答」的气泡比真正的收尾早十六秒），以及命中多条原因时「先说哪一条」被规则 Id 的字母序决定——改成按人问的那句话挑，词表用这一刻读到的事实本身，而尺子还在用老挑法于是伪装成「产品退步了」；**4.72–4.73 是 09-03 那一轮的：「删不掉」是这类功能的常态（排到下次启动，而两个平台的真相不一样——Windows 抛 UnauthorizedAccessException、类 Unix 的 unlink 直接删得掉，判据得分三份），以及要求「所有 X 都有某功能」时要做成契约 + 会变红的规则（适用范围由端口划不由名字划、静态规则挡不住「能选能存却没人读」所以要有动态那条、能力要给硬约束留座位）；**4.74–4.75 同一天：加一条「必须支持」的规则时边界由现场划，而且要把「不要求什么」也写进规则并配一条会红的判据；以及验部署物只查 UTF-16 会对写在特性里的文案报假的「没进去」（特性参数在 #Blob 堆里是 UTF-8）**；**4.76–4.78 是 09-03 傍晚「把本地模型交到别人手里」那一轮的：装机器/打包脚本也是尺子——不许自己写产品的配置、「装好了」要由产品那段代码说（尺子那一族的第四例，前三例量运行时、这次量能不能装起来）；「能稳定复现」在多会话工作区里不足以排除并发（三轮隔离一致地指向错误结论，真相是另一个会话在编 Huike.Ui、每轮取到不同的半途产物）；以及「我拷到 A、它读 B」——服务端启动时的 OLLAMA_MODELS 才决定落点，外加 WSH 只认 ANSI 与带 BOM 的 UTF-16（写成 UTF-8 时中文路径变乱码而服务照样起来）、结掉 ollama.exe 后 llama-server.exe 还占着模型文件**；**4.79–4.81 是 09-03 机台包那一轮的：定「给别人读的格式」时要去读那个别人的代码（自认为想周全了，读完消费侧发现三处会真出事——清单撞名 manifest.json 在那边已经是「插件包清单」的意思、包名必须 ASCII 而中文 Windows 上机器名本身就是中文、承诺了分层却没给对面判断依据；一份契约的对错只在两边之间成立）；「便于以后增加内容」这半句需求的答案是加一个扩展维度而不是加字段（连带两条：「这一节没内容」要区分三种原因对应三种动作、一节抛异常不许拖垮整个包）；以及契约版本 +1 之后红的是 89 条测试而症状是「诊断超时」——耗时从 30s 涨到 5m22s 是最早的信号，而它不在失败列表里**；**4.82–4.88 是 09-08 那一轮的：root 跑出来的绿是假绿（权限类缺陷只在非 root 才现形，Linux 回归账号从此改成非 root）、两种失败的异常类型相同而下一步相反（靠"我改不改得动它"分开，别靠异常类型）、Windows 上是一个目录而 Linux 上是两个（`Config/` 大小写，且修法里的路径比较也要按平台选）、功能做了一半而缺的那半没有落点（`IsDesignTime: false` 只在判据里出现过——这类事实可以 grep）、无头 UI 一轮收尾会执行还排着的渲染作业（队列没排干时症状落在下一条判据上）、模态确认框在无头下开不了所以"问那一句"要留接缝（外加：关 owner 窗口时从属窗口的关闭请求先到）、以及置灰理由挂在每次发布上会让理由里那个探针变成持续的文件写**；**4.89–4.91 是同一轮收尾的：变异检查还原后编译系统要看得见（`copy2` 保留 mtime ⇒ 复跑的还是变异那次的 dll，而"改回去了还是坏的"最像产品真坏了）、PowerShell 脚本参数不能叫 `$Args`（分支静默不走，症状和"命令行开关没生效"这个产品缺陷一模一样）、以及一个改变"下次打开看到什么"的开关必须同一轮给出回来的路（屏幕留痕 + 设上就说怎么回来 + 界面里那条路 + 命令行逃生口；四档里"目录不在了"刻意不进）**；**4.92–4.93 是那一轮收尾又撞的两条：默认内容的含义会随功能变化（"第一次装机的样板"在有了工程管理之后变成"每建一个工程都撞一次"，而且删它要整份删——留着会被下一个人接回启动路径），以及 `await using` 自己也是一次 await（库里少这一处 `ConfigureAwait(false)`，界面线程上阻塞等它就是死锁，而症状是"测试跑不完"、最像环境慢）** ；**4.94–4.100 是 09-08 第三轮（补屏控件 + 出 Linux 交付包）的：接口上"带默认实现的属性"被实现成同名方法时编译器不吭声、功能静默失效，而判据用具体类型调那个方法所以照样绿（判据和产品走的不是同一条路）；一句对的约束得出了偷懒的结论（"控件要在调度线程上造"⇒"那就不造控件"，代价是 `Create()` 从没被执行过）；相对路径按进程当前目录解而人可以从任何目录起软件；跨平台交付时"同名不同内容"的缓存不能跟着走（名字里带的是显卡型号、不带平台，所以名字不会提醒任何人，而后果是硬崩）；交付包里的路径要占位符 + 安装时替换 + **记下当时的根**（包被移动过要重新指并说出来）；判据里的全称量词必须说清论域（指到解开的安装包上跑时，"一个都没被跳过"会红在装载器做对了事上）；WSL 里连续启界面必须有同会话对照**；**4.101–4.105 是 09-08 第三轮（照现场那份 51 个模块搭流程）的："模块少了很多"少的不是插件而是流程——随手搭的示范流程和照现场搭的那份在交付包里长得一模一样（同样在、同样编得过、屏上同样有数字在动、验收同样全绿），所以验收要加**形状**判据而不只是"东西在不在"；一条产线六台相机时六个取图节点会**全部拿到同一帧**而每个节点都报"完成"（判据要断"两路各自拿到了自己那张"，断"跑完了"证明不了）；脚本"报了成功"而软件行为没变（同一个脚本连错两次：改错了字段、以及 ISO 时间串截到整秒后字符串序≠时间序）；环境自检里问硬件的命令一律带超时（D 态的 `nvidia-smi` 让安装脚本永远不返回，而"超时了"和"没装驱动"的下一步不同）；PowerShell 5.1 读没有 BOM 的 `.ps1` 按 ANSI 解时**脚本行为会静默改变**，不止是中文乱码**；**4.106–4.110 是 09-09 那一轮（窗口暗色 + 节拍）的：跨平台修复只在一个平台验过时，另一个平台上它常常不是"没生效"而是**把问题变成两倍**（判据断的是"我们提了这个要求"，不是"系统答应了"——两个平台都绿）；计算属性不发变更通知会让绑定永远停在初值，而"算出来了"的判据绿着、同一块界面里另一半在动是最强的伪装；`??=` 用在有样式默认值的属性上是一句静默空操作；"看起来天经地义"的不等式判据可能是假的，真流程上断不出来的东西要用手造输入断；`pkill -f` 会连执行它的那个 shell 自己一起杀掉，后面的拷贝一行都不执行**；**4.111：一个数字回答不了"慢在哪"，两个对不上的数字能（整机节拍 1520 ms vs 每路 72~77 ms，差的 1400 ms 一眼看出不在检测里）——外加两条：`foreach + await` 遍历互相独立的外部设备时默认它是错的（代价随设备数线性增长，一两路的开发环境里不显形），以及"为了让人看清"而加的等待不许进性能读数**；**4.112–4.118 是 09-09 下半场（条件分支改成选父节点的属性）的：`timeout` 挡不住 D 态进程——上一轮"已修好"的那个超时在同一处又卡了十分钟（一个修复只验过它想挡的那类里较容易的一半时，长得和真修好了一模一样）；"测试绿了"可能是上一次的二进制在绿，而做掉信号的是我为了少看点输出加的那个 `grep`；检查方法自己会坏且**给出相反的结论**（机器上没装 `strings` ⇒ `grep -c` 恒为 0，差点宣布改动没进去）；同一个缺陷形状在第二处重演——"什么时候算改了"是每个实现各自决定一次的语义，判据必须跟着实现走；拆/拼互为逆时"拆不动"必须返回空而不是半张表（`(A`、`2)` 那种名字看起来像拆成功了）；两类插件够不着彼此时共用的语法必须搬到唯一共同依赖上，抄一份的失败方式是"编辑器拼出一句算子看不懂的话而屏幕上完全正常"；以及给人挑的清单在异步 DAG 上"用不了"是**偶发**的（非祖先节点这一帧可能没跑完，得同时加一条只定先后的边）** | `HuikeAgent` | 活跃 | 2026-09-10 |

## 怎么维护

在**任意项目目录**下对 Claude Code 说 `/update-experience`，它会：

1. 读取本仓库 `docs/` 下所有文档的 front matter，找出与当前项目关联的那份；
2. 扫描该项目自 `last_updated` 以来的变化（git log、未提交改动、新增测试与回归结果）；
3. 增量更新对应文档，**只改变了的章节**，并刷新 `last_updated`；
4. 同步本 README 索引，然后 commit & push。

规则见 [CONVENTIONS.md](CONVENTIONS.md)。所有写入都是增量的 —— 已有结论不会被无声覆盖，冲突会先问你。

## 一条硬规矩：不写机器上的路径

这里记的是经验，不是某台机器的目录结构。项目用名字指代，文件用仓库内相对路径加行号；
区分两份副本时按内容特征认（「有 `New3D\` 的那份是主线」），不按盘符认。
理由和完整对照见 [CONVENTIONS.md](CONVENTIONS.md) §3。
